# On‑premise + вход через SSO + push-relay — исследование

Статус: 2026-10-21. Это исследование, разработка не начата. Связано с
[multi-account.md](multi-account.md).

Задача:
- продавать копии серверной части (`~/GolandProjects/iperon`), которые заказчик ставит
  у себя;
- клиент один, из сторов;
- на экране входа есть «Войти через SSO»: OAuth/OIDC заказчика, который отдаёт номер
  телефона;
- пуши уходят через наш отдельный микросервис.

## 1. Вывод

**Сделать можно, принципиальных блокеров нет.** Ниже то, что упрощает задачу.

- **Шифрование пушей.** `p` в пушах уже зашифрован сквозняком между сервером и
  устройством: ключ — HKDF от ключа сессии, `crypto/push.go:16-79`. Relay увидит
  только токен и шифротекст. По этой схеме работают Zulip 12 и Nextcloud.
- **Модель входа.** Код входа через Яндекс — готовый шаблон для SSO (сам вход
  через Яндекс на on‑prem не предлагается, он остаётся только в облаке). Идентичность —
  телефон, внешний ID не храним, создание пользователя общее (`Confirmation`). OIDC —
  это тот же поток, только токен проверяется по-другому.
- **Сервер почти не завязан на нашу инфраструктуру.**
  - Mongo, Redis, NATS, S3 и LiveKit задаются конфигом.
  - Лицензионных проверок нет.
  - `iperon.net` есть только в дефолтах.

Что придётся сделать (подробно ниже):
1. **Push-relay** (отдельный сервис у нас). Call-пуши сейчас идут **открытым текстом**,
   их надо перенести в `p` до запуска relay.
2. **Клиент должен уметь работать с произвольным сервером.** Сейчас хост, отпечаток
   ключа сервера, URL эмодзи и Yandex client_id приходят из **глобального** Firebase
   Remote Config. Их нужно получать из метаданных сервера. По сути это мультисервер из
   multi-account.md, этап 4.
3. **Обнаружение сервера** при входе: код компании, домен, QR, MDM.
4. **SSO** по серверной схеме: OIDC-клиентом выступает сервер заказчика, а не
   приложение.
5. **Упаковка сервера:**
   - снять обязательность call-password и SMTP;
   - переключатели способов входа;
   - подпись ссылок CDN не только в формате Selectel;
   - docker-compose или Helm;
   - лицензия и токен relay.

Как устроено у других:
- **eXpress** (самый близкий российский аналог): серверы заказчика (CTS) ходят через
  вендорские транспортные серверы по выданным вендором токенам. Для крупных заказчиков —
  отдельное брендированное приложение со своими пушами (ETS).
- **Rocket.Chat:** обязательная регистрация сервера на вендорском шлюзе и квота
  10k пушей в месяц бесплатно.
- **Mattermost:** HPNS только на платных тарифах.
- **Zulip:** `register_server` выдаёт ключ; ≤10 пользователей бесплатно, дальше
  подписка.
- **Nextcloud:** бесплатно до 500 пользователей.

## 2. Сервер сегодня (факты)

- **Сборка.** Uber Fx (`internal/api/di.go`). Конфиг — один `iperon.yaml` (cleanenv)
  плюс env. Docker-образ `FROM scratch`. Postgres нет: Mongo, Redis, NATS JetStream.
- **Обязательные настройки.** Валидация при старте (`internal/settings/settings.go:597-640`)
  требует `callPassword.*` и `smtp.*`. Без провайдера new-tel и SMTP сервер не
  запустится. Для on‑prem это надо ослабить: проверять только включённые способы входа.

Зависимости, привязанные к нам:

| Что | Где | Что делать для on‑prem |
|---|---|---|
| Call-password new-tel | `callPassword`, webhook `POST /webhooks/v1/callpassword` | Опционально; по умолчанию выключено |
| Обход для App Store-ревью (`79166200050` / `4545`) | `phoneNumberModerationApplicationStore` | Выключено |
| Yandex ID (наш clientId) | `oauth.yandex` | **Не используется на on‑prem** — всегда выключен; кнопку Яндекса клиент не показывает (способы входа берёт из метаданных сервера) |
| Passkeys (RP ID `iperon.net`) | `webAuthn` | **Выключить.** Приложение из стора не может объявить домен заказчика в associated domains / assetlinks |
| SMTP (письма облачного пароля, шаблоны «Iperon») | `smtp.*` | Опционально, вместе с облачным паролем |
| S3 и CDN: подпись ссылок в формате Selectel `md5(token,expires)` | `storages.*`, `settings.go:38,147` | Добавить S3 presigned или nginx `secure_link`; MinIO в поставке |
| LiveKit (+ TURN) | `livekit.*` | **Переходит к заказчику целиком** — см. §5a; наши `livekit.iperon.net` / skynet не используются |
| FCM / APNs (наш проект, наш .p8) | `push.*` | **Уходит в relay** |
| GeoIP (вшитый GeoLite2) | `internal/geoip` | Проверить лицензию MaxMind на перепродажу; иначе выключать |
| Яровая (`retention.*`) | выключено по умолчанию | Решает заказчик |
| Ключи сервера (EdDSA, ML-DSA, VOPRF, salt, encryptor) | конфиг | Генерируются при установке (`cmd/voprf-keygen` плюс скрипт) |

## 3. Как клиент находит сервер заказчика

Приложение одно, поэтому при входе надо понять, на какой сервер идти. Варианты,
от основного к запасным:

1. **Код компании или домен** (рекомендуется как основной).
   - Пользователь нажимает «Войти через SSO» и вводит `acme` или корпоративный email.
   - Наш справочник (это может быть сам push-relay или отдельный `directory.iperon.net`)
     отдаёт адрес сервера. Сервер регистрируется там вместе с лицензией.
   - Альтернатива без справочника: `https://<домен>/.well-known/iperon` на домене
     заказчика.
2. **QR-код или ссылка** `iperon://server?host=…&key=…` из админки или письма.
   Отпечаток ключа сервера сразу пинится.
3. **MDM / AppConfig** (iOS managed app config, Android managed configurations).
   Для корпоративных парков сервер подставляется без ввода.
4. **Ручной ввод адреса** — для админов (скрытый пункт).

После этого клиент делает pre-auth `META_DATA_INFO` (он уже есть,
`services/metadata.go:72-98`). Ответ расширяется:
- имя организации;
- включённые способы входа;
- SSO-параметры;
- URL CDN и эмодзи;
- нужно ли подключаться к relay;
- минимальная версия клиента.

Сейчас всё это приходит из Remote Config, то есть одинаково для всех. Ключ сервера
пинится при первом подключении (TOFU) или из QR. Сейчас отпечаток
`PUBLIC_KEY_EDDSA_FINGERPRINT` в клиенте **не используется вообще**: ML-DSA-подпись
проверяется ключом из ответа того же сервера.

## 4. SSO (OIDC) с номером телефона

### Схема — серверная (как у Zulip и Rocket.Chat)

Приложение не является OIDC-клиентом IdP заказчика. Клиент у IdP —
**сервер заказчика**: confidential client, секрет хранится только на сервере.

```
App ── ASWebAuthenticationSession / Custom Tabs ──> https://<server>/sso/start?state&code_challenge
<server> ──302──> IdP /authorize (scope=openid phone, PKCE, nonce)
IdP ──302──> https://<server>/sso/callback?code
<server>: code → tokens (token endpoint), UserInfo → phone_number(+verified)
<server> ──302──> net.iperon.messenger:/sso?code=<one-time>&state
App: AUTH_SSO{one-time code, code_verifier, ключи ML-KEM} → confirmationSession
     → (облачный пароль?) → AuthLoginCompleter
```

Почему так:
- **Нет client_id заказчиков в приложении.** Redirect URI для IdP — всегда домен
  самого сервера, он настраивается один раз в админке IdP.
- **Callback в приложение** — фиксированная custom-схема. Универсальные ссылки не
  подходят: приложение из стора не может объявить домены всех заказчиков.
- **Защита от подмены.** Одноразовый код погашается только с `code_verifier` того же
  приложения и только на том сервере, который начал поток. У Mattermost Mobile был CVE
  ровно на это (CVE-2024-39767): привязывать callback к серверу через `state`.
- **SAML** ложится в ту же схему: сервер — SP, телефон берётся из атрибута. Это даёт
  поддержку ADFS и старых IdP.

### Изменения на сервере

Клон `services/auth_yandex.go`:
- телефон в E.164;
- `FindByPhoneNumber`;
- флаги 2FA;
- `AuthConfirmation` в Redis;
- новый `PhoneVerificationSource` (`models/users.go:12-16`) и `loginMethod`;
- ветка в `phoneAllowedForSource`: любой регион, как у Яндекса;
- proto по образцу `yandex_v1.proto`;
- HTTP-ручки `/sso/start` и `/sso/callback` в существующем chi-сервере webhooks.

Конфиг:
```yaml
sso:
  type: oidc            # oidc | saml
  issuer: https://idp.acme.ru/realms/acme   # discovery → JWKS, endpoints
  clientId / clientSecret
  scopes: [openid, phone]
  phoneClaim: phone_number                 # Entra: свой claim из user.mobilephone
  requireVerified: true                    # phone_number_verified
  buttonTitle: "Войти через ACME"
```

Проверки:
- `iss`, `aud`/`azp`, `exp`, `nonce`;
- JWKS кэшируется;
- таймауты http-клиента.

Телефон брать из **UserInfo**. По OIDC Core §5.4 claims из scope `phone` попадают в
id_token, только если access token не выдаётся.

### Номер телефона у разных IdP — главный риск

| IdP | Телефон |
|---|---|
| Okta | scope `phone` → `phone_number` + `phone_number_verified` ✔ |
| Keycloak | встроенный client scope `phone` (атрибут `phoneNumber`). «Verified» что-то значит только с расширением вроде keycloak-phone-provider (SMS OTP) |
| Microsoft Entra ID | по умолчанию нет. Нужен claims mapping `user.mobilephone` → `phone_number` (своя регистрация на заказчика) или Graph `/me?$select=mobilePhone`. Флага verified нет |
| ADFS | своё правило claim из LDAP `mobile`; scope `phone` нет |
| authentik | своя Scope Mapping |
| Google Workspace | **телефона в OIDC нет** (только Admin SDK / People API) |
| Яндекс ID, VK ID | есть, но это потребительские IdP; на on‑prem вход через Яндекс не предусмотрен |

Выводы:
- В корпоративных IdP телефон часто **отсутствует или не подтверждён**.
- Нужна опция `requireVerified: false`: заказчик сам отвечает за свой каталог.
- Нужен запасной путь, если телефона нет. Варианты:
  - (а) отказ с понятной ошибкой `sso.phoneMissing`, как у Яндекса;
  - (б) подтверждение номера после SSO (call-password или SMS у заказчика);
  - (в) телефон из SCIM или каталога по `sub`/email.

  На старте предлагается (а) и (б).

### Привязка к учётке IdP (отличие от Яндекса)

В корпоративной среде уволенного сотрудника надо отключить. Поэтому, в отличие от
Яндекса, предлагается хранить у пользователя `(issuer, sub)`. Варианты отзыва:
- периодически проверять refresh token или UserInfo и отзывать сессии;
- OIDC back-channel logout;
- позже SCIM.

Это решение для обсуждения: оно расходится с правилом «внешних ID не храним». Но на
on‑prem данные принадлежат заказчику.

## 5. Push-relay — отдельный микросервис

### Что выносится
Из `internal/services/push.go` уходят:
- FCM-клиент и два APNs-клиента (production/sandbox из одного `.p8`, топики
  `<bundle>` и `<bundle>.voip`);
- `sendFcmMessage`, `sendApnsVoip`, `sendApnsAlert`, `sendApnsBackground`.

На сервере (в том числе on‑prem) остаётся всё, что знает о пользователях:
- выбор сессий;
- гейт по присутствию;
- настройки уведомлений;
- сборка и шифрование `PushPayload`;
- ретраи (`withRetries`);
- очистка мёртвых токенов (`clearToken`);
- JetStream-очередь `push`.

**Наш облачный сервер тоже ходит через relay.** Один путь кода, и relay
обкатывается на нас самих.

### API relay (черновик)

gRPC или HTTP/2 + protobuf, батч до N сообщений:

```
SendRequest {
  channel: APNS_ALERT | APNS_VOIP | APNS_BACKGROUND | FCM | (позже RUSTORE | HMS)
  token, fcm_fid, apns_sandbox
  p                    // зашифрованный PushPayload — relay не читает
  priority, ttl/expiration
  collapse_id, thread_id   // HMAC на сервере, а не chatID в открытом виде
  badge, sound, mutable_content, content_available
}
SendResult { status: SENT | DEAD_TOKEN | RETRYABLE | QUOTA_EXCEEDED, retry_after }
```

- Топик и bundleID знает только relay.
- `DEAD_TOKEN` возвращается серверу, тот по-прежнему чистит токен у себя.

### Аутентификация, лицензия, лимиты
- **Регистрация установки.** Каждая установка получает `tenantId` и секрет (или mTLS-
  сертификат) при регистрации лицензии. Так устроены Zulip `register_server` и
  токены RTS у eXpress. По этому же ключу работает справочник «код компании → адрес
  сервера» из §3.
- **Лимиты.** Rate limit и квоты на tenant; метрики на tenant (без токенов и
  содержимого).
- **Токен не принадлежит одному tenant.** Один телефон с мультиаккаунтом на разных
  серверах держит один APNs-токен.
- **Отключение.** Отзыв лицензии отключает relay для этой установки. Это рычаг
  монетизации, как у Rocket.Chat и Mattermost.

### Что relay видит — что нужно закрыть до запуска
1. **Call-пуши сейчас открытым текстом** (`push.go:432-462`): `callId`, `fromUserID`,
   `nameCaller`, `callerPhone`, `nameFromContact`. Это надо перенести в `p`.
   - Клиент: расшифровка в `AppDelegate` (PushKit требует сразу показать CallKit; ключ
     в Keychain доступен) и в `CallFcmService.kt`.
   - Это же даёт мультиаккаунту keyId для звонка.
2. `thread-id` = hex `chatID` и `collapse-id` вида `group:<chat>:<msg>` заменить на
   HMAC (ключ — секрет установки).
3. Бейдж и звук видны. Это допустимо.

В остальном relay видит: токен, IP сервера заказчика, время и размер. Логи хранить
по минимуму. 152-ФЗ: в пуше нет персональных данных в открытом виде, это снижает
риск трансграничной передачи через Apple и Google. Юристу всё равно проверить.

### Задержка и доступность
- Звонки чувствительны к задержке. Relay ставить в РФ, рядом с APNs/FCM-egress,
  в два инстанса.
- У сервера заказчика очередь JetStream: если relay недоступен, пуши копятся и
  ретраятся. Звонковые пуши со старым TTL не досылать.

### Позже
- **RuStore Push / HMS** как дополнительные каналы. RuStore требует установленный
  RuStore на устройстве.
- **Брендированное приложение заказчика** со своими ключами и своим relay (модель ETS
  у eXpress) — опция для крупных и закрытых контуров.
- **Без Google:** WebSocket-фоновое соединение на Android.

## 5a. Звонки — инфраструктура заказчика

Медиа звонков полностью уходит к тому, кто разворачивает on‑prem: LiveKit SFU и TURN
стоят в контуре заказчика, наш LiveKit (`livekit.iperon.net`, VDS skynet) и наш TURN
on‑prem-установки не используют. Через нас идёт только пуш-«будильник» о входящем
звонке (через relay, содержимое зашифровано в `p`).

- **Клиент уже готов.** Адрес LiveKit не зашит в приложение: сервер отдаёт его в
  `CALL_TOKEN` (`protos/call_v1.proto:62`, поле `url`), токен LiveKit тоже чеканит
  сервер (`api/v1.go:2244-2310`). Значит, на клиенте менять нечего.
- **E2EE звонков** не зависит от того, чей LiveKit: публичные ключи едут в
  `CALL_TOKEN` и атрибуте `e2ee.pub`, SFU видит только шифротекст.
- **Что поставляем заказчику:** LiveKit в составе docker-compose/Helm, конфиг
  `livekit.{url,apiKey,apiSecret}`, встроенный TURN LiveKit или отдельный coturn.
  Рецепт берём из нашего прода: TURN/TLS на 443 через nginx SNI-мукс (иначе с сотовых
  сетей и из корпоративных сетей с закрытым UDP не дозвониться), UDP-диапазон для
  прямого медиа, валидный сертификат на домен TURN.
- **Требования к заказчику (документация админа):** публичный адрес/домен для LiveKit
  и TURN, если сотрудники звонят извне контура (с мобильного интернета); открытые
  порты (443/TCP, UDP-диапазон медиа, при необходимости 3478); ресурсы под SFU
  (оценка по числу одновременных звонков). Для полностью закрытого контура (только
  Wi‑Fi/VPN внутри) — достаточно внутреннего адреса.
- **Проверка развёртывания:** в админке/CLI — тест «сервер → LiveKit» (выдача токена,
  подключение) и подсказка проверить TURN (например, trickle-ice тест).
- **CallKit / ConnectionService** работают как прежде: пуш будит приложение, дальше
  клиент идёт на LiveKit заказчика по `url` из `CALL_TOKEN`.

## 6. Что не входит

- **Федерация между серверами** (пользователь on‑prem пишет пользователю облака) —
  отдельная большая тема. Аккаунты на разных серверах полностью изолированы,
  мультиаккаунт даёт держать оба.
- **Сертификация ФСТЭК** — отдельный трек, если заказчик из госсектора или КИИ.

## 7. Этапы

1. **Call-пуши в `p` и HMAC вместо thread/collapse-id** (сервер и клиент). Полезно
   уже сейчас, и это нужно для мультиаккаунта.
2. **Push-relay** (новый репозиторий, Go):
   - API;
   - tenant-аутентификация и лимиты;
   - перевод облачного сервера на relay;
   - метрики в Grafana.
3. **Клиент, произвольный сервер:**
   - метаданные сервера вместо Remote Config;
   - TOFU-пиннинг;
   - экран «Войти через SSO» → код компании, QR, ручной адрес;
   - справочник.

   Пересекается с этапами 2 и 4 мультиаккаунта.
4. **SSO на сервере** (OIDC, затем SAML) и `AUTH_SSO` в клиенте. Проверка на
   Keycloak и Entra.
5. **Упаковка on‑prem:**
   - необязательные call-password и SMTP;
   - флаги способов входа (Яндекс на on‑prem выключен всегда);
   - выключенные passkeys;
   - подпись ссылок для MinIO/nginx;
   - docker-compose (Mongo, Redis, NATS, MinIO, LiveKit + TURN/TLS на 443, nginx);
   - документация по сети для звонков (порты, домен TURN, сертификат);
   - генерация ключей;
   - документация админа;
   - лицензия.

- В репозитории сервера закоммичены `iperon.yaml` и `.github/iperon.yaml` с похожими на
  настоящие секретами: SMTP, ключи S3 Selectel, ключ call-password, EdDSA/ML-DSA. Если
  они настоящие, их стоит перевыпустить и вычистить. Перед продажей on‑prem это
  обязательно: заказчики могут получить код.
- Webhook `POST /webhooks/v1/callpassword` не проверяет ни подпись, ни IP провайдера.

## 9. Открытые вопросы (решения бизнеса)

- **Модель лицензии и цены relay:** по пользователям или бесплатно до N, как у Zulip
  и Nextcloud.
- **Обнаружение сервера:** справочник «код компании» у нас (зависимость от нашей
  инфраструктуры) или только `.well-known` на домене заказчика и QR.
- **Способы входа на on‑prem:** только SSO или SSO плюс звонок/SMS провайдера
  заказчика.
- **Хранение `(issuer, sub)`** для отзыва доступа уволенных — да или нет.
- **Брендированные приложения** для крупных заказчиков — предлагать ли сразу.
