# Мультиаккаунт — исследование

Статус: 2026-10-21. Это исследование, разработка не начата. Связано с
[on-premise.md](on-premise.md): там аккаунты могут жить на разных серверах.

## 1. Вывод

Клиент целиком построен вокруг одного пользователя. Кэш SQLite готов примерно на 60%:
большинство таблиц чатов уже имеют ключ `userID`. Всё остальное пока одно на приложение:
`Auth`, `API`, DI, синглтоны чатов, ключ пушей, call-пуши, теги уведомлений.

Сервер к мультиаккаунту почти готов:
- сессии хранятся отдельными документами, уникальных индексов на `deviceId` или токен нет;
- `DeleteDeviceSessions` фильтрует по паре `(userId, deviceId)`, поэтому вход вторым
  аккаунтом не выбивает первый;
- один и тот же push-токен можно зарегистрировать на сессии разных пользователей.

**Рекомендация:**
- **Своя БД и своя папка у каждого аккаунта** плюс **контейнер сервисов на аккаунт**
  (`AccountScope`).
- **Колонку `userID` во все таблицы не добавлять.** Иначе мультисервер (on‑prem) не
  получится: `userID`, `chatID` и `cdnID` уникальны только в пределах сервера, а
  `profiles` зависит от того, кто смотрит (приватность, блокировки).
- **Выход из аккаунта** — удалить его папку.

Лимит — как в Telegram: 3 аккаунта, позже можно 4–5.

## 2. Что сейчас глобальное (факты)

### Auth / сессии
- `lib/auth.dart:24-49`: одна `Session _session`.
- `sessions.getActive()` (`lib/repositories/sessions.dart:27`) берёт `WHERE isActive = 1`
  без `ORDER BY`.
- `deleteAndCreate` (l.18) удаляет только строки того же `userID`. Со вторым аккаунтом
  появятся две активные строки, и какая из них победит — случайно.
- `deleteActive` удаляет все активные строки.
- В таблице `sessions` нет колонки хоста.
- `users.dart:23` удаляет других пользователей с тем же телефоном. Между серверами это
  неверно.
- `AuthLoginCompleter` не передаёт `deviceId` в `AUTH_CONFIRMATION`. Передаёт только
  store-moderation. Без `deviceId` серверная дедупликация по устройству не работает.
- При logout локальные данные не стираются, кэши синглтонов в памяти не сбрасываются.

### БД
- Один файл `iperon.db` (`repositories.dart:90`), один пароль `databasePassword` в
  secure storage.
- Ключ `userID`: `cache`, `myProfile`, `privacySettings`, `notifySettings`, все
  `chat*`-таблицы.
- Ключ `sessionID`: все `secret*`-таблицы.
- Колонка `userID` есть, но запросы её игнорируют: `deviceSessions`
  (`device_sessions.dart:10,19`).
- Без владельца:
  - `settingsDevice` — остаётся глобальной;
  - `profiles` — зависит от смотрящего;
  - `contacts` — облачные контакты (`isCloud`) принадлежат аккаунту;
  - `callLogs`;
  - `hiddenProfiles`;
  - `uploads`, `downloads` — `cdnID` уникален только на одном сервере.
- Папки `chat_outbox`, `secret_media` и кэш `media` (`cdn.dart:780`) — общие.

### API
- `lib/api.dart:252-302`: два канала (`main`, `upload`) создаются **один раз** из
  `settings.apiHost`. Хост во время работы не меняется.
- Авторизация — не gRPC-метаданные. Она лежит в заголовке зашифрованного payload
  (`crypto/syncer.dart:36-58`). Поэтому один канал мог бы обслуживать несколько сессий
  одного сервера, но `sendEncoded`, `unaryEncoded*` и `_dispatch` читают
  `getIt.get<Auth>().session` (l.405, 564, 650, 855, 873, 890).
- Один стрим, один `Subscribe`.
- `_handleMessage` пишет входящие данные под активный `userID` и маршрутизирует в
  `ChatsSync.instance` / `SecretChatsSync.instance`.
- `unauthenticated` → глобальный `Auth.logout()` (l.338, 527, 796).

### Синглтоны с состоянием пользователя
- **get_it:** `Auth`, `API`, `Repositories`, `CDNManager`, `Calls`, `PushManager`,
  `CallPush`. Мест вызова около 200 (`Auth` — 40, `API` — 47, `Repositories` — 56,
  `CDNManager` — 19).
- **Статические `.instance`:**
  - `ChatsSync` — `me`, очередь, флаги, бэкфилл;
  - `ChatsRemoteDataSource` — кэши имён, превью, аватаров, окна истории;
  - `ChatsPresence`, `ChatsTyping`;
  - `SecretChatsSync`, `SecretChatsMedia`;
  - `PrivacyBlocks._refreshed`;
  - `ChatCubit._pendingForwards`;
  - `ChatsMediaCleanup`.
- **Глобальными можно оставить:** `Logger`, `Settings`, `Utils`, `Crypto`, `VoicePlayer`,
  `AudioRoutes`, `DeepLinks`, `DevicePerformance`, `AnimatedEmoji`.

### Пуши
- Протокол уже предусматривает мультиаккаунт: в заголовке `p` лежит `session[0:8]`
  как keyId (`protos/push_payload_v1.proto`, `docs/plans/push-notifications.md:52`).
- Хранилища ключей держат **один** ключ:
  - `PushKeychain.putKey` вызывает `clearKeys()` (`ios/Shared/PushKeychain.swift:51`);
  - `PushKeyStore.put` удаляет все `key_*` (`PushKeyStore.kt:38-47`).
- Теги уведомлений `chat:<chatHex>` (Android) и `threadIdentifier` (iOS) пересекаются,
  если у двух аккаунтов есть личный чат друг с другом: `chatID` у них один.
- Tap, «Ответить» и «Прочитано» несут только `chatID`. Ответ уходит под
  `ChatsSync.instance.me` (`push.dart:434`).
- Флаг пасскода, скрытые профили, аватары (`u<userID>`/`c<chatID>`) и бейдж —
  глобальные.
- Регистрация токена идёт только через активную сессию (`push.dart:577-610`).

### Звонки
- Call-пуши (VoIP и FCM) **в открытом виде** и **не говорят, какому аккаунту звонят**
  (сервер `services/push.go:432-462`: `callId`, `fromUserID`, `nameCaller`,
  `callerPhone`…).
- Клиент: `AppDelegate.swift:306-345`, `CallFcmService.kt`.
- `Calls` берёт `selfUserID` из глобального `Auth` (`calls.dart:764`) и пишет в
  `callLogs` без владельца.
- CallKit — один звонок на устройство. Принять звонок надо через `API` того аккаунта,
  которому звонят.

### Секретные чаты
Состояние ratchet хранится по `sessionID`, то есть уже привязано к аккаунту.
Долгоживущего ключа устройства нет.

## 3. Целевая архитектура

```
global (device):
  settingsDevice, deviceID, Logger/Settings/Utils/Crypto
  accounts.db (или keychain-индекс):
    accounts(accountId, host, port, secure, serverKeyPin, userID,
             sessionID, session, sharedKey, salt, sortOrder, isActive, addedAt)
per account  <appSupport>/accounts/<accountId>/:
  iperon.db (пароль databasePassword:<accountId>), chat_outbox/, secret_media/, media/
  AccountScope { Auth(session), API(host), Repositories, CDNManager,
                 PushManager(часть токенов), Calls(identity, logs),
                 ChatsSync, ChatsRemoteDataSource, ChatsPresence, ChatsTyping,
                 SecretChatsSync, SecretChatsMedia, PrivacyBlocks }
```

- `accountId` — случайный локальный id, не `userID`: на разных серверах `userID` может
  совпасть.
- Таблицы `sessions` и `users` переезжают в `accounts`. Миграция существующей установки:
  текущая `iperon.db` переносится в `accounts/<id>/` и становится первым аккаунтом.
- **Переключение аккаунта:** `getIt.pushNewScope()` / `popScope` с перерегистрацией тех же
  типов. Это наименее инвазивный вариант: около 200 вызовов `getIt.get<…>()` продолжат
  компилироваться и будут обращаться к **активному** аккаунту. Статические `.instance`
  заменяются на `AccountScope.current.chatsSync` и т.п. (или регистрируются в том же
  scope).
- **Фоновые аккаунты.** Всё, что выполняется вне активного аккаунта, получает
  `AccountScope` явно, а не через `getIt`:
  - действия из пушей («Ответить», «Прочитано», tap);
  - принятие звонка;
  - регистрация токенов.
- **Стрим.** На старте стрим держится только у активного аккаунта, остальные
  получают пуши. Telegram держит соединения всех аккаунтов. Это можно сделать позже,
  так как `API` уже инстанс на аккаунт. Бейджи неактивных аккаунтов на экране
  «Аккаунты» берутся из пушей и периодического `GET_DIFFERENCE` по unary.
- **Logout одного аккаунта:**
  1. снять токен;
  2. удалить push-ключ;
  3. удалить папку;
  4. переключиться на соседний аккаунт или уйти на `/auth`, если аккаунтов не осталось.

  `API` при `unauthenticated` разлогинивает **свой** аккаунт, а не текущий.

## 4. Пуши и звонки (клиент + сервер)

1. **Ключи пушей.**
   - Хранилища держат map `keyId → (key, accountId)`. Убрать `clearKeys()` из
     `putKey`/`put`, удалять ключи точечно.
   - Флаг пасскода остаётся глобальным: лок приложения один.
   - Скрытые профили и аватары хранить по `accountId`.
2. **Идентичность уведомлений.**
   - Теги и треды `a<keyId>:chat:<hex>`, в extras tap/reply добавить `accountId`.
   - Android: отдельный канал или группа на аккаунт, в подписи — имя аккаунта
     (как в Telegram: «Имя → Аккаунт»).
   - Шорткаты conversation-уведомлений с префиксом аккаунта.
3. **Бейдж приложения** — сумма по аккаунтам. Сервер шлёт бейдж только по своему
   пользователю, поэтому NSE/Android должны хранить последний бейдж каждого аккаунта и
   складывать.
4. **Call-пуши.**
   - Перенести всё содержимое в зашифрованный `p` с тем же keyId. Это нужно и для
     push-relay (см. on-premise.md, §5).
   - Клиент по keyId находит аккаунт, расшифровывает и показывает CallKit. PushKit
     требует показать CallKit сразу. Ключ уже лежит в Keychain и доступен из
     `AppDelegate`, так что расшифровка успевает.
   - Сервер: пересмотреть `isSameDevice` (`push.go:188-202`) в отмене и принятии
     звонка, когда на одном телефоне два аккаунта.
5. **Токены.** Один FCM/APNs/VoIP-токен регистрируется на **каждой** сессии. Маркер
   дедупликации — в БД аккаунта (он уже лежит в `cache` под `userID`).
6. **Сервер:** `deviceId` должен приходить в `AUTH_CONFIRMATION` для всех способов входа
   (исправление в `AuthLoginCompleter`).

## 5. UX

- **Настройки:** список аккаунтов вверху (аватар, имя, бейдж) и «Добавить аккаунт».
  Долгий тап по вкладке «Настройки» — быстрый свитчер, как в Telegram.
- **«Добавить аккаунт»** открывает обычный `/auth` поверх текущего аккаунта. Плюс точка
  входа «Войти через SSO / сервер компании» (on‑prem).
- **Входящий звонок или пуш неактивного аккаунта:** tap переключает аккаунт и
  открывает чат.
- **Пасскод и биометрия** общие на всё приложение. Скрытые профили — на аккаунт.

## 6. Этапы

1. **Сервер и протокол** (нужно и для relay) — написано 2026-10-24, на
   устройствах не проверено:
   - call-пуши в `p`: `PushPayload` `CALL_INCOMING` / `CALL_CANCEL` (поля
     `callID`, `video`; имя — `title` / `senderPhone` / `titleFromContact`).
     Сервер шифрует только сессиям с capability `callPushEncrypted`
     (`Subscribe.capabilities`), остальным — прежняя открытая map. Натив
     разворачивает `p` обратно в прежнюю map: iOS — `CallSignal.legacyData`
     (`PushBridge.swift`) в `AppDelegate.pushRegistry`, Android —
     `CallFcmService` (отдаёт её в Dart сам, как ресивер firebase_messaging);
   - `deviceId` во всех `AUTH_CONFIRMATION` (`AuthLoginCompleter`);
   - `isSameDevice` проверен: сравниваются только сессии одного пользователя,
     мультиаккаунт его не задевает — менять не нужно.
2. **Клиент, рефакторинг без изменения поведения** (2026-10-24: `API` держит свою
   сессию — `fd3c714`; `AccountScope` для синглтонов чатов — `6c4f5cb`; `device.db` с
   `settingsDevice` и индексом `accounts` — `sessions`/`users` остались в базе аккаунта:
   на `users` ссылаются внешние ключи, на `sessions` — выборки «владельца»
   (`hiddenProfiles`, `spoilerReveals`), поэтому в `accounts` нет ключей сессии;
   папка аккаунта `accounts/<id>/` — база, outbox, секретные вложения, кэш `media`;
   `accounts` — слоты, выход снимает пользователя, папка остаётся):
   - `accounts` вместо `sessions` и `users`;
   - миграция `iperon.db` в `accounts/<id>/`;
   - `AccountScope` с одним аккаунтом;
   - статические `.instance` переведены в scope;
   - `API` больше не читает глобальный `Auth`.
3. **Мультиаккаунт на одном сервере** — разбивка (2026-10-25, не начато). Сервер менять не
   нужно: токен пуша хранится на сессии (`ServiceSessions.SetPushToken`), без
   дедупликации между пользователями; бейдж уже в пуше. Каждая часть — отдельный
   коммит, проверка `flutter test` + раннер (`scenario all`) + ручная.
   - **3.1 Переключение scope.** `AccountScope` на аккаунт; `Repositories` делится на
     общую часть (`device.db`, в корневом scope get_it) и базу аккаунта; `Auth`, `API`,
     `CDNManager`, `PushManager` и база аккаунта — в `getIt.pushNewScope` на аккаунт.
     Сервисы аккаунта получают `dispose` (подписки на `api.on`, таймеры); подписчики
     уровня приложения (`InAppNoticeHost`, `ConnectionCubit`, `CallPush`,
     `app_*._callSub`, бейдж) переподписываются по `AccountScope.changes`. Во время
     звонка переключение запрещено. С одним аккаунтом поведение прежнее.
   - **3.2 Добавить / переключить / выйти.** «Настройки» → список аккаунтов (аватар,
     имя, непрочитанные) и «Добавить аккаунт» (до 3): новый слот и папка, `/auth`
     поверх текущего; отмена — слот удаляется. Выход одного: снять токен и ключ
     пуша, удалить папку, перейти на соседний (или `/auth`). Долгий тап по вкладке
     «Настройки» — быстрый выбор.
   - **3.3 Пуши нескольких аккаунтов.** Хранилища ключей — `keyId → (key, accountID)`
     без `clearKeys`; токены регистрируются на сессии каждого аккаунта; теги
     `a<keyId>:chat:<hex>`; tap / «Ответить» / «Прочитано» несут `accountID` —
     tap переключает аккаунт, ответ и прочтение выполняются в scope своего
     аккаунта без переключения; скрытые профили и аватары — на аккаунт; в
     заголовке — имя аккаунта.
   - **3.4 Бейдж-сумма:** натив хранит последний бейдж каждого аккаунта (из пуша),
     иконка — сумма; активный аккаунт — из `ChatsSync.unread`.
   - **3.5 Звонок на неактивный аккаунт:** keyId → аккаунт в CallKit / баннере
     («→ имя аккаунта»), «Принять» переключает аккаунт и принимает; занятость —
     по всем аккаунтам.
   - **3.6 Раннер:** второй тестовый номер на стенде (`testAccounts`), сценарий
     `accounts` — телефон добавляет его через UI (код постоянный), бот пишет и
     звонит на оба, проверка тегов, бейджа и переключения по тапу.

   Исходный перечень этапа:
   - добавление и переключение аккаунтов;
   - мульти-ключи пушей;
   - теги, маршрутизация tap/reply;
   - бейдж-сумма;
   - звонки на неактивный аккаунт.
4. **Мультисервер** (после on‑prem):
   - хост в `accounts`;
   - метаданные сервера вместо Remote Config;
   - pinning ключа сервера (TOFU) — сейчас `PUBLIC_KEY_EDDSA_FINGERPRINT` вообще не
     используется.

Оценка по объёму: этап 2 — самый большой (около 200 мест вызова и 10 синглтонов),
этапы 1 и 3 — средние.

## 7. Открытые вопросы

- Держать стримы всех аккаунтов (как в TG) или только активного? Предлагается начать
  с активного.
- Лимит аккаунтов и нужен ли Premium для 4-го.
- Должны ли настройки оформления (обои, быстрая реакция) стать «на аккаунт»?
