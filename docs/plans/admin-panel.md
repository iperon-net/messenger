# Админка (веб-панель оператора)

Статус: 2026-10-29. Этап 0 на стенде, вход через Logto проверен. Этап 1 («Пользователи») написан 2026-10-29: поиск, карточка, сеансы и их завершение; на стенде не проверен. Настройка — `docs/admin/README.md` в репо сервера. Вход — OIDC через Logto (`oauth.iperon.net`).

## 1. Задача

Сейчас всё операторское делается руками: Premium (`users.isPremium`) и блокировка
(`users.isBlocked`) — правкой в Mongo, флаги функций (`secretChats.enabled`,
`systemNotices.enabled`, `groups.enabled`, …), тестовые номера (`testAccounts`) и
store-модерация — в `iperon.yaml` с передеплоем, жалоб нет вовсе. Нужна веб-панель для
трёх задач:

1. **Поддержка и модерация** — найти пользователя, посмотреть его аккаунт и устройства,
   завершить сессии, заблокировать; разбирать жалобы; управлять публичными группами и
   каналами.
2. **Операционка** — флаги функций и лимиты без передеплоя, тестовые аккаунты,
   минимальная версия приложения, состояние фоновых задач.
3. **Рассылки и Premium** — служебные сообщения «Iperon» пользователю / сегменту / всем,
   выдача Premium, верификация каналов.

Аналитика — не здесь: метрики и логи остаются в Grafana (в админке только ссылки).

## 2. Принципы

- **Приватность по умолчанию.** Админ не читает личные чаты и группы. Содержимое
  сообщений видно только (а) приложенное к жалобе самим пожаловавшимся, (б) в публичных
  группах/каналах, которые и так видны всем. Секретные чаты недоступны в принципе (E2EE).
  Номер телефона в карточке маскируется (`+7 916 ***-**-50`), «Показать» пишется в аудит.
- **Каждое действие — в аудит** (`adminAudit`): кто, что, над кем, причина, IP, время.
  Для разрушительных действий (блокировка, удаление, рассылка всем) причина обязательна.
  Аудит неизменяем из админки.
- **Адрес — `https://staging.iperon.net/admin/`** (на проде позже — `/admin/` на прод-хосте:
  у каждого окружения своя админка над своими данными). Тот же nginx на alica, что
  терминирует TLS (h2, `*.iperon.net`) и проксирует gRPC: пути gRPC — `/v1.Iperon/…`, с
  `location /admin/` не пересекаются. Сама админка — отдельный HTTP-процесс на
  `127.0.0.1`, не на gRPC-порту; в `location /admin/` — allowlist IP (`allow …; deny all;`).
- **Ответ по закону Яровой (ОРИ)** — не здесь, остаётся `cmd/ori` (отдельный ключ,
  отдельный регламент).

## 3. Архитектура

### Где живёт

**Внутри сервиса `iperon`** (`~/GolandProjects/iperon`): `admin.Module` в `api.Startup()` —
ещё один HTTP-сервер рядом с gRPC / webhooks / metrics на своём `admin.addr` (host:port или
unix-сокет). `admin.enabled: false` по умолчанию — порт не открывается и остальные `admin.*`
не проверяются; включена с ошибкой в настройках — сервис не стартует (как с остальными
настройками). Плюсы: один бинарник и один деплой, сервисы (`ServicePublisher`,
`ServiceChats`, репозитории) доступны напрямую из fx-графа, без второго набора подключений.
Минус — админка делит процесс с API: тяжёлые выборки делать постранично и с таймаутами.
(Первоначально был отдельный бинарник `cmd/admin` — заменён 2026-10-29.)

Действия с «живым» эффектом идут тем же путём, что из приложения: `ServicePublisher`
(NATS `userID.<hex>` / `sessionID.<hex>`), `ServiceChats.PostSystemNotice`,
`RepositorySessions.TerminateBySessions` и т. д. — инстансы API получают события, как от
обычных клиентов.

### Фронтенд

Серверный рендер **Go + [templ](https://templ.guide) + htmx**, вёрстка и стили — из
бесплатного **[TailAdmin](https://github.com/TailAdmin/tailadmin-free-tailwind-dashboard-template)**
(HTML-версия, MIT, Tailwind v4 + Alpine.js). Без npm-сборки и отдельного SPA: панель —
таблицы, карточки, формы.

- **Что берём из TailAdmin:** `src/css/style.css` (тема Tailwind v4, одна точка правды,
  без `tailwind.config.js`) и разметку партиалов — каркас (сайдбар, шапка, тёмная тема),
  таблицы, формы, бейджи, модалки, выпадающие меню, алерты, пагинацию. Партиалы переносим в
  templ-компоненты (`Layout`, `Sidebar`, `Table`, `Badge`, `Modal`, …); их `<include>` и
  webpack не нужны.
- **Что не берём:** webpack/babel/eslint, `i18next` (переводы — на сервере, см. ниже),
  демо-страницы (eCommerce, календарь, карты), ApexCharts / FullCalendar / jsvectormap /
  Swiper / Dropzone / TanStack-таблицы (графики — в Grafana, таблицы — серверные с
  пагинацией через htmx). Шрифт Outfit из Google Fonts — положить локально в `static/` или
  заменить системным (внешних запросов из админки нет).
- **CSS:** Tailwind v4 **standalone CLI** (один бинарник, без Node; плагин
  `@tailwindcss/forms` в нём есть) собирает `style.css` по классам из `*.templ`. Шаг
  `task admin:gen` (templ + css), `admin.css` коммитится; через `go:embed`, ссылки с `?v=<хеш>`
  (кэш навсегда), отдаётся под `/admin/static/…`.
- **JS:** htmx 2.0.10 (локальный файл, `htmx-config` без eval / inline-стилей / чужих
  origin) — поиск по вводу, пагинация, частичная перезагрузка. **Alpine не понадобился:**
  UI-мелочи (сайдбар на мобильном, тема, закрытие выпадашки на `<details>`) — ~70 строк
  `static/js/admin.js` с делегированием событий; тема до отрисовки — `theme.js` в `<head>`.
- **templ:** `templ generate` в Taskfile, сгенерированные `*_templ.go` коммитим (как
  `*.pb.go`), чтобы `go build ./...` и CI работали без инструмента.
- Строгий CSP (`script-src 'self'`), CSRF — **`http.CrossOriginProtection`** (Go 1.25+,
  `Sec-Fetch-Site` / `Origin`) вместо токенов в формах; nginx обязан передавать `Host`. Cookie `HttpOnly; Secure; SameSite=Lax; Path=/admin/` (префикс `__Host-`
  нельзя — он требует `Path=/`, берём `__Secure-`).

### Локализация

Переводы на сервере, закладываются с этапа 0 (потом вычищать строки из сотни шаблонов
дороже); на старте — `ru`, `en` добавляется файлом. Нужна и для on-prem у иностранных заказчиков.

- **[`go-i18n`](https://github.com/nicksnyder/go-i18n) v2**: файлы `internal/admin/i18n/{ru,en}.yaml`
  через `go:embed`, CLDR-плюрализация (для русского one/few/many — «1 жалоба / 3 жалобы /
  5 жалоб»).
- **Язык запроса** — middleware кладёт `*i18n.Localizer` в `context`: cookie выбора (переключатель
  в шапке) → claim `locale` из Logto → `Accept-Language` → `ru`. templ-компоненты получают
  `ctx` неявно, поэтому в шаблоне просто `{ web.T(ctx, "users.search.placeholder") }`; htmx-партиалы
  рендерятся тем же путём и язык не теряют. `<html lang>` — из того же значения.
- **Проверка ключей** — go-i18n ключи строковые, компилятор их не ловит, поэтому тест: все ключи
  есть во всех локалях, и каждый `web.T(ctx, "…")` из `*.templ`/`*.go` существует (грепом по
  исходникам) — красный CI вместо сырого ключа на экране.
- **Даты и числа**: `golang.org/x/text/message` — числа с разделителями; даты — свой
  форматтер на ~20 строк (названия месяцев в родительном падеже для `ru` в YAML), время — в
  часовом поясе браузера (cookie из JS один раз) или Москвы по умолчанию.
- **Что переводится**: интерфейс, enum-подписи (причины жалоб, роли, действия аудита — по ключу
  `enum.<тип>.<значение>`), ошибки форм. **Не переводится**: данные пользователей, текст
  рассылок (у них свои версии ru/en), сырые payload в аудите.

### Вход — OIDC через Logto

Свой Logto: issuer `https://oauth.iperon.net/oidc` (discovery
`/.well-known/openid-configuration`). Админка — **Traditional web app** в Logto
(confidential client, `client_secret_basic`), redirect
`https://staging.iperon.net/admin/auth/callback`, post-logout redirect
`https://staging.iperon.net/admin/` (прод — добавить его адреса в то же приложение или
завести отдельное).

- Authorization Code + PKCE (`S256`) на `coreos/go-oidc/v3` + `golang.org/x/oauth2`;
  `state` в cookie браузера и в Redis (вместе с nonce и PKCE verifier, одноразово, 10 мин).
- **Подпись `id_token` — `ES384`** (Logto отдаёт только её). go-oidc берёт допустимые
  алгоритмы из discovery (`id_token_signing_alg_values_supported`), поэтому явно не задаём —
  так же заработает и RS256 у IdP заказчика on-prem; тест с ES384-ключом есть.
- Ролей нет в `id_token` — берутся из userinfo (`/oidc/me`).
- Scopes: `openid profile email roles` (+ `phone`, если нужна привязка к аккаунту Iperon, см.
  ниже). Из `id_token` берём `sub`, `email`, `name`, `roles`.
- После колбэка — своя веб-сессия в Redis (12 ч, cookie как выше; `SameSite=Lax`, т. к.
  `Strict` ломает возврат с IdP), токены Logto не храним дальше проверки.
- Выход: удаляем сессию + редирект на `end_session_endpoint` (`/oidc/session/end`).
  Logto поддерживает **back-channel logout** — эндпоинт `/auth/backchannel-logout`
  удаляет веб-сессии по `sid`, так что выход/блокировка в Logto сразу выкидывает из админки.
- Опасные действия (рассылка всем, блокировка, Premium): если с `auth_time` прошло > 15 мин —
  повторный вход с `prompt=login`.
- 2FA (TOTP / passkey) включается в Logto (MFA policy), админка её не реализует.
- Привязка к аккаунту Iperon (для «Отправить себе» в рассылках): по `phone_number` из Logto
  (`phone_number_verified`) ищем пользователя Iperon; нет номера — функция недоступна.

### Роли

Источник правды — **роли пользователя в Logto** (claim `roles`): `iperon-admin-support`,
`iperon-admin-moderator`, `iperon-admin-ops`, `iperon-admin-owner`. Пользователь Logto без одной из них в админку
не входит (403 после колбэка). Отдельной таблицы админов в Mongo нет; роли раздаются и
снимаются в консоли Logto, изменение вступает в силу при следующем входе (сессия 12 ч, при
снятии роли — выход через back-channel logout или «завершить сессии» в Logto).

| Роль | Может |
|---|---|
| `iperon-admin-support` | поиск и карточка пользователя (номер маскирован), список сессий, завершить сессию, служебное сообщение одному пользователю |
| `iperon-admin-moderator` | всё `support` + жалобы, блокировка аккаунта, публичные чаты (скрыть, заблокировать, удалить сообщение) |
| `iperon-admin-ops` | флаги и лимиты, тестовые аккаунты, store-модерация, минимальная версия, фоновые задачи |
| `iperon-admin-owner` | всё + Premium, верификация, рассылки сегменту/всем, просмотр аудита |

### Хранилище (Mongo)

- `adminAudit` — `adminSub` (Logto `sub`) + `adminEmail`, `action`, `target` (тип + id), `reason`, `payload` (что
  изменилось: было/стало), `ip`, `createdAt`. Индекс по `target` и `createdAt`.
- `reports` — жалобы (этап 3).
- `runtimeConfig` — флаги и лимиты (этап 5).
- `broadcasts` — рассылки и их прогресс (этап 6).

## 4. Этапы

### Этап 0. Каркас

- `admin.Module` в `api.Startup()`: HTTP-сервер (chi, как `startWebhooks`), конфиг
  `admin.enabled` / `admin.addr` / `admin.network` / `admin.publicUrl` в `iperon.yaml`.
- Приложение в Logto, роли `iperon-admin-*`, MFA-политика; конфиг `admin.oidc.issuer` /
  `clientId` / `clientSecret` в `iperon.yaml`.
- Вход по OIDC (колбэк, сессия в Redis, выход, back-channel logout), middleware проверки
  роли, `adminAudit`, страница «Аудит». Клиентское приложение не меняется.
- Перенос каркаса TailAdmin в templ (layout, сайдбар, таблица, форма, модалка), сборка CSS
  standalone-CLI Tailwind, `task admin:gen` (templ + css).
- Локализация: `go-i18n`, middleware языка, `web.T(ctx, …)`, переключатель в шапке, тест
  полноты ключей; стартовая локаль `ru` (см. «Локализация»).
- Безопасность: CSP / `X-Frame-Options` / `Referrer-Policy` / HSTS, CSRF
  (`http.CrossOriginProtection`).
- Базовый путь — путь из `admin.publicUrl` (`/admin`): роутер chi монтируется под ним, все
  ссылки/редиректы/статика в шаблонах — от него (nginx префикс **не** срезает, `proxy_pass
  http://127.0.0.1:50095;` без URI), чтобы прод и стенд не расходились.
- nginx: `location /admin/` на `staging.iperon.net` с allowlist + `/admin/auth/backchannel-logout`
  без allowlist (`docs/nginx/staging.iperon.net-admin.conf`), образ и CI — те же, что у
  сервиса.

### Этап 1. Пользователи

- Поиск: номер (через `Utils`-подобную нормализацию на сервере), `@username`, `userID` hex.
- Карточка: дата регистрации, страна, источник подтверждения номера
  (`phoneVerificationSource`: звонок / магазин / Яндекс), Premium, облачный пароль да/нет,
  email восстановления (маскирован), ключи доступа, `@username`, число чатов/групп,
  блокировка. Профиль (имя, аватар) — как его видят все.
- Сессии: устройство, ОС, версия приложения, IP + гео, последний вход, возможности
  (`capabilities`), есть ли push-токен. Действия: «Завершить» одну / все — через
  `TerminateBySessions` + публикация, клиент уходит на `/auth` (уже работает).
- «Написать от Iperon» одному пользователю — перенесено в этап 6 (рассылки: текст на двух языках, пуш).
- Ссылки: логи пользователя в Grafana/Loki по `userID`, крэши по сессиям (`admin.grafana.*`).
- Сделано иначе, чем в плане: аватара нет (файлы аватаров зашифрованы, в карточке — имя);
  открытие карточки пишется в журнал (`users.view`, раз в час на админа); «Завершить» —
  форма с обязательной причиной прямо в строке сеанса.

### Этап 2. Блокировка аккаунта

`users.isBlocked` уже есть, но **нигде не проверяется**. Нужно:

- Сервер: `Confirmation` / QR / passkey / Яндекс отказывают заблокированному
  (`permissionDenied`, ключ `auth.accountBlocked`, не `unauthenticated` — иначе `API.call`
  трактует как обычный разлогин); при блокировке все сессии удаляются, стримы закрываются
  через `sessionID.<hex>`; `PROFILE` для других — «аккаунт удалён/заблокирован» (без
  аватара и имени), поиск и `CONTACTS_DISCOVERY_MATCH` его не находят.
- Срок: `blockedUntil` (пусто = навсегда) + причина (для пользователя — категория, без
  текста модератора).
- Клиент: экран «Аккаунт заблокирован» на `/auth` с причиной и ссылкой на поддержку.
- Сообщения заблокированного в публичных чатах — опция «удалить все сообщения в
  публичных чатах» при блокировке (личные не трогаем).

### Этап 3. Жалобы

- Proto `reports_v1.proto`, тип `REPORT` (зашифрованный unary): цель (пользователь / чат /
  сообщения), причина (`SPAM`, `VIOLENCE`, `PORNOGRAPHY`, `CHILD_ABUSE`, `ILLEGAL_DRUGS`,
  `PERSONAL_DATA`, `FAKE`, `COPYRIGHT`, `OTHER`), комментарий, `messageIDs`.
- Сервер копирует указанные сообщения в жалобу (зашифрованными тем же ключом, что
  `messages`) — потом их можно удалить, а доказательство останется. Для личного чата
  прикладываются только выбранные пожаловавшимся сообщения. Секретный чат — жалоба только на
  пользователя, без содержимого. Лимит частоты (как `crashReportLimiter`).
- Клиент: «Пожаловаться» в профиле, в «Ещё» чата/группы/канала, в меню сообщения (выбор
  нескольких → причина → комментарий), обе платформы; «Заблокировать и пожаловаться» в
  баре «неизвестный номер».
- Админка: очередь (новые / в работе / решённые), группировка по цели (N жалоб на одного
  пользователя / канал), карточка жалобы с сообщениями и медиа (расшифровка через
  `CDNManager`-аналог на сервере), действия: отклонить, удалить сообщения, заблокировать
  пользователя, скрыть/заблокировать чат. Решение — в аудит, пожаловавшемуся — ничего (как в
  Telegram).

### Этап 4. Публичные группы и каналы

- Поиск по названию / `@username` (`publicChats`, `Chats.SearchChats`), карточка: владелец,
  админы, участники, дата, жалобы, последние посты.
- Действия: скрыть из поиска (`publicChats.hidden`), освободить `@username`, заблокировать
  чат (вступление и чтение закрыты, участникам — заглушка «Канал заблокирован за нарушение
  правил»), удалить сообщение (обычный `Delete` от имени системы, с апдейтами участникам).
- Верификация: `chats.verified` → `ChatInfo.verified` → галочка в клиенте (заголовок, список,
  поиск). Та же галочка для пользователей позже (`Profile.Response.verified`).

### Этап 5. Операционка

- **Runtime-конфиг.** Коллекция `runtimeConfig` поверх `iperon.yaml`: yaml — дефолт и
  аварийный откат, Mongo — переопределение. Переносятся только безопасные для горячей смены
  значения: аварийные выключатели (`secretChats.enabled/premiumOnly/frozen`,
  `systemNotices.enabled`, `groups.enabled`, `channels.enabled`), лимиты (`maxMembers`,
  `maxPerUser`, лимиты частоты), `appMinimalVersion`. Ключи, DSN, крипто — никогда.
  Изменение → NATS `admin.config` → все инстансы перечитывают. В `settings` — типизированный
  геттер с атомарной подменой, а не прямое чтение поля `Config`.
- **Клиентские флаги через сервер.** Сейчас клиент берёт их из Firebase Remote Config,
  которого нет на десктопе и не будет on-prem. Сервер отдаёт клиентский конфиг в ответе на
  `Subscribe` + пуш при изменении; клиентский `Settings` кладёт его между `.env` и Remote
  Config. Firebase RC остаётся до тех пор, пока все клиенты не обновятся.
- **Тестовые аккаунты и store-модерация** (`testAccounts`, номер/код для ревью App Store /
  Google Play) — в `runtimeConfig`, с аудитом показа кода.
- **Состояние задач**: последний запуск/результат `ChatMediaGC`, `ChatHistoryArchive`,
  `ChannelViewsFlush`, CDN-чистки, баланс call-password; кнопка «Запустить сейчас» для
  идемпотентных.
- Здоровье: те же проверки, что `startHealthcheck` (Redis/NATS/Mongo), число открытых
  стримов, ссылки на дашборды Grafana.

### Этап 6. Рассылки и Premium

- **Рассылка = обычное текстовое сообщение от «Iperon»** в служебный чат (не новый `Kind`
  у `MessageSystemNotice`: старые клиенты показали бы для неизвестного вида только заголовок).
  Текст с разметкой (entities), версии ru/en, язык — по локали последней сессии (если сервер
  её не знает — по стране номера; **уточнить, передаёт ли клиент локаль**).
- Сегменты: один пользователь, список `userID`, страна, ОС, версия приложения ниже X
  («обновитесь»), Premium, все.
- Перед отправкой: предпросмотр, «Отправить себе», оценка числа получателей; отправка —
  фоновой задачей с троттлингом (журнал `pts` + пуш на каждого — нельзя разом на всех),
  прогресс и остановка в админке, идемпотентность по `randomID` (`systemNoticeRandomID`)
  при рестарте.
- Без пуша по умолчанию (галочка «со звуком» — только для важного).
- **Premium**: вкл/выкл с причиной и сроком (`premiumUntil`), публикация `MY_PROFILE` на
  сессии пользователя, чтобы клиент сразу увидел. Платная подписка — отдельная задача.

## 5. Порядок и оценка

0 → 1 → 2 дают рабочую поддержку (найти, разлогинить, заблокировать). 5 (runtime-конфиг)
независим и полезен рано — можно параллельно с 1. 3 требует клиентского релиза (кнопки
«Пожаловаться»), его стоит выпустить до публичного запуска. 4 и 6 — после.

## 6. Открытые вопросы

- Хост: та же ВМ, что API стенда, или отдельная внутренняя; WireGuard или allowlist IP.
- Хранить ли жалобы с содержимым бессрочно или с TTL (юрист: персональные данные).
- On-prem: админка заказчика — та же самая, но issuer — IdP заказчика (Keycloak / AD FS /
  Entra); роли тогда из его claim (`roles` / `groups`) — имя claim вынести в конфиг (см.
  `docs/plans/on-premise.md`).
