## 1. Задача

После этапа 5б админки (`docs/plans/admin-panel.md`, клиент `v0.0.573`) флаги и лимиты
приходят с сервера (`ClientConfig`, `lib/client_config.dart`), а Remote Config остался
запасным вариантом. Убрать его целиком мешают ключи, которые сервер отдать не может —
они нужны **до** подключения к нему:

| Ключ Remote Config | Что это | Куда |
|---|---|---|
| `API_HOST` / `API_PORT` / `API_SECURE` | адрес gRPC-сервера | в bootstrap-файл |
| `PUBLIC_KEY_EDDSA_FINGERPRINT` | отпечаток ключа сервера (сейчас в клиенте **не используется**, см. `docs/plans/on-premise.md` §3) | в bootstrap-файл — задел под пиннинг |
| `PHONE_NUMBER_MODERATION_APPLICATION_STORE(_ENABLE)` | тестовые номера | удалить: сервер сам отвечает `fixedCode` на `AUTH_CALL_PASSWORD` |
| флаги, тайминги звонков, URL эмодзи, client_id Яндекса | — | уже с сервера (`ClientConfig`), из Remote Config — удалить |

Решение: подписанный статический файл по известному адресу — переезд сервера и смена
ключа без новой сборки, без Firebase.

## 2. Файл

`https://download.iperon.net/config.json` (nginx на alica) ← GitHub Release `bootstrap`
этого репо (pre-release, никогда не latest).

**Приложение одно** — сборки для стейджа и прода не делятся. Окружение — свойство
аккаунта (§4): файл описывает все окружения сразу.

```json
{
  "serial": 7,
  "issuedAt": 1793260800,
  "defaultEnvironment": "staging",
  "environments": {
    "production": {"api": [{"host": "iperon.net", "port": 443, "secure": true}], "serverKeyFingerprint": "…"},
    "staging": {"api": [{"host": "staging.iperon.net", "port": 443, "secure": true}], "serverKeyFingerprint": "7abfc2a7…"}
  },
  "signature": "<base64 Ed25519 от канонического JSON без поля signature>"
}
```

- `serial` — монотонный номер: клиент не принимает файл с `serial` меньше закэшированного
  (иначе можно подсунуть старый подписанный конфиг со старым адресом).
- `defaultEnvironment` — окружение **новых** аккаунтов. Пока прода нет — `staging`; при
  запуске прода переключается workflow (без сборки), и обычные пользователи попадают на
  прод, а уже добавленные аккаунты остаются на своём окружении.
- `environments.<имя>.api` — список: первый — основной, остальные — запасные (резервный
  сервер, другой домен на случай блокировки). Имя — `[a-z0-9-]`.
- Подпись — от канонической сериализации (ключи по алфавиту на всех уровнях, без
  пробелов) всех полей, кроме `signature`; подписан весь файл, а не адрес, откуда он
  скачан, — источник (nginx, GitHub, зеркало) не важен. Публичный ключ Ed25519 зашит в
  сборку (`bootstrapPublicKeys`), приватный — секрет GitHub `BOOTSTRAP_SIGNING_KEY`.
- Workflow меняет одно окружение за раз: остальные переносятся из текущего файла, который
  перед этим проверяется ключом сборки (подменённый релиз не переподпишется).

## 3. Безопасность

- **Подпись обязательна.** Без неё подмена файла (взлом хостинга, DNS, чужой
  сертификат) уводит всех клиентов на чужой сервер; HTTPS от этого не спасает.
  Неподписанный / с неверной подписью файл — игнорируется (лог в Talker).
- **Откат** — `serial` (см. выше).
- **Источник не доверенный**: копии на GitHub Releases / S3 проверяются той же подписью.
- **Ключ подписи** — секрет GitHub; файл подписывает workflow (вручную, `workflow_dispatch`
  с параметрами), а не человек на ноутбуке. Ротация ключа подписи — только новой сборкой
  (в сборке можно держать два публичных ключа: текущий и следующий).

## 4. Клиент

Новый `BootstrapConfig` (`lib/bootstrap_config.dart`), читается через `Settings`
(`apiHost` / `apiPort` / `apiSecure` / `serverKeyFingerprint`), как сейчас Remote Config.

Порядок значений: `.env` (debug) → кэш файла в `device.db` → зашитое в сборку.

1. **Окружение аккаунта.** В `accounts` (`device.db`, миграция `DeviceDatabase`) — колонка
   `environment`. Существующие аккаунты получают `staging` (они на стейдж-сервере); новый
   аккаунт — `defaultEnvironment` файла на момент добавления. `Settings.apiHost` и др. —
   адреса окружения **активного** аккаунта; переключение аккаунта (`switchAccount`:
   `closeAccount` → `openAccount`) пересоздаёт `API` — он сразу идёт на сервер нового
   аккаунта. Окружения нет в файле (удалили) — значения из сборки, в лог.
2. **«Разработчик» → «Добавить аккаунт на стейдже / на проде»**: обычный «Добавить
   аккаунт», но слот получает выбранное окружение. В списке аккаунтов (настройки, быстрый
   выбор на «Настройках») аккаунт не из `defaultEnvironment` помечен (`staging`).
3. **Старт.** `Settings` берёт адрес из кэша (`device.db`, таблица `bootstrapConfig`: JSON
   файла + `serial`, одна строка). Кэша нет (первый запуск) — значения из сборки
   (`_defaults`). Подключение не ждёт сети до файла.
4. **В фоне** (`startAccountServices` и раз в сутки): скачать файл (таймаут 5 с), по
   очереди с адресов-зеркал (download.iperon.net, затем GitHub Releases) до первого
   валидного; проверить подпись (`BootstrapFile.verify`) и `serial`; записать в кэш. Новый
   адрес применяется к следующему подключению стрима (`API` пересоздаёт `ClientChannel`
   при смене адреса).
5. **Сервер не отвечает** (несколько неудачных подключений подряд): перекачать файл мимо
   суточного интервала и пробовать следующий адрес из `api` окружения.
6. **On-premise** (`docs/plans/on-premise.md` §3): аккаунт на сервере заказчика хранит
   свой адрес вместо имени окружения и файл не использует.

Офлайн: файл не скачался — работаем с кэшем, ничего не показываем пользователю.

## 6. Этапы

1. **Скрипт и файл.** `scripts/bootstrap_sign.dart` (keygen / sign / verify); workflow
   `bootstrap.yaml` (`workflow_dispatch`: окружение, адреса, отпечаток, окружение по
   умолчанию → подписанный `config.json` → GitHub Release `bootstrap`); location
   `/config.json` в nginx (кэш 5 мин).
2. **Клиент.** `BootstrapConfig` + кэш в `device.db` + окружение аккаунта (`accounts.environment`)
   + «Добавить аккаунт на стейдже» в «Разработчике» + переключение адреса в `API`; тесты:
   `serial` (откат), выбор зеркала, окружение аккаунта.
3. **Удаление Remote Config** (§5). Можно в той же сборке, что и этап 2.
4. **Позже:** пиннинг ключа сервера по `serverKeyFingerprint` (проверка ML-DSA/EdDSA-ключа
   из ответа сервера) — отдельной задачей вместе с on-premise.
