м# Чаты, группы, каналы и сообщества (по модели Telegram)

## Контекст

Переписки в приложении пока нет: вкладка «Чаты» — заглушка (`lib/screens/chats/`, только
баннер разрешения на уведомления). Готова инфраструктура, на которую ляжут чаты:

- транспорт `Unary`/`Stream` в зашифрованном конверте сессии, живой push по NATS
  (`userID.<hex>` / `sessionID.<hex>`, `ServicePublisher`);
- пуши: `PushPayload.Kind.MESSAGE / READ_HISTORY / MESSAGE_DELETED`, `chatID`, `messageID` —
  этап 7 плана `push-notifications.md` ждёт серверную часть чатов;
- настройки уведомлений уже разделены на личные чаты / группы / каналы;
- загрузка медиа (шифрование на клиенте, докачка, CDN, `cdnID`) и `toolbar_attachments`;
- граф контактов + приватность, presence, username, LiveKit (задел под голосовые чаты групп);
- паттерн «последнее известное значение в SQLite, отдаём offline».

## Решения

1. **Модель как у Telegram (cloud chats).** Шифрование клиент↔сервер (сессионный конверт),
   история хранится на сервере, доступна со всех устройств. Секретные E2EE-чаты — не сейчас.
2. **Шифрование в БД — как имя/фамилия в профиле.** Содержимое пишется в Mongo в поля
   `*Encrypted` через `crypto.Encryptor.Encrypt` (общий `encryptor.secretKey` + HKDF-соль
   репозитория, ср. `profileHdf` в `internal/repositories/profile.go`). Шифруются: текст и
   entities сообщения, медиа-ссылки, reply/forward-данные, черновики, название/описание
   закрытых групп. Открыты (нужны индексы): `chatID`, `messageID`, `fromUserID`, дата, тип,
   флаги. Медиа уже шифруются в `RepositoryCDN`. Текст сообщений не пишем в Redis и логи.
   Следствие: серверного полнотекстового поиска по личным чатам/группам нет — поиск локальный
   (SQLite FTS5); серверный — только по публичным каналам.
3. **Один тип групп** (как супергруппы Telegram), лимит — **200 000 участников**.
4. **Каналы** — до **нескольких миллионов** подписчиков → для каналов fan-out на чтение
   (общий журнал канала), не копия каждому подписчику.
5. **Сообщество** — группировка групп и каналов со своими настройками и настройками
   приватности (см. раздел ниже).
6. **Порядок:** сначала **UX-демо** (этап 0) на фейковых данных, чтобы закончить UX; только
   потом сервер и клиент.

## Форматирование сообщений

Как в Telegram: **текст хранится плоским + массив entities**, а не markdown-строкой.

```proto
message MessageEntity {
  enum Type {
    BOLD = 0; ITALIC = 1; UNDERLINE = 2; STRIKE = 3; SPOILER = 4;
    CODE = 5;          // `inline`
    PRE = 6;           // ```блок```, language — подсветка
    TEXT_URL = 7;      // [текст](url)
    URL = 8; MENTION = 9; MENTION_NAME = 10; HASHTAG = 11; EMAIL = 12; PHONE = 13;
    BLOCKQUOTE = 14; EXPANDABLE_BLOCKQUOTE = 15;
    CUSTOM_EMOJI = 16; // задел
  }
  Type type = 1;
  int32 offset = 2;    // в UTF-16 code units (как String в Dart)
  int32 length = 3;
  string url = 4;      // TEXT_URL
  bytes userID = 5;    // MENTION_NAME (упоминание без username)
  string language = 6; // PRE
}
```

Почему entities, а не markdown:
- плоский текст сразу годится для превью в списке чатов и в пуше, для FTS5-поиска;
- нет экранирования и «поломанной» разметки (`*` в обычном тексте), нет инъекций;
- редактирование сообщения не требует перепарсинга, entities пересекаются корректно;
- `URL`/`MENTION`/`HASHTAG`/`EMAIL`/`PHONE` можно детектить и на клиенте при рендере.

Ввод (клиент):
- **Меню выделения** (как в Telegram «Форматирование»): `contextMenuBuilder` поля ввода
  добавляет «Жирный / Курсив / Подчёркнутый / Зачёркнутый / Спойлер / Моноширинный /
  Ссылка / Цитата / Обычный».
- **Markdown-ярлыки при отправке**: `**жирный**`, `__курсив__`, `~~зачёркнутый~~`,
  `||спойлер||`, `` `код` ``, ```` ```блок``` ````, `[текст](url)`, `> цитата` —
  парсятся в entities, маркеры удаляются.
- Поле ввода — свой `TextEditingController`, который держит entities рядом с текстом,
  сдвигает offset'ы при правке и рисует стили в `buildTextSpan` (без тяжёлых rich-editor
  пакетов).
- Рендер: `entities → TextSpan`-дерево (спойлер — анимированная «пыль»/размытие, `PRE` —
  моноширинный блок с кнопкой «Копировать», ссылки/упоминания — `TapGestureRecognizer`).
- Лимиты как в Telegram: текст 4096 символов, подпись к медиа 1024 (уточнить).
- Меню «Форматирование» расширено (2026-10-09, проверено на устройстве 2026-10-09): подчёркнутый
  (`++текст++`), блок кода (```` ```\n…``` ````), упомянуть (`[текст](mention:userID)` →
  `mentionName`, выбор участника; только где есть участники), сворачиваемая цитата (строки
  `>> `, `MessageEntity.expandable`); у уже стоящих форматов галочка, повторный выбор снимает
  только его (в т. ч. вложенный: `**__x__**`); список прокручивается, если не влезает;
  горячие клавиши ⌘/Ctrl + B / I / U / K. В ленте блок кода — плашка с кнопкой «Копировать»,
  цитата — с полосой слева, сворачиваемая длинная — 3 строки, раскрывается по тапу.
  Тесты — `test/message_formatting_test.dart`.

## Сообщества

**Назначение (решено 2026-10-08): сообщество — бизнес-страница организации** (отель,
ресторан, авиакомпания, магазин, сервис), которую она создаёт для продвижения. Это не
«большая группа», а витрина организации: своей ленты сообщений у сообщества нет — общение
идёт в его канале объявлений и дочерних чатах, а главный экран — профиль организации.

**Бизнес-разделы (позже, после базовых экранов сообщества)** — подключаемые вкладки/блоки на
главном экране, набор зависит от вида бизнеса:
- **Вакансии** — список вакансий, отклик (резюме из профиля / сообщение в личку организации).
- **Товары** — каталог (фото, описание, цена, варианты), корзина, заказ.
- **Услуги / заказ** — каталог услуг с записью или заказом. Примеры по отраслям:
  - отель — бронирование номера (даты заезда/выезда, гости, тип номера, доступность);
  - ресторан — бронирование столика (дата, время, число гостей) и заказ из меню
    (доставка / самовывоз / к столику);
  - авиакомпания / перевозчик — поиск и покупка билетов;
  - запись к специалисту (салон, клиника) — слоты в расписании.
- Заказы и брони попадают организации (админам сообщества) и пользователю в «Мои заказы»;
  переписка по заказу — в личке с организацией.

Открыто по бизнес-части: оплата (эквайринг; см. свёрнутую интеграцию Robokassa), верификация
организации (галочка, юрлицо/ИНН), интеграции с внешними системами (PMS отелей, iiko/r_keeper
ресторанов, GDS авиабилетов) или только свой простой каталог, отзывы/рейтинг, модерация
каталогов, комиссия/тарифы для бизнеса.

**Вместо тем (форумов) в группах (решено 2026-10-08).** Темы внутри одной группы, как в
Telegram, не делаем. Их роль играет сообщество: контейнер, где есть бизнес-страница
организации и **группы по темам** — каждая тема является обычной полноценной группой со своими
участниками, правами, медленным режимом, уведомлениями и т. д. Плюсы: не нужен второй уровень
внутри группы (`topicID` в сообщениях, списки тем, непрочитанные по темам), переиспользуем всё,
что уже есть у групп; минусы, которые закрываем на уровне сообщества: общие участники, общая
модерация и вход «одним действием» (см. ниже).

Структурно сообщество = контейнер над группами и каналами:
- состав: канал объявлений (создаётся автоматически) + группы и каналы, **созданные внутри
  сообщества** (решено 2026-10-08). Прикреплять существующие группы/каналы извне и выносить
  чаты наружу нельзя: чат сообщества с рождения принадлежит ему (`communityID` задаётся при
  создании и не меняется) — нет конфликтов владельцев, участников и модерации, наследование
  настроек и сквозной бан работают без исключений;
- в списке чатов сообщество — **одна строка** (решено 2026-10-08); дочерние группы/каналы
  отдельными строками в общем списке не показываются. Тап по строке открывает главный экран
  сообщества: бизнес-страница, канал объявлений и список групп-тем;
- свои настройки: название, описание, аватар, username/ссылка-приглашение, владельцы и
  админы сообщества (права: добавлять/удалять чаты, модерировать участников во всех
  чатах, управлять приглашениями);
- свои настройки приватности (черновой список, обсудить):
  - видимость: публичное (находится поиском) / приватное (только по ссылке);
  - вступление: открытое / по заявке / только по приглашению;
  - ~~кто может создавать чаты внутри~~ — решено 2026-10-09: только админы сообщества
    (с правом «добавлять/удалять чаты»), участники не создают;
  - видимость списка участников сообщества: все / только админы;
  - могут ли участники писать друг другу в личку, не будучи контактами;
  - наследование по умолчанию для новых чатов внутри (вступление, история для новых
    участников, запрет пересылки/копирования);
- сквозная модерация: бан в сообществе = бан во всех его чатах;
- вступление (решено 2026-10-08): вступление в сообщество не добавляет во все чаты
  автоматически (кроме канала объявлений). Группы сообщества видны всем его участникам
  списком на главном экране, вход в тему — одним тапом без заявки (если админ не закрыл
  конкретную группу), выход из сообщества = выход из всех его групп.
- удаление (решено 2026-10-09): группы и каналы сообщества удаляются вместе с ним (вне
  сообщества они не существуют);
- строка сообщества в списке чатов (решено 2026-10-09): последнее сообщение из любой его
  группы/канала с подписью «Группа › Отправитель», суммарный счётчик непрочитанных без
  заглушённых групп.

### Настройки групп и каналов внутри сообщества (решено 2026-10-09)

Три уровня:

1. **Только у сообщества — своих у группы нет:**
   - кто может войти: в группу входят только участники сообщества; своих `joinMode`,
     публичного `username` и ссылок-приглашений у группы нет;
   - баны: бан в сообществе = бан во всех его чатах, своего списка «Заблокированные» у группы нет;
   - владелец: владелец сообщества = владелец всех его групп/каналов, передать владение
     отдельной группой нельзя;
   - админы сообщества — автоматически админы во всех его чатах с теми же правами;
   - приватность сообщества (видимость списка участников, личка не-контактам).
2. **По умолчанию от сообщества, группа может переопределить:**
   - права новых участников (`defaultRole`: только чтение / чтение и сообщения);
   - медленный режим, реакции, «Новичкам — без ссылок и медиа»;
   - **закрытая тема**: вход по одобрению админа вместо одного тапа (например, «Для
     постоянных гостей», «Сотрудники») — единственное ограничение входа на уровне группы.
3. **Полностью свои у группы:**
   - название, описание, аватар; закреплённые, опросы — всё содержимое;
   - **модераторы темы**: свои админы группы, не являющиеся админами сообщества, с правами
     не шире, чем у админов сообщества (например, менеджер зала ведёт тему «Отзывы»);
   - «Заглушить на…» — личная настройка пользователя, как и вне сообщества.

**Каналы внутри сообщества** — тот же принцип: вход, баны, владелец и админы — от сообщества;
«Кто может комментировать», «Подписка не менее», срок комментирования и реакции — свои у
каждого канала (по умолчанию от сообщества).

### Участники больших сообществ (обсуждаем)

Сообщество / группа на 100 000+ человек: весь список не грузим и не рисуем.
- **Клиент**: ленивый список (`SliverList.builder`) с подгрузкой страницами по 50–100 при
  прокрутке; сверху — владелец, админы и модераторы (всегда целиком, их мало), затем «Недавно
  активные», затем остальные. Число — «12 345 участников», без полного списка.
- **Сервер**: курсорная пагинация по индексу `(chatID, role, joinedAt)` (не `skip/offset`),
  фильтры «админы / заблокированные / недавно вступившие / ограниченные».
- **Поиск** вместо листания: по `@username` (открытый) и по именам из своих контактов
  (локально). Имена в Mongo зашифрованы — серверный поиск по имени возможен только через
  «слепой индекс» (HMAC от нормализованных префиксов имени) или не делается вовсе.
- **Скрывать список** («Скрыть участников» — уже есть): в больших сообществах по умолчанию
  список видят только админы, остальным — число и поиск.
- Для админа — те же страницы + поиск; массовые действия (исключить/ограничить) — по поиску и
  фильтрам, не по прокрутке.

## Приватность групп (предложение пользователя)

Группа настраивает, **как человек может присоединиться**, и **какие права он получает**
после вступления. Роли (по возрастанию):

| Роль | Читать | Писать | Управлять группой |
|---|---|---|---|
| **Чтение** | ✓ | | |
| **Запись** | ✓ | ✓ | |
| **Админ** | ✓ | ✓ | ✓ |

Решено:
- **Способы вступления — все четыре** (настройка группы, выбирается один): открытая
  (по username / поиском) / по ссылке-приглашению / по заявке (одобряет админ) / только
  админ добавляет.
- **Роль по умолчанию для вступивших — `Чтение`** (настраивается: `Чтение` / `Запись`;
  `Админ` по умолчанию не выдаётся).
- **Владелец** (создатель) — роль сверх админа: не снимается, удаляет группу, передаёт
  владение, назначает/снимает админов.
- Админ меняет роль конкретного участника, удаляет и банит.

- **Права админа — раздельные, как в Telegram** (галочки при назначении админа):
  - изменять информацию о группе (название, описание, аватар, настройки);
  - удалять чужие сообщения;
  - банить и ограничивать участников (в т.ч. менять роль Чтение/Запись);
  - приглашать участников и управлять ссылками-приглашениями / заявками;
  - закреплять сообщения;
  - управлять голосовыми/видеочатами (LiveKit);
  - оставаться анонимным (сообщения от имени группы);
  - назначать новых админов (только с правами не шире своих);
  - позже: управлять темами (когда появятся форумы).

  Плюс необязательное «звание» админа (подпись в пузыре). Владелец имеет все права всегда.
  Для каналов набор свой: публиковать, редактировать чужие посты, удалять чужие посты,
  приглашать подписчиков, назначать админов.

Отложено:
- Своя роль на конкретной ссылке-приглашении (пока все вступившие получают роль по
  умолчанию).

## Реакции

Один человек может поставить **несколько разных реакций** на сообщение — до
`maxReactionsPerUser` (3, как с Premium в Telegram); тап по своей снимает её, сверх лимита
вытесняется самая ранняя наша. Под сообщением — чипы «эмодзи + число» (наши залиты), время
прижато к правому краю строки реакций; двойной тап по пузырю — быстрая реакция; удержание —
на iOS `CupertinoContextMenu` (пузырь-превью, сверху меню полоса реакций, ниже действия), на
Android — нижний лист с полосой реакций.

Какие реакции доступны:
- **Личные чаты** — фиксированный набор, без настройки (`privateChatReactions` в
  `lib/chats/reactions.dart`: 👍 ❤️ 🔥 😂 😮 😢 🙏 👎).
- **Группы и каналы** — настраивает админ (`Chat.reactionsMode` + `Chat.reactions`):
  все (`allChatReactions`) / только выбранные / никаких.

Сделано в демо (2026-10-05): модели `MessageReaction`, `Message.reactions`,
`ChatReactionsMode`; `ChatsDataSource.setReactions` (весь наш набор целиком, как
`sendReaction` в Telegram); чипы в пузыре, `ReactionPicker` в
long-press-меню (Cupertino action sheet / Material bottom sheet), двойной тап; в демо
«Техно-обзор» — только 🔥 👍 🤯 ❤️, «Родители 5 «Б»» — реакции выключены, собеседник иногда
отвечает реакцией на наше сообщение.

**Настройки** (сделано 2026-10-08; лимит реакций на человека для чата — нет, общий `maxReactionsPerUser = 3`):
- **Инфо группы/канала → «Реакции»** (права: админ с правом «Изменение профиля группы»):
  - режим: «Все реакции» / «Некоторые» / «Нет реакций»;
  - для «Некоторые» — сетка эмодзи с галочками (из `allChatReactions`), порядок = порядок в
    полосе;
  - каналы: «Максимум разных реакций под постом» (как в Telegram, 1–11);
  - (возможно) лимит реакций на человека для чата — пока общий `maxReactionsPerUser = 3`;
  - изменение режима не трогает уже поставленные реакции (старые остаются видны, новые
    поставить нельзя).
- **Настройки → Чаты (или «Оформление») → «Быстрая реакция»**: какой эмодзи ставит двойной
  тап (сейчас константа `defaultQuickReaction = ❤️`); хранить в `settingsDevice` (локально)
  или в профиле (синхронно между устройствами — склоняюсь к профилю).
- **Уведомления → «Реакции»**: уведомлять о реакциях на мои сообщения — в личных чатах / в
  группах, «от всех» / «только от контактов» (как в Telegram).

**Нужно на сервере / в синхронизации (Этап 1+):**
- хранение: отдельная коллекция `messageReactions` (`chatID`, `messageID`, `userID`,
  `emoji`, `date`) + агрегат «эмодзи → число» в сообщении (для списка без выборки); сам
  эмодзи — не секрет, но связь «кто поставил» — шифровать как прочие поля (`Encryptor`)?
  решить;
- проверка: эмодзи из разрешённых для чата, не больше `maxReactionsPerUser` на пользователя
  (лимит — серверная константа/конфиг, клиент берёт его оттуда), права (бан,
  «только чтение» в канале — реакции можно, писать нельзя);
- апдейт `updateMessageReactions` через `pts`/`getDifference` и push в стрим; для каналов —
  только агрегат (fan-out на чтение, без списка авторов);
- «кто поставил»: в личных и группах — список по эмодзи (long-press на чипе), в каналах —
  анонимно;
- непрочитанные реакции на мои сообщения: бейдж ❤️ в списке чатов и прыжок к ним (как
  `unreadMentions`), строка списка «Анна: ❤️ к «…»»;
- офлайн: поставить реакцию без сети — ставим в очередь отправки (как сообщение), а не
  оптимистично-с-откатом.

## Комментарии к постам каналов

Решено (2026-10-08): комментарии — **отдельная сущность, не привязанная группа** (в Telegram
обсуждение — обычная группа, куда пересылается каждый пост; у нас так не делаем).

- **Хранение.** Своя коллекция комментариев: ключ `channelID + postID + commentID`
  (порядковый номер внутри поста), автор, дата, ответ на комментарий, реакции, медиа, опросы,
  упоминания. Текст и entities шифруются так же, как сообщения (`*Encrypted` через
  `Encryptor`). В посте — счётчик, последние 3 комментатора и `commentsCloseDate`.
- **Членства нет.** У ветки нет участников, ролей и настроек группы — права берутся из канала:
  - комментарии включены (`commentsEnabled`);
  - не закрыты: `commentsCloseDate` поста — срок канала на момент публикации
    (`commentsTimeLimit`) или админ закрыл досрочно; закрытая ветка — только чтение для всех;
  - «Кто может комментировать» (`commentsWho`): **Все** (по умолчанию) — любой, кто видит пост
    (у публичного канала — и не подписчик); **Только подписчики** — плюс «Подписка не менее»
    (`commentsMinSubscription`: 1 / 3 / 5 / 8 часов, 1 / 3 дня, неделя, месяц, год, без
    ограничения) — защита от спама «подписался и сразу пишет»; сервер сверяет с датой
    подписки (`joinedAt` в подписчиках канала);
  - заблокированный в канале не комментирует; админов канала ограничения «кто / срок подписки»
    не касаются, модерация (удалить комментарий, заблокировать автора) — по правам админа
    канала.
  Все проверки — на сервере при отправке; клиент заранее показывает причину вместо поля ввода.
- **Доставка.** Комментарии не рассылаются подписчикам канала: клиент подписывается на ветку
  поста по стриму, пока она открыта, и получает новые / правки / удаления; счётчик под постом
  приходит с журналом канала (fan-out на чтение). Ответ на мой комментарий и упоминание — пуш
  автору.
- **Клиент (демо).** Ветка пока показывается скрытым чатом (`Chat.threadOf` / `threadPostID`)
  ради переиспользования окна чата; в реальной реализации это отдельный источник
  (`ChatsDataSource` — комментарии поста), в списке чатов её нет.

## Антиспам

Как защищается Telegram (исследование 2026-10-08): номер телефона как «цена» аккаунта (в части
стран — платная регистрация вместо SMS); урезанная активность новых аккаунтов первые дни;
`FLOOD_WAIT` — лимит частоты по методам; `PEER_FLOOD` — бессрочная метка «ограничен» (после
жалоб / массовых сообщений незнакомым: нельзя начинать чаты с не-контактами, статус —
`@SpamBot`); с 2025 — «заморозка» аккаунта с апелляцией; карточка незнакомца в личке (страна,
дата регистрации, общие группы); платные сообщения от не-контактов; у админа — Aggressive
Anti-Spam (группы от 200 участников, вкл/выкл, журнал и «не спам»), заявки, «вступить, чтобы
писать», медленный режим, бусты для обхода ограничений. Капчи нет — её делают сторонние боты.

У нас:

1. **Серверные лимиты частоты — при реализации сервера (этап 1+).** Отправка
   сообщений/комментариев, вступления, создание чатов, поиск контактов: лимит на пользователя и
   метод, ответ «повтори через N с» (свой gRPC-статус, не `unavailable`/`unauthenticated` —
   их `API.call` превращает в «нет сети» / выход), клиент показывает отсчёт, как у медленного
   режима.
2. **«Новичкам — без ссылок и медиа»** — сделано в демо (см. прогресс этапа 0).
3. **Жалобы и репутация аккаунта — отложено (решено 2026-10-08: делаем позже).**
   - «Пожаловаться на спам» — на комментарий, сообщение в группе и в личке (long-press-меню);
     пожаловавшийся сразу перестаёт видеть сообщение, сервер копит сигнал.
   - Репутация аккаунта на сервере из сигналов: жалобы (с весом по репутации жалующегося),
     возраст аккаунта, источник верификации номера (`phoneVerificationSource`: звонок по RU-номеру
     надёжнее, Яндекс ID — слабее), одинаковые / почти одинаковые тексты по разным чатам, много
     сообщений незнакомым подряд.
   - Ступени: **«ограничен»** (аналог `PEER_FLOOD`: нельзя начинать личные чаты с не-контактами,
     комментировать и писать в группы, где не состоишь давно) → **«заморожен»** (только чтение и
     апелляция) → удаление. Статус и апелляция — в приложении (свой экран), не через бота.
   - **Встроенный антиспам-фильтр** для каналов и больших групп: переключатель у админа, удалённое —
     в журнале админа, кнопка «Не спам» (ложное срабатывание обучает фильтр). Начать с правил
     (дубликаты, ссылки от новичков, частота), ML — потом.
   - **Карточка незнакомца в личке**: при первом сообщении от не-контакта — «в Iperon с … 2026»,
     общие группы, давно ли менял имя / фото; плашка «Пожаловаться / Заблокировать / Добавить в
     контакты».
4. Не берём: платные сообщения и бусты (нет экономики звёзд / Premium).

## Этап 1+. Реализация (после UX)

Разбор 2026-10-09: как клиентское демо ложится на сервер `iperon`. Кода по чатам пока нет ни
на сервере, ни в клиентском репозитории: есть только интерфейс `ChatsDataSource`
(`lib/chats/chats_data_source.dart`, ~60 методов) и демо-реализация `ChatsDemoDataSource`
(`lib/demo/chats_demo_data_source.dart`, в памяти). Экраны и cubit'ы работают только через
интерфейс — настоящая реализация (SQLite + gRPC) встаёт на место демо, UI не меняется.

### Клиентские модели → сервер

**`Chat` смешивает три уровня — на сервере их разделяем:**

| Уровень | Поля `Chat` | Сервер |
|---|---|---|
| Общий чат | title, about, username, joinMode, defaultRole, slowMode, реакции, комментарии, communityID, announcements, overrides | `chats` |
| Моё участие | myRole, rights, rank, joinedAt, isMember, joinRequested | `chatMembers` |
| Мой диалог | pinned, muted/mutedUntil, archived, draft, unreadCount, markedUnread | тот же документ `chatMembers` (один на userID+chatID) + `readInboxMaxID`/`readOutboxMaxID` |

Папки (`ChatFolder`) — один документ на пользователя, синхронизируются между устройствами (как
приватность: снимок + push на все сессии).

**`Message` — представление «глазами смотрящего»:**
- `outgoing` / `senderName` / `status` не хранятся: `outgoing` = `fromUserID == я`, имя — из
  кэша `profiles`, `status` (✓/✓✓) — сравнением с `readOutboxMaxID` (см. «Отметки о прочтении»).
- `reactions[].chosen`, `poll.options[].chosen/voters` — не в сообщении: коллекции
  `messageReactions` / `pollVotes` (по userID) + агрегированные счётчики в сообщении.
- `localPath` / `thumbPath` / `avatarPath` / `coverPath` / `uploadedBytes` — только клиент; на
  сервере — `cdnID` (+ размеры, thumbhash, duration). Ключ файла уже уходит на сервер в
  `UPLOAD_CONFIRM` → отправка: сначала `Upload`, затем сообщение с `cdnID`.
- ID: у клиента `String`; на сервере `messageID` — монотонный int64 в чате (так уже ждёт
  `PushPayload.messageID`), `chatID` — ObjectID (`bytes`).
- Текст + entities + reply/forward + poll + медиа шифруются **одним protobuf-блобом**
  `contentEncrypted` (один `Encryptor.Encrypt` на сообщение, не по полю). Открыты: `chatID`,
  `messageID`, `fromUserID`, `date`, тип, флаги.

**Логика демо, которая переезжает на сервер (он — источник истины, клиент только рисует):**
- роли и права (`covers`, `adminRightsFor`, `canBanMember`, модераторы темы);
- наследование в сообществе (`_effective`, `fromCommunity`, `overrides`, баны сообщества) —
  сервер отдаёт уже вычисленные значения + список `overrides`;
- проверки при отправке: медленный режим, «Новичкам — без ссылок и медиа», срок и «кто может
  комментировать»;
- отложенные сообщения (отправляет сервер по таймеру), опросы / викторины, просмотры, счётчики
  ссылок-приглашений, заявки;
- передача владения — с подтверждением облачным паролем (`CLOUD_PASSWORD_VERIFY` уже есть).

**Решить:**
- **Юзернеймы** — сейчас уникальность только внутри `profiles.username`; у групп/каналов то же
  пространство (`iperon.net/<name>`) → общая коллекция `usernames` (`username → kind, id`,
  unique-индекс).
- **Комментарии каналов** — в демо скрытый чат `threadOf`, решено — отдельная сущность.
  Предложение: в `messages` с `chatID = канал` и `threadID = postID`, своя нумерация в ветке.
- **Личный чат** — создаётся при первом сообщении, unique-индекс на пару
  `(minUserID, maxUserID)`.
- **Превью ссылок** — загружает сервер (как Telegram) или клиент (приватность).

### Что даёт сервер

**Готово и ложится:**
- конверт `MessageType` + `exchangeEncrypted` (`internal/api/v1.go`), `PublishToUser` по NATS
  (`services/publisher.go`);
- presence в Redis (онлайн; «печатает…» — рядом, с коротким TTL);
- пуши: `Notification` с `ChatID/MessageID/Scope`, гейт по онлайну и `applyNotifySettings` —
  готовы, нет только продюсера MESSAGE (образец — `NotifyContactJoined`);
- CDN по `cdnID` (`repositories/cdn.go`), шифрование полей (`profileHdf` в
  `repositories/profile.go`);
- в NATS **уже заготовлен JetStream-стрим `syncer` (`chat.*`, `group.*`)** — не используется;
- приватность «кто может добавлять меня в группы» — по образцу `CanCall`
  (`services/contacts.go`) + поля в `privacySettings`;
- тесты репозиториев — memongo (`internal/repositories/setup_test.go`), Redis — miniredis.

**Нет — делать:**
- **Синхронизация обновлений** — главная новая часть. Сейчас сервер умеет только рассылать
  снимок (приватность, профиль), для сообщений это не годится. Нужны журнал `updates` с `pts`
  (на пользователя — личные и группы; на канал — каналы), `GET_DIFFERENCE` при
  переподключении, детект дыр, `randomID` (идемпотентная отправка), outbox на клиенте.
- **Общий лимитер частоты** в Redis (антиспам, п. 1) — сейчас только точечный `AllowTestPush`.
- **Fan-out**: `PublishToUser` каждому — для личных и небольших групп; группы до 200k — через
  очередь (стрим `syncer`); каналы — чтение из общего журнала, без рассылки каждому.

**Протокол:** в стиле приватности (один `MessageType` на действие) вышло бы 60+ значений enum.
Предложение — по доменам с `oneof`: `CHATS`, `MESSAGES`, `CHAT_MEMBERS`, `CHAT_INVITES`,
`CHAT_FOLDERS`, `UPDATES`, `GET_DIFFERENCE`.

### Mongo / Redis / NATS

- `chats`, `chatMembers` (роль/права + состояние диалога, индекс `(chatID, role, joinedAt)` —
  курсорные страницы участников), `messages` (`(chatID, messageID)`), `updates` (`pts`),
  `messageReactions`, `pollVotes`, `chatReads` (TTL, см. ниже), `usernames`, папки;
- Redis — typing, счётчики, rate limit; NATS — subject на чат для каналов, JetStream для fan-out.

### Клиентский репозиторий

- Миграции SQLite: `dialogs`, `messages`, `message_media`, `chat_members`, `outbox`, `drafts`,
  `updates_state`, FTS5.
- `ChatsRemoteDataSource implements ChatsDataSource`: читает из SQLite (видно offline), пишет
  через API; входящие — централизованно в `API._handleMessage`, как приватность.
- Маппер «сервер → текущие `Chat`/`Message`», чтобы экраны не менялись. Демо остаётся за флагом.

### Порядок по срезам (дорожная карта, 2026-10-10)

**Как делаем каждый срез** — один и тот же цикл:
1. proto — дописываем в `protos/chats_v1.proto` новые ветки `oneof` (старые клиенты их
   игнорируют, номера полей не переиспользуем);
2. сервер (`iperon`) — репозиторий → сервис → `api/chats.go`, тесты на memongo / miniredis; каждое
   изменение — запись в журнал `updates` (pts) + push на все устройства;
3. клиент — миграция SQLite, `ChatsSync` (применение обновлений), `ChatsRemoteDataSource`,
   включение возможности в `ChatsRemoteDataSource.features` (`ChatsFeatures`) — экраны демо уже
   готовы и не меняются;
4. offline: чтение — из SQLite; отправка сообщений — через outbox; прочие серверные действия без
   сети — `ChatsOfflineException` → диалог / SnackBar «нет сети», без оптимистичного отката;
5. проверка на двух устройствах (iOS + Android) → отметка в этом плане.

Всё — под флагом «Серверные чаты» (экран «Разработчик»). Флаг включаем по умолчанию, когда

#### Срез 3. Группы

- **Модель** — `chats` (тип `group`, настройки чата), `chatMembers` (роль, `ChatAdminRights`,
  звание, `joinedAt`, бан), индекс `(chatID, role, joinedAt)` — курсорные страницы участников,
  поиск по `@username`. Общая коллекция `usernames` (`username → kind, id`, unique) — для
  профилей и чатов сразу.
- **Права — на сервере**: перенос `covers` / `adminRightsFor` / `canBanMember` в Go, каждая
  команда проверяет право; клиент только прячет кнопки.
- **Журнал**: решить до начала — у групп свой pts на чат (как супергруппы Telegram и наши
  каналы) вместо копии обновления каждому участнику: при 200 000 участников запись в журнал
  каждого — 200 000 записей на сообщение. Рекомендую сразу журнал на чат + `getChannelDifference`
  для групп, где я участник; per-user журнал оставить личным чатам и моим настройкам диалогов.
- **Доставка**: живой push онлайн-участникам — NATS subject на чат (подписка стрима на мои
  группы) или JetStream `syncer` (`group.*`, уже заготовлен); пуши — очередью с гейтом по
  presence и `muteUntil`; @-упоминание пробивает заглушённый чат.
- **Функции** (демо готово): создание, «Изменить», способы вступления, ссылки-приглашения
  (срок / лимит / одобрение), заявки, участники (роль / исключить / бан / добавить), админы и
  права, «Передать владение» (с облачным паролем — `CLOUD_PASSWORD_VERIFY`), сервисные сообщения,
  @-упоминания и `unreadMentions`, опросы (`pollVotes`), медленный режим и «Новичкам — без ссылок
  и медиа» (проверка при отправке), реакции группы (режим и набор), «Кто прочитал» (≤ 100,
  `chatReads`), «Скрыть участников».
- **Приватность** — «кто может добавлять меня в группы» (по образцу `CanCall`).
- **Реакции и закрепы — из документа сообщения в отдельные коллекции** `chatReactions` /
  `chatPins` по `(chatId, messageId)` (решено 2026-10-13): в больших группах реакции раздувают
  сообщение, а тело после окна правки становится неизменным — основа архива истории (раздел
  «Архив истории сообщений»). Миграция существующих `reactions` / `pinnedFor` личных чатов.

#### Срез 4. Каналы

- **Журнал канала** (pts на канал) и чтение из него без рассылки каждому (fan-out на чтение);
  догон — `getChannelDifference` по моим каналам; живые посты — NATS subject канала.

### Отметки о прочтении (решено 2026-10-09: как в Telegram)

Как в Telegram (исследование 2026-10-09) — два разных механизма:

1. **Галочки ✓ / ✓✓.** ✓ — на сервере, ✓✓ — прочитано; отдельного «доставлено» нет. Сервер
   не хранит статус у сообщения: на диалог пользователя — `readInboxMaxID` (до какого я прочитал
   входящие) и `readOutboxMaxID` (до какого собеседник прочитал мои). Клиент шлёт
   `readHistory(maxID)` → сервер рассылает «inbox прочитан» моим устройствам (снять счётчик и
   пуш `READ_HISTORY`) и «outbox прочитан» отправителю (✓✓). В группе ✓✓ — когда прочитал **хоть
   один** участник. В каналах галочек нет — счётчик просмотров.
2. **«Прослушано»** — отдельно от «прочитано»: голосовые (и видео-кружки, когда появятся)
   отмечаются при воспроизведении (`readMessageContents` в Telegram); тем же вызовом снимаются
   непрочитанные @-упоминания (по сообщению).
3. **«Кто прочитал» в группе** — long-press-меню своего сообщения: «N прочитали» + аватарки,
   тап → список «кто и когда» вместе с реакциями. Запрашивается **по требованию** (не push).
   Только в группах **до 100 участников** (больше — «чат слишком большой»); хранится **7 дней**
   после отправки (старее — «сообщение слишком старое»).
4. **«Прочитано в 12:30» в личном чате** — строка в long-press-меню своего сообщения, по
   требованию, хранится **7 дней**. Приватность — в «Последнем посещении»: флаг «Скрывать время
   прочтения» от тех, от кого скрыто последнее посещение. **Взаимно всегда** (у Telegram Premium
   снимает взаимность — у нас исключения нет): скрыл своё — не видишь чужое. Скрыл собеседник —
   строка не показывается. Галочки ✓✓ при этом остаются — скрывается только время.

**Хранение — события прочтения, а не отметки на сообщениях.** Одно `readHistory(maxID)` —
один документ `chatReads {chatID, readerID, maxID, date}` с TTL-индексом Mongo 7 дней:
- «когда прочитал сообщение X» — самое раннее событие читателя с `maxID ≥ X`;
- «кто прочитал X» — то же по всем читателям (группы ≤ 100 — дёшево);
- записей столько, сколько раз открывали чат, а не сколько сообщений; удаляются сами.

Гейт времени прочтения — по образцу `CanSeeLastSeen` (там уже есть allow/deny-списки и та же
взаимность). Пороги 100 участников / 7 дней — в конфиге сервера.

**UI в демо** (2026-10-09, проверено на устройстве 2026-10-09): в меню своего прочитанного сообщения
(`readReceiptsApply` в `lib/chats/read_receipts.dart`: личный чат кроме «Избранного» или группа

### Архивирование сообщений (блобы)

Mongo держит только «горячую» историю; старые сообщения упаковываются пачками в зашифрованные
блобы в S3.

- **Пачка** — непрерывный диапазон `messageID` одного чата: закрывается по количеству (напр.
  1000 сообщений) или по возрасту (напр. сообщения старше 30 дней). Порог — обсудить.
- **Формат блоба**: protobuf `MessageBatch{chatID, fromMessageID, toMessageID, messages[]}` →
  сжатие (zstd) → шифрование. Ключ — случайный на блоб, обёрнутый `crypto.Encryptor` (как ключ
  файла в `RepositoryCDN`); блоб в S3 — только шифротекст.
- **Индекс в Mongo** (`messageArchives`): `chatID`, `fromMessageID`/`toMessageID`,
  `fromDate`/`toDate`, `count`, ключ объекта в S3, обёрнутый ключ + HKDF-соль, sha256, размер,
  класс хранения (hot/cold), `createdAt`. После успешной заливки и сверки хэша сообщения
  диапазона удаляются из горячей коллекции.
- **Чтение истории**: запрос «сообщения до `messageID` X» → если диапазон в архиве, сервер
  берёт блоб (LRU-кэш расшифрованных пачек в памяти/Redis), расшифровывает, режет нужное окно.
  Вариант на обсуждение: отдать клиенту presigned-URL + ключ блоба по сессионному каналу, чтобы
  клиент качал и расшифровывал сам (разгружает сервер).
- **Изменения после архивации** (правка, удаление, реакции, закрепы): блоб неизменяемый —
  пишем оверлей (`messageOverrides`: правки/tombstone по `chatID`+`messageID`), применяем при
  чтении; при накоплении оверлеев — переупаковка пачки (compaction) с новым ключом, старый
  объект удаляем.
- **Удаление чата / «удалить у всех»**: удаляем объекты и обёрнутые ключи (без ключа блоб
  нечитаем, в т.ч. в бэкапах S3).
- **Горячие → холодные блобы**: свежие пачки — в `s3Message.dsn`, старые (напр. > 6–12 мес. без
  обращений) перекладываются в `s3Message.dsnArchive`; в индексе меняется класс хранения.
- Счётчики (просмотры в каналах, непрочитанные) и `pts`-журнал в блобы не уходят — остаются в
  Mongo/Redis.

### Медиа: горячее → холодное хранилище

- Новые файлы — в горячем CDN-бакете (`s3Cdn.dsn`, `s3Cdn.host`).
- Фоновая задача (`gocron`, как `CallPasswordBalance`) перекладывает файлы без обращений дольше
  порога (напр. 90 дней) в холодный бакет (`s3Cdn.dsnArchive`, `hostArchive`): копирование →
  проверка хэша → смена `storageClass`/хоста в `cdn` → удаление из горячего. Аватары и прочие
  «живые» файлы не трогаем (флаг закрепления).
- `lastAccessAt` в `cdn` обновляется при выдаче URL (батчем через Redis, не на каждый запрос).
- Клиент получает URL уже под нужным хостом (`cdnID` не меняется — кэш на устройстве остаётся
  валидным). Холодный класс у Selectel может отдавать медленнее/дороже за чтение — при частых
  обращениях файл можно вернуть в горячий (обсудить).
- Альтернатива перекладке кодом — lifecycle-правила бакета (если Selectel поддерживает смену
  класса хранения на месте) — проверить, это проще.

## Удаление файлов и медиа (план 2026-10-13)

**Сервер написан 2026-10-13** (на стенде 2026-10-13: задача работает, файлы ничьих сообщений удаляются из S3 — проверено после очистки чатов и после «удалить у всех»; пересланная копия сохраняет файл — проверено; «удалить у себя» обоими по очереди не проверялось): пункты 1–5 —
`services/chats_media_gc.go`, `repositories/chats_media.go`, `repositories/cdn_gc.go`, задача
`ChatMediaGC` (`internal/tasks`), настройки `chatMediaGc` (**выключено по умолчанию** — включить
`enabled: true` в конфиге стенда). Тесты `TestServiceChats_MediaRefs`,
`TestServiceChats_CollectMedia`, `TestTasks_ChatMediaGC`. Не сделано: сообщения, скрытые у всех
ещё до этой версии, окончательно не удаляются (их файлы остаются) — только новые удаления.

Сейчас ни один путь удаления файл не трогает: «удалить у всех» стирает документ сообщения,
«удалить у себя» дописывает `deletedFor`, «удалить чат» сдвигает `clearedMaxId` — объекты в S3 и
записи `cdn` остаются навсегда, как и загруженные, но так и не отправленные файлы. Удалять сам
файл в момент удаления сообщения нельзя: пересылка копирует содержимое с тем же `cdnID`, один
объект в S3 принадлежит оригиналу и всем пересланным копиям (в т. ч. в «Избранном»). Счётчик
ссылок в `cdn` хрупок (путей удаления много, сбой посередине — неверное число), поэтому —
**сборка мусора по ссылкам**. Закон Яровой рабочее хранилище не касается: копия для него пишется
в отдельные бакеты в момент передачи (раздел ниже), поэтому удалённое удаляется по-настоящему.

1. **Ссылки на файлы открыто в сообщении**: `messages.mediaCdnIds` и
   `scheduledMessages.mediaCdnIds` — `cdnID` вложений и обложек видео (сервер знает их при
   отправке; это не содержимое). Пересылка пишет те же `cdnID`. Индекс по полю.
2. **Окончательное удаление сообщений, которые не видит никто**: «удалить у себя» → если
   `deletedFor` покрывает всех участников (в «Избранном» — сразу), документ удаляется; «удалить
   чат» → сообщения с `messageId` ≤ `clearedMaxId` у всех участников удаляются. При удалении
   сообщения его `cdnID` ставятся в кандидаты (`cdn.gcCandidateAt`).
3. **Сборка мусора** (`gocron`, раз в час, на любой копии сервера — захват кандидата с арендой,
   как у отложенных): кандидаты с истёкшим периодом ожидания (по умолчанию сутки — гонки с
   пересылкой, outbox после обрыва, отложенными) → нет ссылок ни в `messages`, ни в
   `scheduledMessages`, ни в аватарах → `RepositoryCDN.Delete` (S3, затем запись в Mongo;
   повторяемо). Ссылка нашлась — пометка снимается. Только папка `chats`.
4. **Брошенные загрузки**: `cdn` из папки `chats` старше 3 дней без единой ссылки — туда же.
5. **Существующие сообщения**: разовая задача расшифровывает содержимое и заполняет
   `mediaCdnIds`; до её завершения сборка мусора выключена (флаг в настройках).
6. **Клиент**: обязательных изменений нет; позже — чистка локального кэша файлов удалённых
   сообщений.
7. **Тесты**: удалил у всех — файл удалён после ожидания; переслал и удалил оригинал — файл
   жив, удалил копию — удалён; «удалить у себя» обоими и очистка чата обоими — сообщение и файл
   удалены; отложенное держит файл; брошенная загрузка — через 3 дня; сбой посередине —
   повтор доводит до конца.

Настройки: `chatMediaGc.enabled`, `graceAfter` (сутки), `abandonedAfter` (3 дня), `every` (час).

индексы. С горячим окном 7 дней — ~2,8 млн активных пользователей на 1,5 ТБ
(расчёт ниже). В архиве сообщение ~100–150 байт (сжатие до шифрования, одна
обвязка на блок). После среза 3 — потому что с группами меняются объёмы и журнал.

**Горячее окно — решено 2026-10-13: 7 дней.** В Mongo на чат: сообщения за
последние **7 дней** + закреплённые + непрочитанные; **минимума «последние N
на чат» нет** (решено 2026-10-13: новое устройство — редкий случай). Цена: на
новом устройстве последнее сообщение молчащего чата для списка диалогов и
первая страница его истории читаются из архива (последний блок последней
пачки) — чуть медленнее; на своём телефоне история локальная, разницы нет. **«Избранное»
пока не архивируется** (решено 2026-10-13): там правка без срока, сообщения
целиком остаются в Mongo.

Вместе с окном **журнал обновлений (`UpdatesRetention`) — 7 дней** вместо
нынешних 14: устройство, офлайн до недели, догоняет из журнала и всё нужное
ещё в Mongo; дольше — `tooLong`, перезагрузка диалогов, старое — из архива
при прокрутке. Окно 7 дней > окна правки 48 ч → архив неизменяем.

Расчёт (2026-10-13, грубо): 50 сообщений/день на активного пользователя,
~500 Б сообщение в Mongo, ~25 чатов на пользователя, журнал 2 записи × 170 Б
на сообщение, «прочее» (диалоги, участники, контакты, профиль) ~100 КБ —
прикидка, измерить на стенде; полезно 1,1 ТБ из 1,5 ТБ.

| Вариант | На пользователя | Пользователей на 1,1 ТБ |
|---|---|---|
| **7 дней, без минимума на чат, журнал 7 дней (выбрано)** | ~395 КБ | **~2,8 млн** |
| 7 дней + последние 20 на чат, журнал 7 дней (отклонено) | ~645 КБ | ~1,7 млн |
| 48 ч, без минимума, журнал 7 дней | ~270 КБ | ~4 млн |
| вся история за год, без архива | ~9,3 МБ | ~120 тыс. |

При 30 сообщениях/день — примерно в 1,5 раза больше пользователей. Раньше
диска упрётся одиночный сервер Mongo (CPU, сеть). 48 ч отклонено: заметно
чаще чтения из архива (всё старше двух дней на новом устройстве — из S3) ради
~30% места. Группы — только с журналом на чат (срез 3), иначе журнал съест
всё.

**Пачка из блоков.** Задача раз в сутки собирает старые сообщения чата в пачку
(~1000 сообщений) = один объект S3: **блоки по 100 сообщений** (решено
2026-10-13), каждый сжат (zstd) и зашифрован серверным ключом отдельно,
лежат подряд. Указатель в Mongo:

```
messageArchives: { chatId, fromMessageId, toMessageId, s3Key,
                   blocks: [{fromMessageId, offset, length}],
                   mediaCdnIds[],   // для сборщика мусора файлов
                   deleted[],       // messageId, удалённые совсем
                   deletedFor{},    // messageId → [userId], «удалить у себя»
                   createdAt }
```

Чтение одного блока — GET с `Range` (~10–15 КБ), не всей пачки. `History`
дошёл до границы горячих → указатель → нужные блоки → расшифровка → страница;
протокол клиента не меняется, новое устройство получает старое при прокрутке.
Небольшой кэш недавно прочитанных блоков (память/Redis, минуты) — для
пролистывания подряд. `MediaReferenced` смотрит и в `mediaCdnIds` указателей.

Порядок записи (надёжность): пачка в S3 → указатель → удаление сообщений из
Mongo; упали посередине — дубль схлопывается по `messageId` при чтении,
следующий проход доделывает.

**Изменения архивных сообщений — решено 2026-10-13: изменяемое вынесено из
сообщения.** Реакции и закрепы хранятся не в документе сообщения
(`reactions`, `pinnedFor` сейчас), а рядом, по `(chatId, messageId)`:

```
chatReactions: { chatId, messageId, userId, emoji, date }
chatPins:      { chatId, messageId, userId }
```

Тогда тело сообщения после окна правки (48 ч, `chatEditWindow`) неизменно, и
в архив уходят только неизменные тела: ничего не поднимается обратно в Mongo,
нет `overridden`, повторного ухода в архив и склейки мелких пачек. Реакции и
закрепы работают на сообщениях любой давности (пользователь ничего не теряет,
клиенту прятать нечего). История — плюс один запрос на страницу (реакции
диапазона `messageId` по индексу). **Переделку хранения реакций и закрепов
делаем в срезе 3** (в больших группах реакции в документе сообщения раздувают
его), к архиву сообщения уже неизменяемы. Отклонённый вариант — запретить
реакции/закреп на архивных: проще, но заметная потеря для пользователя и
клиенту нужен признак «в архиве».

Что остаётся изменяемым в архиве — только удаление (запретить нельзя):
- «удалить у себя» — в указателе, кто удалил (`deletedFor: {messageId: [userId]}`),
  при чтении этому пользователю пропускается; удалили все — как удалённое;
- удаление у всех / невидимо всем — `deleted` в указателе, при чтении
  пропускается;
- «удалить чат» обоими — пачки и указатели удаляются целиком;
- «Избранное» (правка без срока) — пока не архивируется (см. «Горячее окно»).

**Перепаковка (дефрагментация).** Удалённые сообщения занимают место, а
удалённое у всех физически остаётся в S3 — так нельзя
надолго (ожидание пользователя «удалил — значит удалил», 152-ФЗ). Поэтому
фоновая перепаковка: читает живые сообщения пачки → пишет новый объект →
меняет указатель (новый `s3Key`, пустой `deleted`) → старый объект
удаляет с задержкой (чтения в полёте). Когда:
- в пачке есть удалённые у всех — в течение суток (срок из конфига), не ждать
  порога;
- удалённых > ~30% — по порогу (экономия места).

Закон Яровой — отдельно (свои бакеты, копия в момент передачи, TTL); архив
истории его не заменяет и не смешивается с ним.

**Совместимость с группами (решено 2026-10-13: архив делаем до среза 3, группы
вписываются потом).** Архив работает с `(chatId, messageId)` и не зависит от
типа чата; пачки/блоки/указатель/перепаковка/`mediaCdnIds` — общие. Заложить:
1. Всё изменяемое — вне тела сообщения: реакции, закрепы, а в группах/каналах
   сразу так же голоса опросов (`pollVotes`), просмотры и т. п. — отдельные
   коллекции по `(chatId, messageId)`. Ещё изменяемое в теле сейчас:
   `mediaUnread` (голосовое прослушано — может случиться и через неделю) и
   `deletedFor` (уходит в указатель пачки) — `mediaUnread` решить при архиве
   (вынести так же или держать непрослушанные голосовые горячими).
2. «Непрочитанные остаются в Mongo» — только в личных чатах; в группах (кто-то
   из участников не читает никогда) — только окно 7 дней.
3. Видимость — фильтром при чтении, одинаково для Mongo и архива:
   `deletedFor`, `clearedMaxId`, в группах — граница «история скрыта для новых
   участников» (minMessageId участника). Пачки не трогаются.
4. В больших группах «невидимо всем» почти не бывает — удаление только «у
   всех», удалением чата и перепаковкой.
5. История — одна функция чтения Mongo + архив, группы получают архив даром.
6. Пачка закрывается по 1000 сообщений или раз в сутки (большая группа
   набирает 1000 за часы, личный чат — за месяцы).

## Хранение по закону Яровой (ОРИ) — отдельные бакеты (план 2026-10-13)

Требование (ст. 10.1 149-ФЗ; уточнить у юриста; обязательно только после включения в реестр
ОРИ): **содержимое** (текст, медиа, файлы) — до **6 месяцев с момента окончания приёма /
передачи / доставки** (не с момента удаления: удаление пользователем срок не продлевает и не
сокращает; пересылка — новая передача, новый отсчёт); **сведения о передаче** (кто, кому, когда,
что) — **3 года** после завершения действий (с 1 января 2026, постановление № 1698 от 30.10.2025).

**Решение: отдельные бакеты для логов, запись в момент передачи** — Mongo о законе не знает и
удаляет по-настоящему (раздел выше). **Исключение — файлы**: оригинал в CDN-бакете держится
6 месяцев от последней передачи (решено 2026-10-14, см. «Медиа»), копий нет.

- **Два бакета — Cloud.ru Evolution, ледяной класс (обновлено 2026-10-14)**:
  `iperon-retention-content` и `iperon-retention-meta` (стенд — `iperon-staging-retention-*`).
  Пачки по ~20 МБ, читаются только по запросу; медиа в `content` не копируются. Срок —
  lifecycle-правило `Expiration` на весь бакет через S3 API (`put-bucket-lifecycle-configuration`,
  срок от загрузки объекта, округление до полуночи UTC + до суток): **184 дня** для content,
  **1096 дней** для meta, + `AbortIncompleteMultipartUpload` 2 дня. Раз всё пишется в момент
  передачи, срок от загрузки = срок от передачи — своих задач удаления нет. **Object Lock не
  включаем** — в Cloud.ru он блокирует `Expiration`; версионирование выключено.
- **Ключ сервера к этим бакетам — только запись** (без `Get` / `List` / `Delete`): сервер
  ничего не читает и не удаляет, объекты удаляет само хранилище по сроку. Чтение — отдельным
  ключом для ответа на официальный запрос. **Проверить в Cloud.ru (на стенде)**: роль
  сервисного аккаунта «только запись» или политика бакета через S3 API (`PutBucketPolicy`;
  через панель политика не заработала). Не получится — обычный ключ записи: прочитать всё равно
  нельзя (шифрование ключом ОРИ), остаётся риск раннего удаления при взломе сервера — к юристу.
  Ключ — отдельный от `storages` (там полный доступ).
- **Сведения о передаче** (3 года): на каждое событие (отправка, доставка, прочтение, правка,
  удаление, звонок, загрузка / скачивание файла) — строка лога: время, `chatID`, `messageID`,
  отправитель, получатели, тип, размер, `cdnID` вложений, сессия / IP. Без содержимого. Пачками
  (каждые 10 минут или по 32 МБ) в `retention.meta`. До отправки записи не теряются при рестарте
  (очередь NATS JetStream, см. «Тексты — правила»).
- **Текст** (6 месяцев): тем же способом — лог содержимого (текст, entities, подписи,
  **каждая правка — новой записью**) пачками в `retention.content`. Удаление и правка в рабочем
  хранилище копию не трогают — она уже записана.
- **Медиа** (6 месяцев) — **держим оригинал в CDN-бакете, без копий (решено 2026-10-14)**.
  Копии стоили бы ~72 млн COPY/мес при 1 млн сообщений/ч (~150–220 тыс. ₽/мес только запросы)
  плюс второе хранение; оригинал и так лежит в холодном бакете.
  1. При каждой передаче файла (отправка, пересылка, отложенное — в момент реальной отправки)
     `cdn.retainedUntil = max(retainedUntil, сейчас + 6 месяцев)`.
  2. Сборщик мусора удаляет файл, только если на него **нет ссылок и `retainedUntil` прошёл**.
     Удаление пользователем снимает ссылку; объект лежит до срока.
  3. Доступ к удалённому, но хранимому файлу закрыт ссылками с токеном: сервер не выдаёт ссылку
     на файл без живого сообщения, старые ссылки истекают за 7 дней.
  4. Когда на файл не осталось ссылок, из записи `cdn` стирается `encryptionKey` (остаются путь
     и `retainedUntil` для удаления) — дальше файл открывает **только ключ ОРИ** (ключ файла —
     в записи `media` лога содержимого).
  5. Загруженное, но не отправленное — не передача: `retainedUntil` нет, брошенная загрузка
     удаляется через 3 дня, как раньше. Аватары — не передача.
  - Слабее отдельного бакета: ключ сервера к CDN-бакету умеет удалять, гарантия срока — код
    сборщика, а не хранилище (уточнить у юриста, достаточно ли). Цена — удалённые
    пользователями файлы лежат до 6 месяцев в холодном бакете.
- **Шифрование**: записи и ключи файлов — открытым ключом отдельной пары «ОРИ» (закрытая часть
  офлайн, не на серверах): сервер может записать, но не прочитать; утечка бакета или ключа
  записи переписку не раскрывает.
  - **Без шифрования — отвергнуто (2026-10-14).** Ключ «только запись» защищает лишь от взлома
    сервера; от доступа к аккаунту / панели Selectel, ключа чтения, ошибки ACL бакета,
    инсайдеров, открытого текста на диске NATS (и от случая, если Selectel не умеет «только
    запись») защищает только шифрование. По объёму разницы нет (сжатие до шифрования), по
    процессору — незаметно. SSE Selectel — только от кражи дисков, не замена.
  - **Закрытый ключ ОРИ — главный риск** (потерян → выдать по запросу нельзя): две офлайн-копии
    в разных местах (флешки с паролем / бумажная копия в сейфе), раз в квартал — пробная
    расшифровка одной пачки.
- **Шифрование медиа — правила (решено 2026-10-14; с 2026-10-14 без копий — оригинал в
  CDN-бакете).** Сейчас файл шифрует клиент случайным ключом 32 байта (AES-GCM + `hkdfSalt`), в
  CDN лежит шифртекст, ключ — в `cdn.encryptionKey`, обёрнутый серверным секретом.
  1. **Тело файла не перешифровываем и не копируем**: шифртекст остаётся в CDN-бакете до
     `retainedUntil`. Обложки видео / превью — отдельные `cdnID`, так же.
  2. **Ключ файла — в лог содержимого, не рядом с файлом**: сервер разворачивает
     `encryptionKey` своим секретом и пишет запись `media`: ключ + `hkdfSalt`, SHA-256
     шифртекста, размер, тип, `cdnID`, путь объекта, `chatId` / `messageId`. Едет в часовой пачке
     вместе с текстами.
  3. **Пачка — открытым ключом ОРИ**: на каждую пачку одноразовый ключ, передаётся гибридно
     (X25519 + ML-KEM-768, как в клиентском обмене ключами) → AES-256-GCM по сжатой пачке;
     одноразовый ключ после записи стирается. Формат — **age** (`filippo.io/age`, своя
     криптография не пишется, есть CLI для расшифровки); проверить поддержку постквантового
     получателя в текущей версии, иначе только X25519. В заголовке пачки — отпечаток ключа ОРИ
     (смена ключа; старые закрытые ключи хранить 3 года).
  4. **Порядок**: `retainedUntil` и запись `media` — в той же операции отправки, что и
     сообщение (до ответа клиенту).
  5. **Повторная передача** — новая запись `media` с тем же ключом и продление `retainedUntil`.
  - **Пример — фото удалено через день** (решено 2026-10-14): день 0 — отправка,
    `retainedUntil` = +6 мес., запись `media` (ключ файла) уходит в лог содержимого под ключом
    ОРИ; день 1 — удаление: ссылка снята, `cdn.encryptionKey` стёрт, ссылки на файл сервер
    больше не выдаёт, объект лежит как был (шифртекст клиента); ~день 183 — сборщик удаляет
    объект и запись `cdn`; ~день 184 — пачку лога удаляет lifecycle бакета. Файл **не
    перешифровывается и не копируется** — ни запросов, ни второго хранения; срок — от передачи,
    не от удаления.
  - **Кто что читает**: пока на файл есть ссылки, он открывается серверным секретом (как и
    сейчас); без ссылок `encryptionKey` стёрт → файл открывает **только закрытый ключ ОРИ**. Сервер не читает даже свои прошлые
    пачки; утечка `retention.*` даёт только шифртекст. Не защищает от взлома сервера «сейчас» —
    новые сообщения он видит в момент передачи.
  - **Выдача по запросу**: утилита ОРИ находит пачки за период, открывает их закрытым ключом,
    берёт ключи файлов из записей `media` и расшифровывает файлы форматом приложения.
- **Тексты — правила (решено 2026-10-14).**
  1. **Записи лога содержимого**: `send` — отправка (в т.ч. пересылка — новая передача):
     `MessageContent` как есть (текст, entities, подписи, ответ, forward, `cdnID` вложений) +
     `chatId`, `messageId`, отправитель, время; `edit` — **полное новое содержимое** (не разница);
     отложенное — в момент реальной отправки; `reaction` — эмодзи, кто, на что (содержимое ли —
     юрист; по умолчанию пишем); «Избранное» — по умолчанию пишем (юрист). Удаление, доставка,
     прочтение, звонки — только в лог сведений. Ключей файлов в `send` нет (сервер добавляет их
     только при выдаче) — они в записи `media`.
  2. **Где**: в сервисе чатов сразу после успешной записи в Mongo (рядом с рассылкой
     обновлений) — открытое содержимое в этот момент у сервера в памяти. Архив истории и удаление
     в рабочем хранилище на лог не влияют.
  3. **Ключ эпохи**: раз в час сервер создаёт случайный ключ 32 байта, сразу шифрует его ключом
     ОРИ (age) — эта копия идёт в заголовок пачек; открытый ключ только в памяти. **Микропачки**
     (решено 2026-10-14, для обоих логов): записи копятся в памяти до 100 штук или 1 секунды
     (что раньше) → zstd всей микропачки → AES-256-GCM ключом эпохи (одна nonce + тег на
     микропачку) → только потом в очередь: **открытого текста на диске нет** (в памяти — до 1 с).
     Сжатие по микропачке в 2–3 раза лучше, чем по записи (повторяются `userId`, `chatId`,
     `serverIp`, близкое время), обвязка шифрования ~0,3 байта на запись вместо 28. Рестарт
     теряет только несброшенную микропачку (≤ 1 с). Эпоха кончилась — ключ стёрт, сервер не
     читает даже свою недоотправленную очередь; рестарт — новая эпоха.
  4. **Буфер — NATS JetStream** (уже есть для уведомлений), стрим в режиме WorkQueue: запись
     удаляется из NATS после подтверждения загрузки пачки в S3 — в NATS только невыгруженный
     хвост. **Выгрузка каждые 10 минут или по 32 МБ** (что раньше) — в NATS максимум десятки МБ
     (лог сведений ≈ 120 МБ/ч при 1 млн сообщений/ч — расчёт в «Лог сведений — поля»). Лимиты стрима:
     срок 7 дней, объём ~10 ГБ; **алерт**, если в очереди записи старше 30 минут. Переполнение
     → новые записи отбрасываются с ошибкой в лог, **отправка сообщений не блокируется**
     (решение показать юристу). Код не привязан к способу доставки — очередь можно заменить.
  5. **Пачка**: записи одной эпохи → `retention.content/text/ГГГГ/ММ/ДД/ЧЧ/<сервер>-<эпоха>-<n>.pack`;
     внутри заголовок (формат, версия, отпечаток ключа ОРИ, ключ эпохи под age) + записи с
     длиной. Сбой загрузки — записи остаются в очереди, повтор.
  6. **Лог сведений** — так же (свои эпохи, стрим, `retention.meta`), без содержимого.
  7. **Выдача по запросу**: по логу сведений — `messageId` пользователя за период → пачки
     содержимого за эти часы целиком открываются ключом ОРИ → нужные записи.
- **Лог сведений — поля (решено 2026-10-14).** Плоская запись на событие, без содержимого
  (текста, эмодзи, имён файлов). Порт не пишем; содержимое звонков не пишем — только факт
  соединения «с какого IP на какой».
  - **Общие поля**: `ts` (UTC, мс), `event`, `userId`, `sessionId`, `deviceId`, `platform`,
    `appVersion`, `ip` (клиент, `realip`; для стрима — на момент открытия), `serverIp`
    (публичный адрес нашего сервера, принявшего соединение; из конфига), `server` (копия).
    Телефон в запись не кладём — его история в событиях `user.*` (по `userId` + времени).
  - **События**:
    - `message.send` — `chatId`, тип чата, `messageId`, получатели (личный — собеседник;
      группа — только `chatId`, состав из `member.*`), вид (текст / фото / видео / голосовое /
      файл), размер содержимого, `cdnId` + размеры вложений, `forwardFrom`, `replyTo`, флаг
      «отложенное»;
    - `message.edit` — `chatId`, `messageId`, новый размер; `message.delete` — `chatId`,
      `messageIds`, «у себя / у всех»;
    - `message.deliver` — **на устройство, а не на сообщение** (решено 2026-10-14): «сессия X
      получила чат C до `messageId` N» — сессия, `chatId`, до какого `messageId`, сколько
      сообщений. Не чаще раза в 10 секунд на пару «сессия + чат» (накопление в памяти, сброс по
      таймеру и при закрытии стрима), догон — одна запись на чат; `message.read` — `chatId`,
      до какого `messageId`;
    - `reaction.set` / `unset`, `pin` / `unpin` — `chatId`, `messageId`;
    - `file.upload` — `cdnId`, размер, тип, SHA-256 шифртекста;
    - `call.start` / `accept` / `reject` / `end` — `callId`, звонящий, вызываемые, аудио / видео,
      длительность, причина завершения; `call.join` / `call.leave` — участник, **IP клиента**
      (видит наш сервер при выдаче `CALL_TOKEN`) → **IP медиасервера** (LiveKit / TURN, из
      конфига), время входа / выхода. Проверить: отдаёт ли LiveKit (вебхуки
      `participant_joined/left`) реальный адрес участника — смена сети посреди звонка;
    - `session.register` / `login` / `logout` / `revoke` — способ входа, телефон;
      `stream.open` / `close` — сессия, IP, время;
    - `user.*` — смена телефона, username, имени («сведения о пользователях»);
    - `member.*` (группы, позже) — вступил / вышел / исключён, кем.
  - **Скачивание файлов** — через ссылки с токеном (см. «Холодное хранение файлов чатов» →
    «Защищённый доступ»): событие `file.link` (кому выдана ссылка, токен, `cdnID`, срок) +
    **access-лог нашего nginx на ВМ** (обновлено 2026-10-14: CDN нет — раздаёт свой nginx):
    время, IP, токен, путь, объём, код ответа. Лог раз в 10 минут сжимается, шифруется ключом
    ОРИ (age) и уходит в `retention-meta` (`nginx/ГГГГ/ММ/ДД/<вм>-<время>.log.age`), на ВМ —
    ротация, локально не копится. Сопоставление токен → пользователь — утилита ОРИ.
  - **Объём (расчёт 2026-10-14)**. Допущения: 1 млн сообщений/ч (~280/с, условно 1–2 млн
    активных в день), у получателя 2 устройства. Запись (protobuf): `ts` 8 + `event` /
    `platform` / `appVersion` ~10 + 4 ObjectID по 12 + `deviceId` 16 + `messageId` 8 + `ip` /
