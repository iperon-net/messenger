Да# Чаты, группы, каналы и сообщества (по модели Telegram)

## Контекст

Переписки в приложении пока нет: вкладка «Чаты» — заглушка (`lib/screens/chats/`, только
баннер разрешения на уведомления). Готова инфраструктура, на которую ляжут чаты:

- транспорт `Unary`/`Stream` в зашифрованном конверте сессии, живой push по NATS
  (`userID.<hex>` / `sessionID.<hex>`, `ServicePublisher`);
- пуши: `PushPayload.Kind.MESSAGE / READ_HISTORY / MESSAGE_DELETED`, `chatID`, `messageID` —
  этап 7 плана `push-notifications.md` ждёт серверную часть чатов;
- настройки уведомлений уже разделены на личные чаты / группы / каналы;
- загрузка медиа (шифрование на клиенте, докачка, CDN, `cdnID`) и `toolbar_attachments`;
- граф контактов + приватность, presence, username, LiveKit (задел под голосовые чаты групп);
- паттерн «последнее известное значение в SQLite, отдаём offline».

## Ветка

Вся работа по чатам — в ветке **`chats`**: клиент (`messenger`, уже на ней) и сервер
(`iperon` — создать `chats` от `main`, когда начнём серверную часть). Коммитит и собирает
пользователь.

## Решения

1. **Модель как у Telegram (cloud chats).** Шифрование клиент↔сервер (сессионный конверт),
   история хранится на сервере, доступна со всех устройств. Секретные E2EE-чаты — не сейчас.
2. **Шифрование в БД — как имя/фамилия в профиле.** Содержимое пишется в Mongo в поля
   `*Encrypted` через `crypto.Encryptor.Encrypt` (общий `encryptor.secretKey` + HKDF-соль
   репозитория, ср. `profileHdf` в `internal/repositories/profile.go`). Шифруются: текст и
   entities сообщения, медиа-ссылки, reply/forward-данные, черновики, название/описание
   закрытых групп. Открыты (нужны индексы): `chatID`, `messageID`, `fromUserID`, дата, тип,
   флаги. Медиа уже шифруются в `RepositoryCDN`. Текст сообщений не пишем в Redis и логи.
   Следствие: серверного полнотекстового поиска по личным чатам/группам нет — поиск локальный
   (SQLite FTS5); серверный — только по публичным каналам.
3. **Один тип групп** (как супергруппы Telegram), лимит — **200 000 участников**.
4. **Каналы** — до **нескольких миллионов** подписчиков → для каналов fan-out на чтение
   (общий журнал канала), не копия каждому подписчику.
5. **Сообщество** — группировка групп и каналов со своими настройками и настройками
   приватности (см. раздел ниже).
6. **Порядок:** сначала **UX-демо** (этап 0) на фейковых данных, чтобы закончить UX; только
   потом сервер и клиент.

## Форматирование сообщений

Как в Telegram: **текст хранится плоским + массив entities**, а не markdown-строкой.

```proto
message MessageEntity {
  enum Type {
    BOLD = 0; ITALIC = 1; UNDERLINE = 2; STRIKE = 3; SPOILER = 4;
    CODE = 5;          // `inline`
    PRE = 6;           // ```блок```, language — подсветка
    TEXT_URL = 7;      // [текст](url)
    URL = 8; MENTION = 9; MENTION_NAME = 10; HASHTAG = 11; EMAIL = 12; PHONE = 13;
    BLOCKQUOTE = 14; EXPANDABLE_BLOCKQUOTE = 15;
    CUSTOM_EMOJI = 16; // задел
  }
  Type type = 1;
  int32 offset = 2;    // в UTF-16 code units (как String в Dart)
  int32 length = 3;
  string url = 4;      // TEXT_URL
  bytes userID = 5;    // MENTION_NAME (упоминание без username)
  string language = 6; // PRE
}
```

Почему entities, а не markdown:
- плоский текст сразу годится для превью в списке чатов и в пуше, для FTS5-поиска;
- нет экранирования и «поломанной» разметки (`*` в обычном тексте), нет инъекций;
- редактирование сообщения не требует перепарсинга, entities пересекаются корректно;
- `URL`/`MENTION`/`HASHTAG`/`EMAIL`/`PHONE` можно детектить и на клиенте при рендере.

Ввод (клиент):
- **Меню выделения** (как в Telegram «Форматирование»): `contextMenuBuilder` поля ввода
  добавляет «Жирный / Курсив / Подчёркнутый / Зачёркнутый / Спойлер / Моноширинный /
  Ссылка / Цитата / Обычный».
- **Markdown-ярлыки при отправке**: `**жирный**`, `__курсив__`, `~~зачёркнутый~~`,
  `||спойлер||`, `` `код` ``, ```` ```блок``` ````, `[текст](url)`, `> цитата` —
  парсятся в entities, маркеры удаляются.
- Поле ввода — свой `TextEditingController`, который держит entities рядом с текстом,
  сдвигает offset'ы при правке и рисует стили в `buildTextSpan` (без тяжёлых rich-editor
  пакетов).
- Рендер: `entities → TextSpan`-дерево (спойлер — анимированная «пыль»/размытие, `PRE` —
  моноширинный блок с кнопкой «Копировать», ссылки/упоминания — `TapGestureRecognizer`).
- Лимиты как в Telegram: текст 4096 символов, подпись к медиа 1024 (уточнить).

## Сообщества

Сообщество = контейнер над группами и каналами:
- состав: канал объявлений (создаётся автоматически) + произвольные группы и каналы;
  существующий чат можно добавить, вынуть, создать новый внутри;
- свои настройки: название, описание, аватар, username/ссылка-приглашение, владельцы и
  админы сообщества (права: добавлять/удалять чаты, модерировать участников во всех
  чатах, управлять приглашениями);
- свои настройки приватности (черновой список, обсудить):
  - видимость: публичное (находится поиском) / приватное (только по ссылке);
  - вступление: открытое / по заявке / только по приглашению;
  - кто может создавать и добавлять чаты внутрь: только админы / все участники
    (с одобрением);
  - видимость списка участников сообщества: все / только админы;
  - могут ли участники писать друг другу в личку, не будучи контактами;
  - наследование по умолчанию для новых чатов внутри (вступление, история для новых
    участников, запрет пересылки/копирования);
- сквозная модерация: бан в сообществе = бан во всех его чатах;
- вступление в сообщество не добавляет во все чаты: в чаты вступают отдельно (кроме канала
  объявлений) — обсудить.

## Папки (табы) в списке чатов

- Табы **вверху**, в том же стиле, что фильтр «Все / Пропущенные» на «Звонках»
  (`CupertinoSlidingSegmentedControl` в `calls_cupertino.dart`, `SegmentedButton` в
  `calls_material.dart`). Папок может быть много (первой всегда «Все чаты»), а штатные
  сегмент-контролы не скроллятся → свой компонент `ChatFolderTabs` (пара
  `_cupertino`/`_material`): выглядит как сегмент-контрол «Звонков», при переполнении
  скроллится по горизонтали, активный таб автоматически докручивается в зону видимости.
- **Переключение свайпом влево/вправо** по списку: `PageView` (по странице на папку), бегунок
  таба плавно следует за `PageController.page` (не прыгает по окончании свайпа); тап по табу →
  `animateToPage`.
- На табе — счётчик непрочитанных папки (заглушённые не считаются / считаются серым).
- Long-press по табу: «Изменить», «Прочитать все», «Удалить», «Изменить порядок».
- Папка: название, иконка/эмодзи (позже), включённые типы (контакты / не контакты / группы /
  каналы / сообщества), явные «добавить чаты» / «исключить чаты», флаги «исключить
  заглушённые / прочитанные / архивные». Экран «Настройки → Папки» + рекомендованные
  папки («Непрочитанные», «Личные», «Группы», «Каналы»).
- Лимит папок — **10** (решено). Папки синхронизируются между устройствами (серверная
  настройка + кэш в SQLite, как приватность).
- **Конфликт жестов**: горизонтальный свайп по строке чата сейчас = действия
  (`flutter_slidable`), а теперь он же листает папки. **Решение (этап 0):** когда папок больше
  одной, свайп по списку листает папки, действия над чатом — через long-press-меню.

## Приватность групп (предложение пользователя)

Группа настраивает, **как человек может присоединиться**, и **какие права он получает**
после вступления. Роли (по возрастанию):

| Роль | Читать | Писать | Управлять группой |
|---|---|---|---|
| **Чтение** | ✓ | | |
| **Запись** | ✓ | ✓ | |
| **Админ** | ✓ | ✓ | ✓ |

Решено:
- **Способы вступления — все четыре** (настройка группы, выбирается один): открытая
  (по username / поиском) / по ссылке-приглашению / по заявке (одобряет админ) / только
  админ добавляет.
- **Роль по умолчанию для вступивших — `Чтение`** (настраивается: `Чтение` / `Запись`;
  `Админ` по умолчанию не выдаётся).
- **Владелец** (создатель) — роль сверх админа: не снимается, удаляет группу, передаёт
  владение, назначает/снимает админов.
- Админ меняет роль конкретного участника, удаляет и банит.

- **Права админа — раздельные, как в Telegram** (галочки при назначении админа):
  - изменять информацию о группе (название, описание, аватар, настройки);
  - удалять чужие сообщения;
  - банить и ограничивать участников (в т.ч. менять роль Чтение/Запись);
  - приглашать участников и управлять ссылками-приглашениями / заявками;
  - закреплять сообщения;
  - управлять голосовыми/видеочатами (LiveKit);
  - оставаться анонимным (сообщения от имени группы);
  - назначать новых админов (только с правами не шире своих);
  - позже: управлять темами (когда появятся форумы).

  Плюс необязательное «звание» админа (подпись в пузыре). Владелец имеет все права всегда.
  Для каналов набор свой: публиковать, редактировать чужие посты, удалять чужие посты,
  приглашать подписчиков, назначать админов.

Отложено:
- Своя роль на конкретной ссылке-приглашении (пока все вступившие получают роль по
  умолчанию).

## Реакции

Один человек может поставить **несколько разных реакций** на сообщение — до
`maxReactionsPerUser` (3, как с Premium в Telegram); тап по своей снимает её, сверх лимита
вытесняется самая ранняя наша. Под сообщением — чипы «эмодзи + число» (наши залиты), время
прижато к правому краю строки реакций; двойной тап по пузырю — быстрая реакция; удержание —
на iOS `CupertinoContextMenu` (пузырь-превью, сверху меню полоса реакций, ниже действия), на
Android — нижний лист с полосой реакций.

Какие реакции доступны:
- **Личные чаты** — фиксированный набор, без настройки (`privateChatReactions` в
  `lib/chats/reactions.dart`: 👍 ❤️ 🔥 😂 😮 😢 🙏 👎).
- **Группы и каналы** — настраивает админ (`Chat.reactionsMode` + `Chat.reactions`):
  все (`allChatReactions`) / только выбранные / никаких.

Сделано в демо (2026-10-05): модели `MessageReaction`, `Message.reactions`,
`ChatReactionsMode`; `ChatsDataSource.setReactions` (весь наш набор целиком, как
`sendReaction` в Telegram); чипы в пузыре, `ReactionPicker` в
long-press-меню (Cupertino action sheet / Material bottom sheet), двойной тап; в демо
«Техно-обзор» — только 🔥 👍 🤯 ❤️, «Родители 5 «Б»» — реакции выключены, собеседник иногда
отвечает реакцией на наше сообщение.

**Нужно реализовать в настройках:**
- **Инфо группы/канала → «Реакции»** (права: админ с правом «Изменение профиля группы»):
  - режим: «Все реакции» / «Некоторые» / «Нет реакций»;
  - для «Некоторые» — сетка эмодзи с галочками (из `allChatReactions`), порядок = порядок в
    полосе;
  - каналы: «Максимум разных реакций под постом» (как в Telegram, 1–11);
  - (возможно) лимит реакций на человека для чата — пока общий `maxReactionsPerUser = 3`;
  - изменение режима не трогает уже поставленные реакции (старые остаются видны, новые
    поставить нельзя).
- **Настройки → Чаты (или «Оформление») → «Быстрая реакция»**: какой эмодзи ставит двойной
  тап (сейчас константа `defaultQuickReaction = ❤️`); хранить в `settingsDevice` (локально)
  или в профиле (синхронно между устройствами — склоняюсь к профилю).
- **Уведомления → «Реакции»**: уведомлять о реакциях на мои сообщения — в личных чатах / в
  группах, «от всех» / «только от контактов» (как в Telegram).

**Нужно на сервере / в синхронизации (Этап 1+):**
- хранение: отдельная коллекция `messageReactions` (`chatID`, `messageID`, `userID`,
  `emoji`, `date`) + агрегат «эмодзи → число» в сообщении (для списка без выборки); сам
  эмодзи — не секрет, но связь «кто поставил» — шифровать как прочие поля (`Encryptor`)?
  решить;
- проверка: эмодзи из разрешённых для чата, не больше `maxReactionsPerUser` на пользователя
  (лимит — серверная константа/конфиг, клиент берёт его оттуда), права (бан,
  «только чтение» в канале — реакции можно, писать нельзя);
- апдейт `updateMessageReactions` через `pts`/`getDifference` и push в стрим; для каналов —
  только агрегат (fan-out на чтение, без списка авторов);
- «кто поставил»: в личных и группах — список по эмодзи (long-press на чипе), в каналах —
  анонимно;
- непрочитанные реакции на мои сообщения: бейдж ❤️ в списке чатов и прыжок к ним (как
  `unreadMentions`), строка списка «Анна: ❤️ к «…»»;
- офлайн: поставить реакцию без сети — ставим в очередь отправки (как сообщение), а не
  оптимистично-с-откатом.

## Хранение: архив сообщений в S3 и холодное хранилище медиа

Задел в конфиге сервера уже есть (Selectel S3, `internal/settings/settings.go`,
`internal/s3/CLAUDE.md`): `s3Message.dsn` (горячие блобы сообщений), `s3Message.dsnArchive`
(холодные), `s3Cdn.dsnArchive` / `hostArchive` (холодный CDN для медиа). Синглтоны `Message` /
`MessageArchive` в `internal/s3` ещё не созданы — добавить по образцу `CDN`, когда появится
потребитель.

### Архивирование сообщений (блобы)

Mongo держит только «горячую» историю; старые сообщения упаковываются пачками в зашифрованные
блобы в S3.

- **Пачка** — непрерывный диапазон `messageID` одного чата: закрывается по количеству (напр.
  1000 сообщений) или по возрасту (напр. сообщения старше 30 дней). Порог — обсудить.
- **Формат блоба**: protobuf `MessageBatch{chatID, fromMessageID, toMessageID, messages[]}` →
  сжатие (zstd) → шифрование. Ключ — случайный на блоб, обёрнутый `crypto.Encryptor` (как ключ
  файла в `RepositoryCDN`); блоб в S3 — только шифротекст.
- **Индекс в Mongo** (`messageArchives`): `chatID`, `fromMessageID`/`toMessageID`,
  `fromDate`/`toDate`, `count`, ключ объекта в S3, обёрнутый ключ + HKDF-соль, sha256, размер,
  класс хранения (hot/cold), `createdAt`. После успешной заливки и сверки хэша сообщения
  диапазона удаляются из горячей коллекции.
- **Чтение истории**: запрос «сообщения до `messageID` X» → если диапазон в архиве, сервер
  берёт блоб (LRU-кэш расшифрованных пачек в памяти/Redis), расшифровывает, режет нужное окно.
  Вариант на обсуждение: отдать клиенту presigned-URL + ключ блоба по сессионному каналу, чтобы
  клиент качал и расшифровывал сам (разгружает сервер).
- **Изменения после архивации** (правка, удаление, реакции, закрепы): блоб неизменяемый —
  пишем оверлей (`messageOverrides`: правки/tombstone по `chatID`+`messageID`), применяем при
  чтении; при накоплении оверлеев — переупаковка пачки (compaction) с новым ключом, старый
  объект удаляем.
- **Удаление чата / «удалить у всех»**: удаляем объекты и обёрнутые ключи (без ключа блоб
  нечитаем, в т.ч. в бэкапах S3).
- **Горячие → холодные блобы**: свежие пачки — в `s3Message.dsn`, старые (напр. > 6–12 мес. без
  обращений) перекладываются в `s3Message.dsnArchive`; в индексе меняется класс хранения.
- Счётчики (просмотры в каналах, непрочитанные) и `pts`-журнал в блобы не уходят — остаются в
  Mongo/Redis.

### Медиа: горячее → холодное хранилище

- Новые файлы — в горячем CDN-бакете (`s3Cdn.dsn`, `s3Cdn.host`).
- Фоновая задача (`gocron`, как `CallPasswordBalance`) перекладывает файлы без обращений дольше
  порога (напр. 90 дней) в холодный бакет (`s3Cdn.dsnArchive`, `hostArchive`): копирование →
  проверка хэша → смена `storageClass`/хоста в `cdn` → удаление из горячего. Аватары и прочие
  «живые» файлы не трогаем (флаг закрепления).
- `lastAccessAt` в `cdn` обновляется при выдаче URL (батчем через Redis, не на каждый запрос).
- Клиент получает URL уже под нужным хостом (`cdnID` не меняется — кэш на устройстве остаётся
  валидным). Холодный класс у Selectel может отдавать медленнее/дороже за чтение — при частых
  обращениях файл можно вернуть в горячий (обсудить).
- Альтернатива перекладке кодом — lifecycle-правила бакета (если Selectel поддерживает смену
  класса хранения на месте) — проверить, это проще.

## Хранение по закону Яровой (ОРИ)

Требование: **метаданные** (факты приёма/передачи/обработки сообщений) хранить **3 года**, **само
содержимое** (текст сообщений и медиа/файлы) — **6 месяцев**. Хранилище отдельное от рабочего:
пользовательское «удалить у всех», удаление чата и архивация (раздел выше) его не трогают.

Всё включается **настройкой сервера** (выключено по умолчанию, в `internal/settings/settings.go`),
сроки — тоже из конфига:

```yaml
retention:
  enabled: false
  dsn: ...               # отдельный холодный бакет, ключ сервера — только запись (PutObject)
  metaDeleteAfter: 3y    # X-Delete-After для логов метаданных
  contentDeleteAfter: 6mo # X-Delete-After для содержимого и медиа
```

### Метаданные (3 года)

- На каждое событие (отправка/доставка/прочтение/правка/удаление сообщения, вступление/выход,
  загрузка/скачивание файла, звонок) сервер пишет строку в **лог без шифрования**: время,
  `chatID`, `messageID`, `fromUserID`, получатели, тип, размер, `cdnID` вложений, IP/сессия
  отправителя. Текста нет.
- Раз в сутки лог закрывается, сжимается (zstd) и уходит в **холодный бакет** с
  `X-Delete-After` = 3 года. Ключ сервера к бакету — **только на запись**: читать, листать и
  удалять он не может, объекты удаляет само хранилище по сроку.
- Пока файл дня не отправлен, он лежит на диске/в очереди — не терять при рестарте
  (досылка при старте).

### Содержимое сообщений и медиа (6 месяцев)

- **Медиа**: при загрузке файла (`UPLOAD_CONFIRM`) параллельно с горячим CDN шифротекст файла
  кладётся в холодный бакет **вместе с ключом расшифровки**, с `X-Delete-After` = 6 месяцев.
- **Текст сообщений** (и entities, подписи, правки): тем же способом, что метаданные, — дневной
  лог содержимого → холодный бакет, но с `X-Delete-After` = 6 месяцев (отдельно от лога
  метаданных, у них разные сроки).
- Ключи и текст в этих объектах предлагаю шифровать **открытым ключом** отдельной пары
  «ОРИ» (приватная часть хранится офлайн, не на серверах): сервер может только записать, но не
  прочитать — и утечка бакета/ключа записи не раскрывает переписку. Обсудить.

### Проверить

- Поддерживает ли Selectel `X-Delete-After` через S3 API (это заголовок Swift API; в S3 —
  lifecycle-правила по префиксу/тегу). Если нет — два бакета/префикса с lifecycle 6 мес. и 3 года.
- Политика бакета «только запись» для ключа сервера (без `Get`/`List`/`Delete`).
- Точный состав метаданных и формат выдачи — по требованиям (уточнить у юриста).
