# 06-callpassword-reconnect — восстановление входа по звонку-паролю

**Статус:** in progress (2026-11-22)

## Цель

Вход по звонку-паролю перестаёт сбрасываться, когда пользователь уходит в системную звонилку: разрыв gRPC-стрима во время звонка, уход приложения в фон и смерть процесса на Android больше не возвращают его на ввод номера. Приложение переподключает стрим проверки с той же сессией, синхронизирует остаток таймера с сервером и восстанавливает незавершённую сессию после рестарта — пользователь после звонка либо сразу входит, либо возвращается на экран подтверждения, а не на `/auth`.

## Принятые решения

- **Исправление только на клиенте, сервер не трогаем** — сервер уже поддерживает восстановление: `CallPasswordConfirmation` создаёт эфемерный JetStream-консьюмер с дефолтным `DeliverPolicy = DELIVER_ALL` и фильтром `callPassword.<session>`, confirmation-событие хранится в стриме `MaxAge = CallPassword.Timeout` (GolandProjects/iperon: `internal/services/auth.go`, `internal/nats/nats.go`). Повторное открытие стрима с тем же `callPasswordSession` до истечения TTL Redis возвращает уже изданное success-событие или продолжает healthcheck'и с актуальным остатком таймера. Альтернатива отклонена: правки сервера не требуются, а его поведение (ack-подтверждение, retention) перепроверено.
- **Переподключение стрима вместо сдачи** — на `onError`/`onDone`, не вызванных терминальным исходом, кубит переоткрывает стрим с той же `callPasswordSession` с коротким экспоненциальным backoff (до ~5 с), пока локальный тикер > 0. `_serverTimerSynced` сбрасывается при каждом (пере)открытии: первый healthcheck нового стрима снова синхронизирует остаток. Исключения без ретраев: `success`/`error`/`blocked` уже обработаны, ответ сервера «сессия не найдена» (`ErrNotFoundInRedis` → Unknown/NotFound) означает истечение TTL — уводим на `/auth`.
- **Кубит наблюдает жизненный цикл** — на `resumed` переподключается, если стрим мёртв. Локальный тикер в фоне НЕ приостанавливается (на Android изолят продолжает тикать и успевал «истечь» во время звонка) — вместо этого тикер стал чисто информационным: локальный ноль запускает финальную сверку с сервером (свежий стрим с той же сессией), и терминальный timeout наступает только по вердикту сервера (healthcheck с остатком → продолжаем ждать; «not found in redis» или закрытие без остатка → таймаут). Так сервер остаётся единственным арбитром таймаута на всех платформах, включая iOS, где изолят засыпает.
- **Персистенция незавершённой сессии в device.db** — новая таблица в следующей миграции `DeviceDatabase.migrations` (device.db на миграции 10 → добавлена 11; аккаунтные миграции не трогаем: состояние пре-авторизационное и девайсовое). Хранит `callPasswordSession` (hex), `confirmationPhoneNumber`, полный `timeout` (сек) и `createdAt` (epoch-ms), из чего вычисляется остаток. Запись делает `AuthCubit.onPressed` в момент ответа сервера (это и есть момент создания серверной сессии); чтение — зеркалом в памяти (`PendingCallPassword._cached`, заполняется при старте), потому что `_redirect` синхронный. Альтернатива отклонена: колонки в `settingsDevice` — это транзиентное состояние потока, а не настройка; отдельная таблица из одной строки проще атомарно перезаписывать и чистить.
- **Восстановление после смерти процесса — сразу на экран подтверждения** — `Routers._redirect` (оба роутера) при неавторизованном пользователе и живой записи (остаток > 0) ведёт на `/auth/call_password_confirmation` с восстановленными параметрами вместо `/auth`. Решение пользователя (AskUserQuestion 2026-11-22).
- **Объём: все три механизма** (переподключение + lifecycle + персистенция) — по частям сценарий остаётся сломанным: только reconnect не спасает при смерти процесса, только персистенция не спасает при живом процессе с умершим стримом. Решение пользователя (AskUserQuestion 2026-11-22).
- **Запись очищается на всех терминальных исходах** — успех входа (включая переход на two-step `/auth/cloud_password`), `error`, `blocked`, локальный таймаут и ответ сервера «сессия не найдена».
- **Защита от двойного завершения входа** — флаг «success уже обработан» в кубите: при пересечении старого и нового стримов success не должен два раза запускать `AuthLoginCompleter.complete()`.
- **Слои** — вся логика в `AuthCallpasswordConfirmationCubit` (общая для вариантов) и в `lib/repositories/{device,pending_call_password}.dart` + `Routers`; экраны `auth_callpassword_confirmation_{cupertino,material}.dart` не менялись — новое поведение целиком в состоянии кубита.
- **Новые зависимости** — не нужны.
- **НЕ делаем в этом этапе**: правки сервера; изменение flow fixedCode/модерации; отдельный UI-индикатор «переподключение» (таймер и подсказка остаются как есть); deep-link возврат из системной звонилки.
