# Чистка хранилища CDN: сироты, аватары групп, сверка бакета

Сервер — `~/GolandProjects/iperon`. Клиент затрагивает только этап 4.

## Откуда план (2026-10-27)

Сверка бакета стенда `iperon-staging-cdn` (Cloud.ru) с коллекцией `cdn`:

- 55 объектов в `chats/` (2,3 ГБ) без записи в `cdn` и одна незавершённая
  загрузка частями. Все от 26.10, 20:55–22:11 UTC — сбой загрузки видео от
  16 МБ: Cloud.ru создавал объект, minio-go принимал ответ за ошибку, сервер
  не писал запись, клиент повторял — 37 копий одного файла по 44 МБ и 17 по
  37 МБ. Удалены вручную; причина устранена в `3b1a7e0` (одиночный PUT).
- Сборщик файлов чатов (`chatMediaGc`) работает: всё, что он удалил, из
  бакета ушло; 62 записи `cdn` ↔ 62 объекта.
- `emoji/` (859 объектов, 64 МБ) — статика Noto, записей в `cdn` у неё нет
  и не должно быть.

Что осталось без присмотра:

1. **Сироты при сбое загрузки.** `RepositoryCDN.UploadEncrypted`
   (`internal/repositories/cdn.go`) кладёт объект под случайным именем и
   только потом пишет запись. Ошибка `PutObject` (при уже созданном
   объекте) или `InsertOne` оставляет объект, о котором никто не знает;
   каждый повтор `UPLOAD_CONFIRM` создаёт ещё один.
2. **Аватары групп не удаляются никогда.** `EditChat` (смена / удаление
   фото, `chats_groups.go`) и `DeleteChat` старый `avatarCdnID` не трогают;
   сборщик смотрит только папку `chats`. Удаляется лишь прежний аватар
   своего профиля (`myprofile.go`, сразу `Delete`).
3. **Брошенные загрузки в `avatars/`.** Загрузили фото, но не поставили
   (отмена, сбой) — в отличие от `chats/` и `secret/` пометки кандидата нет.
4. **Нет сверки бакета с базой** — любой новый сбой снова копит мусор молча.

Файлы секретных чатов (`secret/`) уже покрыты своим сборщиком
(`ServiceSecretChats.CollectFiles`), в план не входят.

## Этап 1. Сначала запись, потом объект

Сервер, небольшой. Порядок в `UploadEncrypted` меняется так, чтобы объекта
без записи не могло появиться: запись создаётся **до** загрузки и уже
помечена кандидатом сборщика, а сбой где угодно дальше оставляет помеченную
запись, которую сборщик уберёт вместе с объектом. Временной папки и
перемещения нет: в S3 это копия + удаление (двойная запись больших файлов,
а у холодного класса — возможная плата за минимальный срок хранения).

Новый порядок:

1. Сгенерировать `cdnID` и имя объекта (как сейчас, случайное), завернуть
   ключ.
2. `InsertOne` записи с `storage`, `fileName`, `folder`, ключами и **`gcFrom`
   = `now + AbandonedAfter - Grace`** (то, что сейчас ставит `Confirm` после
   загрузки, переезжает сюда — `UploadEncrypted` получает срок параметром),
   **`size`** и **`kind`** (см. «Новые поля» ниже). `hashSumEncrypted` и
   `readyAt` пока пустые.
3. `PutObject` на постоянное место.
4. `UpdateOne`: дописать `hashSumEncrypted` и **`readyAt`** = now.
5. Вернуть `cdnID` клиенту.

Новые поля записи `cdn`:

- **`size`** (int64) — размер шифротекста в байтах (`state.fileSize`,
  известен до загрузки). Отчёты «что сколько занимает» и будущие квоты на
  пользователя (`ownerUserId` + `size`) — запросом к Mongo, без бакета.
- **`readyAt`** (date) — когда объект загружен и запись дописана (вместе с
  хэшем). Фильтр выдачи (`GetByID` / `GetByIDs` / файлы секретных чатов)
  проверяет хэш, а не `readyAt`: у старых записей хэш есть, а `readyAt` нет
  до этапа 5. Страховка: в норме `cdnID` недогруженной записи наружу не
  попадает.
- **`kind`** (string) — назначение файла: `media` (вложение сообщения),
  `thumb` (превью фото / обложка видео — отдельный объект, по `contentType`
  от основного не отличить), `avatar` (профиль / группа), `secret` (файл
  секретного чата), `system` (серверные загрузки, `RepositoryCDN.Upload`).
  Для `avatars/` и `secret/` сервер выводит сам из папки / `opaque`;
  `media` / `thumb` в `chats/` указывает клиент — новое поле
  `UploadConfirm.Request.kind` (enum `CdnKind`: `UNSPECIFIED` = 0, `MEDIA`,
  `THUMB`, `AVATAR`) в `protos/upload_confirm_v1.proto`, общем с сервером.
  Старый клиент шлёт `UNSPECIFIED` → для `chats/` пишем `media`.

Метаданные содержимого (исходное имя, разрешение, длительность, геометка) в
`cdn` **не** храним: клиент держит их в зашифрованном содержимом сообщения;
открытая копия на сервере — лишние данные и для запросов по закону Яровой.

Клиент (после сервера): `CDNManager.uploadFile` получает `kind`; превью и
обложки видео шлют `THUMB`, аватары — `AVATAR`, остальное — `MEDIA`.

Почему безопасно:

- Сбой на шагах 3–5 (ошибка S3, ложная ошибка как у Cloud.ru, обрыв, падение
  сервера) — `cdnID` клиент не получил, ссылок на файл нет; через
  `AbandonedAfter` сборщик удалит запись и объект (`RemoveObject`
  несуществующего — не ошибка). Повтор `UPLOAD_CONFIRM` создаёт новую
  запись, старая уходит тем же путём.
- Недогруженная запись наружу не попадает: `cdnID` знает только сервер, пока
  шаг 5 не прошёл. Сборщик не тронет её раньше `AbandonedAfter` (72 ч) —
  загрузка столько не идёт.
- Нормальный путь не меняется: файл ушёл в сообщение — сборщик найдёт ссылку
  и снимет пометку, как сейчас.

Папки:

- Любая папка: на сбое шагов 3–4 сразу удаляем объект и запись
  (`RepositoryCDN.Delete` с отдельным контекстом и таймаутом: исходный мог
  истечь). Не вышло или сервер упал посередине — дальше по папке:
- `chats/`, `secret/` — запись с `gcFrom`, уберёт сборщик.
- `avatars/` — сборщика нет до этапа 2, пометку не ставим; остаток при
  падении посередине — этап 3. После этапа 2 — как `chats/`.
- Серверная загрузка `RepositoryCDN.Upload` (`cdn.go:140`) — тот же порядок.

Тесты (`cdn_test.go`, `upload_test.go`): ошибка S3 → запись с `gcFrom`,
сборщик после срока удаляет её и объект; ошибка дописывания хэша → то же;
успех → запись с хэшем, `size`, `kind`, `readyAt`, после отправки сообщения
пометка снимается; запись без `readyAt` не выдаётся `GetByID`; `avatars` при
ошибке — ни записи, ни объекта; `kind` выводится для `avatars` / `opaque` и
`UNSPECIFIED` → `media`.

## Этап 2. Аватары групп и брошенные аватары

Сервер, средний. Делаем сборщиком с проверкой ссылок, а не мгновенным
удалением: тема (`chats_threads.go:219`) копирует `avatarCdnID` родителя, и
файл может оставаться нужным.

- `EditChat`: при смене / удалении фото старый `avatarCdnID` → `ScheduleGC`.
  `DeleteChat` / `DeleteGroupChat` — то же для аватара чата.
- `Upload.Confirm`: папка `avatars` тоже сразу кандидат (как `chats`,
  `AbandonedAfter - Grace` вперёд). Установка фото пометку не снимает — её
  снимет сборщик, найдя ссылку.
- Сборщик для `avatars`: тот же цикл `ClaimGC` → проверка ссылок → `ClearGC`
  / `Delete`, но ссылки ищутся в `profiles.avatarCdnId` и `chats.avatarCdnId`
  (включая темы). Индексы по этим полям, если их нет. Удобнее обобщить
  `CollectMedia` на папку + функцию «есть ли ссылка», чем копировать цикл.
- Свой профиль: оставить мгновенный `Delete` или перевести на `ScheduleGC`
  ради единообразия — решить при реализации (сейчас работает).
- Разовое заполнение: `ScheduleFolderGC("avatars")` один раз (флаг в
  `serviceState`, как `chatMediaRefsBackfill`): лишние удалятся, нужным
  сборщик снимет пометку.
- Закон Яровой: аватар не содержимое сообщения, `retainedUntil` у него нет —
  удаляем без удержания. Сверить с решениями юриста
  (`docs/` сервера, retention), прежде чем включать на проде.
- Тесты: смена фото группы → старый удалён после grace; фото, на которое
  ссылается тема, не удалён; брошенная загрузка в `avatars` удалена.

## Этап 3. Сверка бакета с базой

Сервер, средний. После этапа 1 — только страховка от редкого (ручные правки
бакета, баги, падение посередине загрузки аватара до этапа 2); можно
отложить.

- Задача `cdnOrphanSweep` в `internal/tasks` с конфигом:
  `enabled` (false по умолчанию), `every` (24h), `minAge` (7 суток),
  `dryRun` (true по умолчанию).
- Проход: для каждого хранилища из `Config.Storages` — `ListObjects` только по
  известным папкам загрузок (`chats/`, `avatars/`, `secret/`; **не** `emoji/`
  и не прочие префиксы); объект старше `minAge` ищется в `cdn` по
  `(storage, fileName)` пачками; нет записи — удалить (в `dryRun` — только
  лог). Итог в лог: найдено / удалено / байт.
- Индекс `cdn` по `fileName` (сейчас его нет — поиск был бы полным
  сканированием).
- `minAge` с запасом больше `upload.ttl` (24h) и времени между `PutObject` и
  `InsertOne`, чтобы не задеть загрузку в процессе.
- Включать на стенде сначала в `dryRun`, сверить лог с ручной проверкой,
  потом снять `dryRun`.

## Этап 4. Клиент: повторы отправки

Клиент, разбор. 26.10 один и тот же файл ушёл на `UPLOAD_CONFIRM` 37 раз за
~75 минут. После этапа 1 это перестанет копить мусор, но трафик и батарея
остаются.

- Проверить, как outbox (`ChatsSync`, `CDNManager.uploadFile`) повторяет
  неудачный `UPLOAD_CONFIRM`: есть ли нарастающая пауза и предел попыток,
  повторяется ли только подтверждение (temp-файл на сервере сохраняется
  именно для этого) или весь файл заново.
- Если пауза постоянная — экспоненциальная с потолком; после N неудач —
  ошибка на сообщении с «Повторить», как у Telegram.

## Этап 5. Новые поля у старых записей

Сервер, небольшой. Разово (флаг в `serviceState`, как
`chatMediaRefsBackfill`) для записей без новых полей:

- `size` — через `StatObject` (можно в проходе этапа 3);
- `readyAt` = `createdAt` (старые записи создавались уже после загрузки);
- `kind`: `avatars` → `avatar`, `secret` / `opaque` → `secret`; `chats` —
  проход по сообщениям, как в `BackfillMediaRefs` (`contentMediaCdnIDs`
  читает содержимое): `cdnID` из `thumbCdnID` вложения → `thumb`, остальные →
  `media`.

## Порядок и проверка

1 → 2 → 4 → 3 (сначала `dryRun`, можно отложить) → 5. Перед коммитами сервера — `go build`,
`go vet`, `go test`, `golangci-lint`; на стенде после каждого этапа — сверка
бакета с `cdn`, как 2026-10-27.
