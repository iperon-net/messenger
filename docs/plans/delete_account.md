# Удаление аккаунта: вручную и по периоду неактивности

Статус: реализация добавлена; фактический worker по умолчанию выключен (`accountDeletion.enabled`). Сервер — `~/GolandProjects/iperon`.

## 1. Цель и принятые решения

Реализовать два самостоятельных сценария:

1. **Ручное удаление** — по явному запросу пользователя, с обязательной задержкой
   **7 дней** и возможностью отмены.
2. **Автоудаление по неактивности** — через **3, 6 или 12 месяцев** без реальной
   активности пользователя. Варианта «Никогда» нет; для всех аккаунтов по умолчанию
   выбрано **12 месяцев**.

Оба сценария используют один идемпотентный серверный `AccountDeletionService`.
Предупреждения и подтверждения приходят в существующий служебный чат «Iperon» на
все устройства. Для запланированного ручного удаления в системном уведомлении есть
кнопка «Отменить удаление», для предупреждения об автоудалении — «Оставить аккаунт».

Ключевые правила:

- ручное удаление нельзя выполнить мгновенно;
- до истечения семи дней аккаунт работает как обычно;
- ручной запрос отменяется только явным действием, а не входом или активностью;
- активность на любом устройстве переносит только срок автоудаления;
- если одновременно существуют оба срока, наступает более ранний;
- после начала фактической очистки отмена невозможна;
- сообщения в обычных чатах остаются у собеседников;
- push и фоновая обработка не считаются активностью.

Задержка ручного удаления защищает владельца, если злоумышленник получил доступ к
разблокированному телефону. Повторная SMS-проверка эту угрозу не решает: код придёт
на тот же телефон. Если установлен облачный пароль, ручной запрос дополнительно
защищается им.

## 2. Пользовательские сценарии

### 2.1. Ручное удаление

1. В настройках аккаунта пользователь выбирает «Удалить аккаунт».
2. Отдельный экран объясняет последствия:
   - аккаунт будет удалён через 7 дней;
   - до этого момента удаление можно отменить;
   - будут удалены профиль, контакты, настройки, облачный пароль, секретные чаты
     и другие личные данные;
   - сообщения в обычных чатах останутся у собеседников;
   - после начала очистки восстановление невозможно.
3. Пользователь подтверждает операцию полным номером телефона. Если включён
   облачный пароль, дополнительно требуется свежая проверка пароля и его
   10-минутный токен.
4. Операция требует сети. Без сети локальная сессия и данные не удаляются,
   показывается явная ошибка.
5. Сервер сохраняет `manualDeleteAfter = now + 7 дней` и отправляет системное
   уведомление всем устройствам, включая инициатора.
6. В настройках и системном чате показываются дата удаления и кнопка отмены.
7. При отмене сервер очищает `manualDeleteAfter`, не меняя настройку и срок
   автоудаления, и рассылает подтверждение «Удаление аккаунта отменено».
8. По истечении срока планировщик атомарно начинает очистку, отзывает все сессии
   и запускает `AccountDeletionService`.

Повторный запрос при уже запланированном ручном удалении не продлевает и не
перезаписывает срок: API возвращает текущее состояние.

### 2.2. Автоудаление по неактивности

1. В разделе «Конфиденциальность» пользователь выбирает период 3, 6 или 12 месяцев.
2. Сервер пересчитывает `autoDeleteAfter` от `lastActivityAt` календарными месяцами.
3. Реальная активность с любого устройства обновляет `lastActivityAt` и переносит
   `autoDeleteAfter`.
4. За 7 дней до срока сервер отправляет в служебный чат предупреждение с датой и
   кнопкой «Оставить аккаунт». Push является дополнительным каналом, а не единственным.
5. Нажатие кнопки или обычное открытие приложения обновляет активность. Сервер
   отправляет подтверждение с новой датой автоудаления.
6. Если активности не было, по наступлении срока запускается общая очистка без
   дополнительной семидневной задержки: период ожидания уже истёк.

## 3. Что считается активностью

Активностью считаются:

- открытие авторизованного приложения на переднем плане;
- возвращение приложения на передний план, если сутки с предыдущего события прошли;
- новый вход в аккаунт;
- действие «Оставить аккаунт» в предупреждении.

Не считаются активностью:

- получение или обработка push-уведомления;
- фоновой запуск iOS NSE / Android push-обработчика;
- автоматическое переподключение стрима в фоне;
- наличие сохранённой сессии;
- фоновая синхронизация без выхода приложения на передний план.

Клиент отправляет отдельную операцию `ACCOUNT_ACTIVITY`; сервер не обновляет дату на
каждый RPC. Запись в Mongo выполняется не чаще одного раза в сутки на пользователя.
Это предотвращает лишнюю нагрузку и не позволяет установленному, но неиспользуемому
приложению бесконечно продлевать аккаунт.

Существующий `lastSeenAt` не переиспользуется: он относится к presence и обновляется
при уходе последней сессии в офлайн. Для удаления нужен отдельный служебный timestamp
с однозначной семантикой.

## 4. Модель данных сервера

В `users` добавить поля:

```text
autoDeletePeriodMonths  int       // только 3, 6 или 12
lastActivityAt          time
autoDeleteAfter         time
autoDeleteWarningFor    time      // срок, для которого уже отправлено предупреждение
manualDeleteAfter       *time     // nil — ручное удаление не запрошено
deletionState           string    // пусто или running
deletionStartedAt       *time
deletionReason          string    // manual или auto
deletionStep            string    // возобновление идемпотентной очистки
```

`deletionState = running` означает, что отмена уже невозможна. Пользовательская запись
сохраняется до завершения очистки, чтобы номер не был повторно зарегистрирован на
полуудалённый аккаунт: индекс `users.phoneNumber` уникальный.

Индексы:

- составной частичный индекс по `manualDeleteAfter` для запланированных ручных удалений;
- индекс по `autoDeleteAfter` для выбора аккаунтов с наступившим сроком и отправки
  предупреждений;
- при необходимости частичный индекс по `deletionState = running` для повторной
  обработки незавершённых задач.

Сроки хранятся в UTC. Месяцы вычисляются через `AddDate(0, months, 0)`, а не как
фиксированные 30/90 дней.

### Миграция существующих пользователей

Чтобы выкатка не удалила старые аккаунты немедленно:

```text
autoDeletePeriodMonths = 12
lastActivityAt = время миграции
autoDeleteAfter = lastActivityAt + 12 календарных месяцев
manualDeleteAfter = nil
deletionState = пусто
```

Не использовать `createdAt` или старый `lastSeenAt` как начальную активность.
Для новых пользователей `lastActivityAt` равно времени регистрации.

## 5. Протокол

Изменения вносить в общие `protos/*.proto` клиента и сервера, затем точечно
перегенерировать обе стороны.

### Настройка автоудаления

В `PrivacySettings_Response` добавить `autoDeletePeriodMonths`. Это позволяет
переиспользовать существующий offline-кэш, `PublishToUser` и синхронизацию между
устройствами.

Добавить:

```text
PRIVACY_AUTO_DELETE_UPDATE
  request:  autoDeletePeriodMonths
  response: обновлённые настройки или пустой ответ + последующий PrivacySettings_Response
```

Сервер принимает только 3, 6 и 12. Нулевое, отрицательное и любое другое значение —
`InvalidArgument`.

### Ручное удаление

Добавить операции:

```text
ACCOUNT_DELETION_REQUEST
  request:  подтверждение номера + cloudPasswordToken, если пароль установлен
  response: manualDeleteAfter, уже запланировано ли удаление

ACCOUNT_DELETION_CANCEL
  request:  пустой
  response: фактически отменено или уже неактивно

ACCOUNT_DELETION_STATUS
  response: manualDeleteAfter, autoDeleteAfter, deletionState
```

Все операции доступны только через зашифрованную авторизованную сессию. Клиент не
передаёт `userID`: сервер берёт его из сессии.

### Активность

Добавить `ACCOUNT_ACTIVITY` без пользовательских аргументов. Сервер обновляет дату с
учётом суточного throttling и сбрасывает `autoDeleteWarningFor`, если срок перенесён.
Операция не трогает `manualDeleteAfter`.

### Системные уведомления

Расширить `MessageSystemNotice.Kind`:

```text
ACCOUNT_DELETION_SCHEDULED
ACCOUNT_DELETION_CANCELLED
ACCOUNT_AUTO_DELETE_WARNING
ACCOUNT_AUTO_DELETE_EXTENDED
```

В `MessageSystemNotice` добавить `deletionAfter`. Текст и кнопки клиент строит через
slang; сервер не присылает готовую локализованную строку.

Кнопки используют существующий механизм `MessageBubble.actions` /
`ChatMessagesView.actionsFor` и `system_notice_common.dart`:

- «Отменить удаление» → `ACCOUNT_DELETION_CANCEL`;
- «Оставить аккаунт» → `ACCOUNT_ACTIVITY`.

Системный чат остаётся read-only: кнопка вызывает отдельный API, а не отправляет
команду сообщением. Доступность действия определяет сервер. Старое уведомление после
отмены, переноса срока или начала очистки не даёт выполнить операцию повторно; клиент
показывает актуальное состояние без ошибки.

Для новых видов добавить `SYSTEM_NOTICE` push с локализуемыми `args`. Уведомление о
ручном запросе рассылается всем сессиям без `ExceptSessionID`.

## 6. Планировщик и состояния

В `internal/tasks` добавить периодическую задачу `AccountDeletion` с ограниченными
пачками, таймаутом прохода и существующим `Tasks.track`. Часовой запуск подходит и
для ручного срока, и для предупреждений; сутки удаления не требуют отдельной задачи.

Каждый проход:

1. Выбрать аккаунты с `manualDeleteAfter <= now` или `autoDeleteAfter <= now`.
2. Выбрать аккаунты, до `autoDeleteAfter` которых осталось не более 7 дней и для
   которых предупреждение ещё не отправлено.
3. Выбрать незавершённые `deletionState = running` после сбоя или перезапуска.
4. Атомарно захватить каждый срок через условное `FindOneAndUpdate`:
   - документ всё ещё имеет тот же срок;
   - `deletionState` ещё пуст;
   - в ответ установить `running`, причину и `deletionStartedAt`.
5. Отправить уведомления только после успешной атомарной пометки предупреждения,
   чтобы несколько инстансов не создали дубли.
6. Вызвать `AccountDeletionService` для захваченных аккаунтов.

Гонки разрешаются на сервере:

- если активность записана до захвата, `autoDeleteAfter` меняется и условный захват
  не срабатывает;
- если планировщик захватил аккаунт первым, последующая активность не отменяет очистку;
- отмена ручного удаления успешна только пока `deletionState` пуст и совпадает
  исходный `manualDeleteAfter`;
- авторизованные запросы и вход отклоняются для `deletionState = running`.

Очистка должна возобновляться после рестарта сервера. Ошибки не очищают `running` и
не переводят аккаунт обратно в обычное состояние.

## 7. AccountDeletionService

Сервис выполняет долгую очистку асинхронно относительно scheduler tick. Все шаги
идемпотентны и безопасны при повторном запуске.

Порядок:

1. Отозвать все сессии, QR-авторизации, passkeys и push-токены; отправить `LOGOUT`
   устройствам через существующий механизм.
2. Закрыть активные звонки и исключить пользователя из presence / typing / других
   эфемерных Redis-состояний.
3. Удалить секретные чаты, их конверты и связанные медиа через механизмы secret chats.
4. Исключить пользователя из обычных групп и каналов. Его сообщения не удалять.
5. Разрешить владение группами и каналами:
   - сначала передать владение старейшему другому администратору;
   - если администраторов нет — старейшему другому участнику;
   - если других участников нет — удалить пустой групповой чат или канал.
6. Удалить личные чатовые настройки, черновики, закрепы, папки, реакции и другие
   принадлежащие только пользователю записи, не затрагивая чужие копии сообщений.
7. Удалить профиль, username и его индекс, аватар, контакты, настройки приватности и
   уведомлений, privacy allow/deny-списки, blocked, email и OPAQUE cloud-password
   запись.
8. Удалить passkeys, WebAuthn credentials, discovery/OPRF-данные и остальные записи,
   связанные с `userID`, по явному инвентарю коллекций.
9. Удалить принадлежащие пользователю медиа только если на них нет ссылок из
   сохранённых сообщений других пользователей. Использовать существующие CDN/GC
   механизмы; не удалять файл только по `ownerUserId`.
10. Удалить документ `users` последним. После этого номер доступен для новой
    регистрации, а повторный worker завершается как no-op по сохранённому deletion job.

Для надёжного возобновления после удаления `users` задача удаления должна иметь
отдельную durable-запись `accountDeletionJobs` с `userID`, причиной, текущим шагом,
числом попыток и сроками. Она создаётся при захвате аккаунта и не зависит от
существования пользовательского документа.

Обычные сообщения остаются у собеседников. При отсутствии профиля клиенты показывают
«Удалённый аккаунт», без подмены незагруженного профиля временным дефолтом при
обычной сетевой ошибке.

Данные обязательного retention и резервные копии не редактируются точечно этим
сервисом: их срок хранения определяется существующими legal/backup-политиками. В UI не
обещать мгновенное физическое удаление таких копий.

## 8. Клиент

### Настройки и состояние

В `SettingsPrivacyAndSecurityCubit` добавить выбранный период и чтение/запись через
существующий BLOB `PrivacySettings_Response`. При `_persistFromState` обязательно
сохранять `blocked` и все неизменённые поля.

В «Конфиденциальность» добавить пункт «Удалить аккаунт, если я не захожу» и отдельный
экран выбора 3 / 6 / 12 месяцев. Пояснение:

> Если вы не будете заходить в Iperon в течение выбранного периода, аккаунт и его
> личные данные будут удалены. Сообщения останутся у собеседников.

Offline поведение:

- последний известный период и статус удаления показываются из SQLite;
- изменение периода, запрос и отмена удаления требуют сети;
- без сети не выполняется оптимистичный emit; iOS показывает Cupertino dialog,
  Material — SnackBar.

Ручное удаление разместить в настройках профиля рядом с другими действиями аккаунта,
но визуально отделить от обычного выхода. После принятия запроса показывать в настройках
дату и кнопку отмены; локальный logout до фактического удаления не выполнять.

### UI

Добавить Cupertino и Material-варианты:

- экран выбора периода автоудаления;
- экран подтверждения ручного удаления;
- блок запланированного удаления с датой и отменой;
- тексты и действия новых системных уведомлений;
- отображение «Удалённый аккаунт» вместо удалённого профиля.

Общую логику держать в `*_common.dart`, новые экраны добавить в обе ветки роутера.
Для full-screen push routes использовать `pageBuilder` и существующие `_page` /
`_pageMaterial`. Все строки добавить в `en.i18n.yaml` и `ru.i18n.yaml`, затем запустить
slang. Состояния, меняющиеся через `@MappableClass()`, перегенерировать build_runner.

### Активность и локальная очистка

Отправку `ACCOUNT_ACTIVITY` подключить к существующему foreground lifecycle авторизованного
приложения. Не вызывать её из push-кода и фоновых изолятов.

Когда сервер начинает удаление, другие устройства получают `LOGOUT` и проходят
существующий `Auth.logout()`. Локальные SQLite и account-scoped файлы очищаются через
существующие `Sessions.deleteActive`, `afterLogout` и `AccountScope`; не обращаться
напрямую к общему application support в обход account scope. При наличии других
аккаунтов сохранить переключение на соседний слот.

## 9. Наблюдаемость и эксплуатация

Добавить метрики:

- запрошено / отменено ручных удалений;
- отправлено предупреждений об автоудалении;
- запущено и завершено удалений по причинам `manual` / `auto`;
- количество активных `deletionState = running`;
- ошибки и повторные попытки по шагам;
- длительность полной очистки и размер обработанной пачки.

Логи содержат `userID`, job ID, причину, шаг и `request_id`, но не телефон, email,
облачный пароль, токены или содержимое сообщений.

Для аварийной остановки предусмотреть серверный feature flag планировщика. Он должен
останавливать новые захваты, но не делать уже удалённые данные доступными. В админке
полезно видеть статус deletion job и ошибку шага; повторный запуск должен быть
идемпотентным.

Выкатка:

1. Сначала proto и серверная модель с миграцией, без включения scheduler.
2. Затем клиентская настройка, activity, системные уведомления и ручной запрос.
3. После проверки миграции включить предупреждения.
4. После проверки deletion worker на тестовых аккаунтах включить фактическое удаление.

Старые клиенты должны безопасно игнорировать неизвестные поля настроек. До выпуска
клиента с поддержкой новых `MessageSystemNotice.Kind` не включать соответствующие
уведомления, иначе старые сборки увидят пустое служебное сообщение.

## 10. Тестирование

### Сервер

Unit и repository/service-тесты:

- принимаются только периоды 3, 6 и 12; остальные отклоняются;
- календарный пересчёт срока, включая конец месяца и високосный год;
- миграция существующих пользователей не создаёт немедленно просроченные сроки;
- активность на любом устройстве переносит только `autoDeleteAfter`;
- throttling не пишет в Mongo чаще суток;
- фоновые события не вызывают activity;
- ручной запрос требует свежий cloud-password token, если пароль включён;
- повторный ручной запрос не перезаписывает срок;
- ручная отмена не меняет период и срок автоудаления;
- обычная активность не отменяет ручное удаление;
- более ранний из двух сроков запускает очистку;
- предупреждение отправляется один раз на конкретный срок;
- гонки activity / cancel / scheduler разрешаются атомарно;
- после `deletionState = running` вход и отмена запрещены;
- worker идемпотентен и возобновляется после сбоя на каждом шаге;
- сообщения других участников и используемые ими медиа сохраняются;
- владение группами передаётся по правилам, пустые группы удаляются;
- номер нельзя зарегистрировать повторно до завершения очистки.

### Клиент

- период читается из кэша offline и синхронизируется между устройствами;
- изменение без сети не делает оптимистичный emit и показывает платформенную ошибку;
- ручной запрос и отмена работают только онлайн;
- `_persistFromState` сохраняет `blocked`;
- системные кнопки вызывают правильные API и корректно обрабатывают устаревший срок;
- activity отправляется только на переднем плане и не чаще нужного интервала;
- `LOGOUT` очищает текущий слот и сохраняет остальные аккаунты;
- обе UI-вариации и обе локали отображают одинаковые сценарии.

### End-to-end

На тестовых аккаунтах с управляемыми часами, без реального ожидания месяцев:

1. Запросить удаление, получить уведомление на втором устройстве и отменить его там.
2. Дождаться наступления ручного срока и проверить logout всех устройств, очистку и
   возможность зарегистрировать номер заново только после завершения.
3. Проверить предупреждение об автоудалении, «Оставить аккаунт» и перенос срока.
4. Проверить автоматическое удаление неактивного аккаунта.
5. Проверить сохранение сообщений у собеседника и корректное отображение удалённого
   профиля.

## 11. Этапы реализации

1. **Протокол и модель** — поля, индексы, миграция, API настройки и статуса, тесты.
2. **Активность** — `ACCOUNT_ACTIVITY`, foreground lifecycle, throttling, пересчёт сроков.
3. **Системные уведомления** — новые виды, кнопки, пуши, RU/EN и синхронизация устройств.
4. **Ручной запрос и отмена** — UI, cloud-password проверка, семидневный срок.
5. **AccountDeletionService** — durable jobs, отзыв сессий, инвентарь и очистка данных,
   правила чатов и CDN, идемпотентность.
6. **Планировщик** — предупреждения, захват сроков, возобновление jobs, метрики и flag.
7. **Проверка и выкатка** — полный набор тестов, E2E, поэтапное включение.
