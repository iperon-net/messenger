# Feature plans

Long-lived plans for features and stages live here, one file per feature.

Conventions:

- A new plan is created only by copying `TEMPLATE.md` (section set and
  order are fixed; instructional comments are removed). New plans are
  named `<nn>-<feature>.md` (`01-secret-chat-ui.md`, …), `nn` — the next
  number after the last numbered plan here.
- A plan is written before implementation starts and updated as decisions
  are made during the work (checked-off items, resolved questions).
- Plans are written in Russian.
- Each plan records: goal, agreed decisions (with alternatives rejected),
  step list, open questions.
- While drafting a plan the agent collects open questions and asks them
  to the user (`AskUserQuestion`), not one by one ad hoc: answers are
  recorded in «Принятые решения» and the questions are struck through as
  resolved (~~question~~ «решено: <answer>»).
- Questions affecting this stage's implementation must be closed BEFORE
  the first code step — a plan with unresolved blocking questions does
  not move to implementation. Before starting (and resuming) code work on
  a plan, re-read its «Открытые вопросы» section and ask whatever is
  still unresolved. Only questions explicitly deferred to a future plan
  may stay open; each such item is marked «не блокирует» with the reason
  for deferral.
- Status line at the top: `draft` / `in progress` / `done`.
- `INDEX.md` is the plan index (plan, status, one-line goal), generated by
  `scripts/gen-plan-index.sh`. Regenerate it before every docs commit that
  touches plans — never edit `INDEX.md` by hand.
- After each executed step, record the commit hash next to the step item:
  `- [x] 1. ... (commit a1b2c3d)`. The plan then doubles as a
  changelog for the feature — handy when tracing regressions later.
  Mechanics: the hash of a commit can't be inside that same commit, so hash
  updates go into a follow-up docs commit (`docs: update plan ... with
  commit hashes`). Batching is fine — record hashes of several steps in one
  docs commit at the end of a work session.

Legacy plans: the old-format plans (descriptive names, pre-template) live in
`archive/` — kept for history as provenance for code comments: code comments
across this repo and the server repo reference them by their old
`docs/plans/<name>.md` paths, and that is fine. They are not maintained and
not indexed; never rename them. The template applies to new plans only.

## Testing

Every plan has a "Тестирование" section listing what must be verified
before the feature is done.

- Whatever the agent can test itself (unit tests, `flutter analyze`,
  `flutter test`, scenarios on emulators/simulators, the server's
  `cmd/testpeer` as the "second phone"), it tests and reports the
  result — no asking the user for things that can be checked
  automatically.
- What the agent cannot verify (visual/UX acceptance on devices, business
  judgment), it hands to the user as an explicit checklist item and waits
  for the user's verdict.
- Checkbox notation (testing section only — plan steps keep plain `[x]`/`[ ]`):
  - `[🤖]` — agent tested it itself, passed;
  - `[✅]` — the user tested it and confirmed it works.
  An unchecked item (`[ ]`) means not verified by anyone yet. A failed check
  is never marked — it stays `[ ]` with a note of what failed.
  `scripts/check-plans.sh` mechanically enforces that every `[✅]` carries
  a confirmation date.
