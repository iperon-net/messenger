# 01-contacts-loading — диагностика и ускорение загрузки контактов

**Статус:** in progress (с 2026-11-13)

## Цель

Разобраться, почему вкладка «Контакты» долго подгружается, и устранить самые
тяжёлые задержки. Проблемный случай зафиксирован: адресная книга **6000+
контактов** — на Android приложение перестаёт отвечать (ANR «Приложение
Iperon не отвечает», скриншот от 2026-11-13). Список должен появляться
мгновенно из локального кэша, обработка книги не должна блокировать
UI-isolate, имена и аватарки — дозагружаться без поштучных запросов. Состав
мер уточняется по замерам первого шага, а не по догадкам.

## Принятые решения

- **Связанный план:** [docs/plans/archive/cloud-contacts-sync.md](archive/cloud-contacts-sync.md)
  — старый план, из которого взята текущая архитектура контактов: две дорожки
  (книжные — локально через OPRF, облачные — server-truth `CONTACTS_LIST` /
  `CONTACTS_UPDATED`), снимок в таблице `contacts` с `isCloud`/`oprf`
  (миграция 4), лимит облачных 5000 без пагинации. Этот план его не меняет —
  только ускоряет клиентскую сторону поверх готовой архитектуры.
- **Симптом зафиксирован: ANR на Android с книгой 6000+ контактов.** Это
  блокировка UI-isolate синхронной работой, а не «медленная сеть». Главные
  подозреваемые: цикл `phoneNormalization` по каждому телефону каждого из
  6000 контактов в UI-isolate (`contacts_cubit.dart:512-529`), десериализация
  `FlutterContacts.getAll` на main isolate (`contacts_cubit.dart:502`),
  построение всех плиток списка без виртуализации, полный `_emitAll`
  (сортировка и копия трёх списков на 6000 записей) и лавина поштучных
  БД-запросов аватаров. Альтернатива отклонена: лечить только сетевой
  пайплайнинг OPRF — ANR не сетевая проблема.
- **План начинается с инструментирования и замеров.** Симптом известен, но
  сначала измеряем фазы (bootstrap → preload → fetchCloud → discover по
  фазам: доступ, `getAll`, нормализация, `replaceBook`, OPRF-батчи,
  аватарочные PROFILE-запросы), цифры фиксируем в плане, приоритеты
  последующих шагов — по цифрам. Альтернатива отклонена: сразу править
  «подозреваемых» без данных.
- **Scope — только клиент.** Сервер (`~/GolandProjects/iperon`) не трогаем;
  если замеры укажут на медленные серверные обработчики
  (contacts discovery/list) — отдельное решение. Альтернатива отклонена:
  менять сервер/протокол без измерений.
- **Список всегда показывается из кэша мгновенно.** Сейчас `preload()`
  (`lib/cubit/contacts/contacts_cubit.dart:346`) при пустой таблице `contacts`
  возвращается, не эмитя success, и экран держит спиннер до конца всего
  discovery (доступ к адресной книге + чтение книги + последовательные
  OPRF-батчи, 3 unary RTT на 512 телефонов: `contacts_cubit.dart:981-1020`).
  Делаем: кэш показываем сразу (в т.ч. пустое состояние с неблокирующим
  прогрессом discovery), тяжёлые фазы — фоном.
- **Вся обработка книги уходит из UI-isolate.** Чтение `FlutterContacts.getAll`
  (десериализация на main isolate), нормализация/дедуп по e164, сборка входов и
  снимка — в `Isolate.run`; результат в кубит — готовыми структурами. Эмиссия
  состояния чанками (первый кадр — по первым записям), а не один `_emitAll`
  поверх 6000 записей. Альтернатива отклонена: «ускорить нормализацию» —
  даже быстрый цикл на 20–30 тыс. телефонов останется блокирующим.
- **Виртуализация списка + батч-подгрузка имён/аватарок.** Сейчас оба экрана
  строят все плитки сразу (`children:` без builder), каждая плитка делает
  свой SQL-запрос аватара (`lib/components/user_avatar.dart:142`) и на промахе
  — поштучный PROFILE-запрос с CDN-скачиванием (`user_avatar.dart:205-235`).
  Альтернатива отклонена: оставить как есть и «просто ускорить запросы» —
  N поштучных запросов на первый кадр останутся. **Уточнение по итогам
  шага 4:** полноценный batch-`getByUserIDs` на кадр не понадобился — после
  виртуализации поштучный SQL остаётся только у видимых зарегистрированных
  строк (у приглашаемых `userID == null`, SQL не нужен вовсе), а повторные
  чтения при пересоздании строк при прокрутке отсечены памятью сессии в
  `UserAvatar` (картинка уже показана → SQL пропускается; смена аватара
  приходит по `avatarChanges` с форсированной перезагрузкой). Отклонено как
  излишнее: отдельный координатор батч-подгрузки усложняет общий компонент
  `UserAvatar` (используется звонками/чатами) ради экономии ~десятка
  индексированных запросов на экран на фоновом изоляте БД.
- **Дешёвые оптимизации БД/RPC:** индекс на `contacts.userID` (миграция 54 —
  таблица создана в миграции 2, `userID` не индексирован, запросы
  `WHERE userID = ?` — full scan: `lib/repositories/repositories.dart:296-339`,
  `lib/repositories/contacts.dart:62,85,99`); батч-запись last-seen одной
  транзакцией вместо поштучных UPDATE на каждый оффлайн-контакт
  (`contacts_cubit.dart:322-330`); gRPC-дедлайн на unary-вызовы (сейчас
  только channel `connectionTimeout: 30s`, `lib/api.dart:1048-1081`) — без
  дедлайна зависший RPC молча продлевает «загрузку»; не переписывать
  `replaceBook` (DELETE + N INSERT), если fingerprint книги не изменился.
- **Полное перечитывание адресной книги не убираем, но ограничиваем
  последствия:** нативное `FlutterContacts.getAll` (`contacts_cubit.dart:502`)
  выполняется на каждый discover (первое открытие вкладки, resume, debounced
  изменение книги) — обойти его без OS-level change-tracking нельзя, но можно
  не переписывать таблицу и не пересортировывать состояние, если ничего не
  изменилось.
- **OPRF-пайплайнинг (параллельные батчи) отложен** — см. «Открытые вопросы»:
  он кратно увеличивает параллельную нагрузку на сервер и меняет порядок
  `full`-батча в `_upsertGraph`; делать только если замеры покажут, что фаза
  доминирует, и с согласия пользователя.
- **Что НЕ делаем в этом этапе:** пагинация CONTACTS_LIST (серверный лимит
  5000, `docs/plans/archive/cloud-contacts-sync.md`), изменения протокола и
  MessageType, OS-level change-tracking адресной книги, правки `ChatsSync`,
  новые pub-зависимости.
- **Клиентская специфика:** слои repository → cubit → экраны; миграция 54
  добавляется следующей `SqliteMigration` в
  `lib/repositories/repositories.dart` (существующие не редактируются);
  Cupertino- и Material-варианты экранов меняются синхронно, общая логика — в
  кубите; существующий мёртвый `refresh()` (`contacts_cubit.dart:630-632`)
  оживляем как pull-to-refresh на обоих экранах (нужен и для замеров —
  форсировать re-discover без переустановки приложения).

## Шаги

- [x] 1. Инструментирование и замеры: тайминги `bootstrap`/`preload`/
  `_fetchCloud`/`discover` по фазам (запрос доступа, `FlutterContacts.getAll`,
  нормализация телефонов, `replaceBook`, каждый OPRF-батч:
  evaluate/match/upsert), счётчик поштучных PROFILE-запросов аватарок и
  SQL-запросов аватаров на первый кадр; pull-to-refresh через оживлённый
  `refresh()`. Прогон на устройстве с книгой 6000+ контактов, цифры фаз —
  вписать в план. (commit 8a144af)

  **Цифры замеров (эмулятор Pixel 9a / Android 16, debug-сборка, staging,
  книга 6000 контактов × 1 телефон, 2026-11-13):**
  - Cold start (кэш пуст): `bootstrap.total=18594ms` — preload 222ms (кэш
    пуст) → `getAll=1056ms` → **`normalize=5584ms`** (6000 телефонов в
    UI-isolate — блокировка UI выше порога ANR Android ~5s) → replaceBook
    4720ms → **OPRF 4602ms** (12 последовательных батчей по ~380–450ms:
    blind 40–230ms + evaluate 110–400ms + match 30–140ms + upsert 34–128ms).
  - Warm start (fingerprint совпал, OPRF пропущен): `bootstrap.total=12541ms`
    — dbGetAll 958ms (rows=6000) → **`normalize=4615ms`** → **replaceBook
    4658ms — перезапись НЕизменённой книги** (DELETE + 6000 INSERT) →
    fingerprintCheck 4ms → skip OPRF.
  - Pull-to-refresh (force, полный проход): getAll 3648ms + normalize 4575ms +
    replaceBook 3154ms + OPRF 4972ms ≈ 20s.
  - `emitAll` на 6000 записей: 10–165ms за emit — терпимо, но вызывается на
    каждый presence-push.
  - Подтверждено воспроизведение фриза пользователя: первый рендер вкладки с
    6000 записями (все плитки строятся в один кадр: `SliverList.list` +
    6000 анимированных аватарок) давал чёрный экран на минуты при живом
    сетевом стриме; после перезапуска вкладка отрисовалась.
  - Вывод: доминанты — синхронная нормализация на UI-isolate (каждый запуск
    приложения!), бессмысленная перезапись неизменённой книги и полный
    материализованный список; OPRF — вторичен и уже корректно скипается по
    fingerprint.
- [x] 2. Обработка книги вне UI-isolate (устранение ANR): нормализация,
  дедуп по e164, сборка `_Entry`/снимка и fingerprint — в `Isolate.run`;
  эмиссия состояния чанками (первый кадр по первым записям, дальше дозагрузка)
  вместо одного полного `_emitAll` на 6000 записей.

  **Результат (эмулятор, та же книга 6000, 2026-11-13):**
  - `discover.normalize=4399ms … (isolate)` — нормализация ушла из
    UI-isolate (было 4.6–5.6 с синхронного блока — прямая причина ANR);
    `discover.getAll=1049ms` — чтение книги тоже в фоновом изоляте через
    `BackgroundIsolateBinaryMessenger`.
  - Чанковая эмиссия: `reveal=653–1445ms chunks=12`, все `emitAll` ≤ 80 мс
    (до шага — единичные пики 3–5 с при полной пересборке); первый кадр
    списка появляется после первого чанка (500 записей).
  - Warm `bootstrap.total=10790ms` (было 12541ms) — но принципиально: все
    тяжёлые фазы (getAll, normalize, replaceBook) теперь вне UI-isolate,
    синхронная работа UI — emitAll ≤ 80 мс и bookBuild 1 мс.
  - Найдено и отработано: замыкание для `Isolate.run`, созданное в методе
    кубита, захватило общий контекст скоупа с `this` (его тянут соседние
    замыкания `_measure` с `repositories.users`) → «object is unsendable»
    на весь граф приложения. Решение — top-level функции
    `_readBookInIsolate`/`_normalizeBookInIsolate`: их замыкания создаются
    без контекста кубита.
  - Попутно: `Utils.normalizePhone` вынесен в статичный чистый
    `Utils.normalizePhone` (dlibphonenumber — чистый Dart, работает в любом
    изоляте), инстансный метод делегирует; юнит-тесты, включая прогон в
    свежем изоляте.
  - Замечено вне шага (для шагов 4–5): при прогреве на загруженной системе
    постройка плиток IndexedStack на каждый emit доходила до 3 с на чанк —
    окончательно лечится виртуализацией списка (шаг 4). (commit ecec6af)
- [x] 3. Мгновенный показ кэша: при пустой таблице `preload` эмитит состояние
  с прогрессом discovery (не молчание); экраны показывают список/скелетон
  сразу, спиннер — только пока нет вообще никаких данных и не идёт discovery;
  при горячем кэше список сразу, обновления фоном без пересортировки видимого
  состояния на каждый push.

  **Результат (эмулятор, cold start с пустым кэшем через `pm clear` + логин,
  2026-11-13):** e2e прошёл полностью — пустой кэш → баннер доступа (не
  блокирует) → выдача разрешения → экран показывает «Ищем контакты в
  телефонной книге…» с индикатором во время discovery (вместо бывшего
  бесконечного голого спиннера) → список отрисован чанками по мере готовности
  (счётчики аватаров: tiles 2000 → 4500 → 6000 вместе с чанками reveal).
  Механика: `ContactsState.discovering` (зеркалится из `discover()`, снимается
  в finally); пустой `preload` эмитит `Status.loading`; presence-push
  применяется с дебаунсом 300 мс (пересортировка/показ раз за окно, а не на
  каждый item); i18n `screenContacts.searchingBook` (en/ru). Замечено для
  шага 5: на холодном прогоне нагруженного эмулятора `replaceBook=22813ms`
  (фоновая БД, UI не блокирует, но лишняя работа — skip-rewrite по
  fingerprint уже закрывает большую часть). (commit ecec6af)
- [x] 4. Виртуализация списков на обоих экранах (builder вместо `children:`)
  и батч-подгрузка имён/аватарок: один `getByUserIDs` на кадр, PROFILE-запросы
  только для недостающих видимых пользователей, без поштучного SQL в каждой
  плитке.

  **Результат (эмулятор, книга 6000, 2026-11-13):** оба экрана переведены на
  `searchListView(itemCount/itemBuilder)` — плоская индексная раскладка
  (секция = заголовок + плитки, затем поиск людей и пустое состояние); в
  Cupertino фон «листа» и дивидеры рисуются по индексу строки. `UserAvatar`:
  SQL пропускается, когда картинка уже показана из памяти сессии;
  `avatarChanges` форсирует полную перезагрузку. Проверка прокруткой: 8
  флингов вглубь (Perf0957+) и обратно к началу — **0 кадров дольше 700 мс**
  (Davey-логи пусты), строки и аватарки-плейсхолдеры корректны. Батч-
  `getByUserIDs` не понадобился (см. уточнение в «Принятых решениях»):
  поштучный SQL остался только у видимых зарегистрированных строк без
  картинки в памяти. (commit 0e90e3e)
- [x] 5. БД/RPC-оптимизации: миграция 54 — индекс `contacts(userID)`; батч-
  запись last-seen одной транзакцией; gRPC-дедлайн на unary-вызовы; пропуск
  rewrite `replaceBook` при неизменном fingerprint книги.

  **Результат (эмулятор, книга 6000, warm-старт, 2026-11-13):**
  - Skip-rewrite работает: в логах warm-старта `replaceBook` отсутствует
    («fingerprint unchanged, skipping replaceBook and OPRF»), нет и OPRF —
    `bootstrap.total=8578ms` (было 10790ms со skip-OPRF и rewrite 2.8s; все
    тяжёлые фазы по-прежнему вне UI-isolate). Компромисс: имена из
    системной книги в БД обновляются на ближайшем полном проходе (TTL 24 ч
    или pull-to-refresh) — показ в памяти всегда свежий.
  - Миграция 54 (`CREATE INDEX contacts_userID`) прошла на обновлённой БД,
    контакты на месте; запросы «контакт по userID» (имена в звонках/чатах,
    профили) перестали сканировать таблицу.
  - last-seen пачки PRESENCE пишется одной транзакцией
    (`Profiles.updateLastSeenBatch`), юнит-тест ассертит батч.
  - Unary-вызовы (`unaryEncoded`/`unaryEncodedAs`/`unaryEncodedWithResponse`)
    ходят с дедлайном 30 с (`CallOptions.timeout`) — зависший RPC больше не
    висит неопределённо и не продлевает «загрузку» молча; истечение даёт
    DEADLINE_EXCEEDED, обрабатываемый существующими офлайн-ветками.
    (commit 0a5d624)
- [ ] 6. Прекоммиты (`dart format lib`, `flutter analyze`, `flutter test`),
  регенерация `INDEX.md` (`scripts/gen-plan-index.sh`) перед docs-коммитами.

## Открытые вопросы

- ~~Какой симптом доминирует (спиннер при первом открытии / дозагрузка имён и
  аватарок / тормозит каждый раз)?~~ — **решено:** адресная книга 6000+
  контактов, Android, ANR «Приложение не отвечает» (скриншот от 2026-11-13);
  распределение времени по фазам всё равно снимаем на шаге 1.
- ~~**Тестовая база:** сколько контактов в адресной книге тестового
  устройства?~~ — **решено:** воспроизводится на книге пользователя 6000+
  контактов (Android); для эмулятора контакты нагенерируем.
- **Пайплайнить ли OPRF-батчи** (параллельные evaluate/match/upsert вместо
  строгой последовательности)? — **не блокирует**: отложено до цифр шага 1;
  если фаза доминирует — отдельный шаг после явного согласия пользователя
  (кратная нагрузка на сервер, порядок full-батча в `_upsertGraph`).
