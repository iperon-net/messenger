# Срез 3. Группы на сервере

План 2026-10-19. Это развёрнутый «Срез 3» из `chats-groups-channels.md`. Решения по UX,
ролям, способам вступления и правам там уже приняты и в этом файле не повторяются (разделы
«Приватность групп», «Реакции», «Отметки о прочтении», «Антиспам»). Здесь описано, как
перенести готовое демо на сервер.

## Что уже есть

**Клиент.** UX групп готов целиком, но работает только на демо-данных.
- Интерфейс `ChatsDataSource` содержит все методы для групп: создание и правка, вступление,
  ссылки, заявки, участники и их страницы, баны, админы и права, передача владения, реакции
  группы, медленный режим, опросы, `readInfo`.
- Модели готовы: `ChatRole`, `ChatJoinMode`, `ChatAdminRights` (с `covers`), `ChatMember`,
  `ChatInviteLink`, `ChatJoinRequest`, а у `Chat` есть все групповые поля.
- Экраны и cubit'ы (`chat_info_*`, `chat_admins_*`, `chat_banned_*`, `chat_invite_*`,
  `chat_join_requests_*`, `chat_create_*`) работают только через интерфейс. Подмена источника
  данных не требует менять экраны.
- В `ChatsRemoteDataSource` групповые методы бросают `_unsupported()` или возвращают пустое.
  `_loadChats` отбрасывает всё, что не `CHAT_TYPE_PRIVATE`.
- У модели `Message` нет `fromUserID`, есть только `senderName`. Имя отправителя сейчас
  подставляется из одного `peerName`.
- В SQLite (последняя миграция — 34) нет ничего группового, кроме `chatDialogs.type` и
  `chatMessages.fromUserID`.
- В `ChatsFeatures` всего 4 флага, и ни один не относится к группам.

**Сервер.** Групп почти нет.
- Есть `ChatTypeGroup` в `models/chats.go` и в `ChatType` proto, есть `NotifyScopeGroups`, а
  флаги папок `includeGroups` уже работают.
- Членство — это массив `chats.userIds`. В `chatMembers` нет ни роли, ни прав, ни даты
  вступления.
- `chat.Peer()` (ровно два участника) зашит в `ReadHistory`, `notifyMessage`, `canWrite`,
  `ReadDate`, `dialogToProto`, `Send(peerUserID)`, TTL, no-forwards, `peerHex()` закона Яровой
  и в архив истории (`archiveReadUpTo` — цикл N×N).
- Журнал `updates` ведётся на пользователя. `deliver` / edit / delete / реакции пишут запись
  каждому участнику, то есть O(участников) на каждое событие.
- JetStream-стрим `syncer` (`chat.*`, `group.*`) создан, но им никто не пользуется.
- Упоминаний нет нигде: ни в proto, ни на сервере, ни в пушах. В `PushPayload` нет названия чата.
- Реакции и закрепы уже лежат в отдельных коллекциях `chatReactions` / `chatPins` (`dda4f2a`).

## Главное решение: журнал на чат

Для групп заводим **свой pts на чат**, как у супергрупп Telegram и как будет у наших каналов.
Копировать обновление в журнал каждого участника не будем: при 200 000 участниках это 200 000
записей на одно сообщение. Тот же механизм в срезе 4 переиспользуется для каналов.

| Что | Куда |
|---|---|
| Новое / правка / удаление сообщения, реакции, закрепы «для всех», опросы, сервисные сообщения, смена информации и настроек группы, изменения участников (роль, бан, админ) | журнал **чата** `chatUpdates {chatId, pts, …}` (TTL 7 дней, как `updates`) |
| Моё состояние диалога: прочитано, заглушить, закреп в списке, архив, черновик, папки. Я вступил / вышел / меня исключили / сменили мою роль | журнал **пользователя** (как сейчас) |

**Живая доставка.** Используем NATS subject `chat.<hex>`. Стрим-сессия при подключении
подписывается на все мои группы (их ≤ 500, см. «Лимиты») и меняет подписку, когда я вступаю
или выхожу. Сообщение публикуется **один раз** в subject чата. Онлайн-участники получают его,
офлайн-участников это никак не нагружает. Небольшие группы идут по тому же пути, отдельной
ветки для них нет.

**Догон после офлайна.**
1. `GET_DIFFERENCE` по журналу пользователя работает как сейчас.
2. Новый запрос `Chats.GetChatsState {[(chatID, pts)]}` отправляет пачкой мои группы с
   локальным pts. Сервер возвращает те, где `chats.pts` больше: верхнее сообщение, счётчики и
   новый pts.
3. Для каждой изменённой группы запускается `Messages.GetChatDifference {chatID, pts, limit}`
   (аналог `getChannelDifference`). Для первых N диалогов списка он идёт сразу, для остальных —
   при открытии чата. `tooLong` означает перезагрузить верх истории этого чата.

**Дешёвый список диалогов.** При новом сообщении документ `chatMembers` каждого участника не
трогаем. Верх диалога (`topMessageId` / `topDate`) хранится в `chats`. `Chats.List` сливает
личные диалоги (сортировка по `chatMembers`) с моими группами (`chats.topDate`, групп ≤ 500) в
памяти. Непрочитанные считаются в момент запроса так:
`count(messageId > readInboxMaxId && fromUserId != я)` с потолком (как `CountUnread`).

**Галочки ✓✓ в группе.** По решению «как в Telegram» сообщение считается прочитанным, если его
прочитал хоть один участник. При `readHistory(maxID)` от R сервер:
1. берёт отличных от R отправителей сообщений в диапазоне `(старый max, maxID]` (их немного);
2. поднимает им `readOutboxMaxId` в их `chatMembers`;
3. пишет каждому в журнал пользователя `readOutbox`.

В журнал чата и в рассылку всей группе событие прочтения не попадает.

## Решения 2026-10-19

1. **История для новых участников — как в супергруппах Telegram.** По умолчанию новичок
   видит всю историю. У частной группы есть настройка «Скрыть историю»: тогда новичку
   видно только то, что пришло после его `joinedAt`. У публичной группы история видна
   всегда, настройка не показывается. Если группу переводят в частную, ранее включённое
   «Скрыть историю» снова начинает действовать. Проверка — на сервере, в
   History / GetChatDifference / поиске.
2. **Название и описание шифруются всегда** (`infoEncrypted` через `Encryptor`), у публичных
   групп тоже. Для поиска публичных групп есть отдельная открытая коллекция
   `publicChats {chatId, username, title, words[], membersCount}`: в ней только то, что и так
   видно любому. Индекс по `words` ищет по началу слова (`^запрос`). Если понадобятся
   миллионы записей или поиск с опечатками, внешний поисковик (Meilisearch) встанет поверх
   этой же коллекции. Документ группы при этом не меняется.
3. **Публичная ⇄ частная** — как «Тип группы» в Telegram, в «Изменить» (способ вступления +
   username).
   - Стала публичной: username регистрируется в `usernames`, в `publicChats` появляется
     запись.
   - Стала частной: username и запись удаляются. Участники и история остаются.
   - Перешифровывать ничего не нужно: смена типа — это только добавить или удалить запись в
     индексе. Ограничение, как у Telegram: название, увиденное через поиск, пока группа была
     публичной, уже не отозвать.
4. **Свои группы ищутся на устройстве.** Название и описание лежат в SQLite уже
   расшифрованными, сервер не нужен, поиск работает без сети.
5. **Поиск участника в большой группе:**
   - по @username — напрямую, username открыт;
   - по имени — слепым индексом: HMAC с серверным ключом от начал слов имени, хранится у
     участника. При смене имени индекс обновляется во всех группах человека (их ≤ 500).
     Делается в подэтапе 3.5.
   - в группах до нескольких тысяч человек можно проще: сервер расшифровывает страницы и
     фильтрует в памяти.
6. **Поиск сообщений на сервере — слепой индекс слов** (подэтап 3.6). Это поправка к
   решению 2 основного плана: локальный поиск (FTS5) не находит того, чего нет на
   телефоне. Пример: новичок ищет сообщение годичной давности. Подробности — в разделе
   «Поиск по сообщениям».

## Поиск по сообщениям (слепой индекс)

Решено 2026-10-19 для групп и сразу для личных чатов: на новом устройстве старой
переписки тоже нет. Каналы подключатся в срезе 4.

- **Индексация при отправке и правке.**
  1. Текст и подпись разбиваются на слова.
  2. Каждое слово нормализуется: нижний регистр, `ё → е`, основа слова (стеммер Snowball
     для русского и английского — «квартиру», «квартиры» → «квартир»).
  3. Стоп-слова («и», «в», «что», «the»…) и слова короче 2 символов пропускаются.
  4. Токен — `HMAC-SHA256(searchKey, основа)`, обрезанный до 8 байт. `searchKey` выводится
     из `encryptor.secretKey` через HKDF, по образцу `profileHdf`.
- **Хранение — списки по месяцам:**
  `chatSearch {chatId, token, month, ids:[messageId…]}`, уникальный ключ
  `(chatId, token, month)`.
  - Отправка дописывает id одним `bulkWrite` (`$push` с upsert, по разу на уникальную
    основу).
  - Около 60–80 байт на сообщение — в разы меньше самого сообщения.
  - Индекс остаётся в Mongo навсегда, в том числе когда сообщения уже ушли в архив S3.
  - Если документ месяца перерастает лимит, он режется на части (`part`).
- **Поиск** (`Messages.Search {chatID, query, offsetID, limit}`):
  1. Запрос разбивается так же; несколько слов — пересечение списков.
  2. Кандидаты идут от новых к старым.
  3. Сервер расшифровывает только кандидатов страницы (≈ 20) и проверяет настоящее
     совпадение. Так отсекаются случайные совпадения 8-байтного хэша, слова, убранные
     правкой (старые токены не вычищаем), удалённые сообщения и «удалено у меня».
  4. Сообщения старше горячего окна достаются из архива, только нужные пачки.
- **Права:** только участник чата. При «Скрыть историю» — только `messageId` после
  вступления.
- **Безопасность:** открытого текста в базе нет. Тот, кто украл базу без ключа, видит лишь
  «эти сообщения содержат одно и то же слово», но не само слово. Стоп-слова не
  индексируются, поэтому частотный анализ мало что даёт.
- **Ограничение:** поиск по целым словам и их формам, не по произвольному куску слова
  («вартир» не найдёт «квартиру»). У Telegram примерно так же.
- **Клиент:** ищет сначала локально (FTS5, мгновенно), затем догружает с сервера страницы
  «ещё раньше». Найденное старое сообщение открывается переходом в историю (подгрузка
  вокруг `messageID`, как переход по цитате). Без сети — только локальные результаты и
  пометка «нет соединения — показаны только сообщения на устройстве».
- **Без индекса**, по открытым полям, работают:
  - переход к дате (календарь);
  - вкладки «Медиа / Файлы / Ссылки / Голосовые» — по типу и флагам;
  - фильтр «от кого» — по `fromUserID`.
- **Существующие сообщения** индексирует разовая фоновая задача. Она идёт по чатам
  пачками, с флагом прогресса в `serviceState`, включая сообщения из архива. Новые
  сообщения индексируются сразу после включения.

## Протокол (`protos/chats_v1.proto`)

Новые `MessageType` не заводим, только новые ветки `oneof` (номера с 17).
- `ChatInfo` — полное описание группы: название, описание, `avatarCdnID`, username, `joinMode`,
  `defaultRole`, slow mode, реакции (режим / набор / максимум), «новичкам без ссылок и медиа»,
  `membersHidden`, `membersCount`, `pts`.
- `ChatMemberInfo` — участник: `userID`, роль, `ChatAdminRights`, звание, `joinedAt`,
  `inviterID`.
- `Dialog` получает `myRole`, `myRights`, `chatPts` и `unreadMentions`.
- В `ChatMessage` уже есть `fromUserID`. Клиенту он нужен в модели.
- `Update` получает новые ветки: `chatInfo`, `chatMember` (роль / бан / админ), `chatPts`
  (обёртка «обновление журнала чата» с `chatID` и `pts`).
- `MessageContent` получает сервисные сообщения: создана, добавил, вступил (по ссылке /
  заявке), вышел, исключил, сменил название / фото, закрепил, стал админом, передал владение.
- `Chats` получает Create, Edit, Leave / Delete, Join, ResolveLink, GetChatsState, Members
  (страница + поиск), SetMemberRole, RemoveMember (`ban`), Unban, AddMembers, SetAdmin,
  RemoveAdmin, TransferOwnership, ссылки (Create / Edit / Revoke / DeleteRevoked / List),
  заявки (List / Answer), SetReactions / SetSlowMode, ReadInfo.
- `Messages` получает GetChatDifference, VotePoll / ClosePoll и упоминания (`UnreadMentions`,
  снятие через `ReadContents`).
- `PushPayload` получает `chatTitle` (`optional`), чтобы показывать «Группа: Отправитель».
  Скрытая группа даёт анонимный пуш, как скрытый профиль. Новые поля читают NSE и
  `MessagePushHandler.kt`.

После правки proto скопировать его в `~/GolandProjects/iperon/protos/` (см. CLAUDE.md).

## Сервер (`iperon`)

**Коллекции.**
- `chats`: добавляются `pts`, `topMessageId` / `topDate`, `membersCount`, `infoEncrypted`
  (название, описание, аватар — по решению 2 шифруем через `Encryptor`, как имя в профиле) и
  открытые настройки (`joinMode`, `defaultRole`, `slowMode`, реакции, `membersHidden`, `ownerId`).
- `chatMembers`: добавляются `role`, `rights`, `rankEncrypted`, `joinedAt`, `inviterId`,
  `bannedUntil` / `kicked`. Индекс `(chatId, role, joinedAt)` нужен для страниц участников и
  админов. Для групп `chats.userIds` не используем: это граница O(N).
- `chatUpdates`: `{chatId, pts}` (уникальный ключ), TTL 7 дней.
- `chatInvites`: `{chatId, code (уникальный), title, creatorId, expireAt, usageLimit, usage,
  requestApproval, revoked}`.
- `chatJoinRequests`: `{chatId, userId, date, inviteCode}`.
- `chatMentions`: `{chatId, userId, messageId}`. Ответ на моё сообщение тоже считается
  упоминанием, как в Telegram.
- `pollVotes`: `{chatId, messageId, userId, options}` + счётчики в сообщении.
- `usernames`: `{username → kind, id}`, общая с профилями. Перенос `users.username` делается
  миграцией с флагом в `serviceState`.

**Права (новый файл `services/chats_groups_rights.go`).** Это зеркало `covers` /
`adminRightsFor` / `canBanMember` / `canPromoteMember` из `chat_info_common.dart`. Каждая
команда проверяет право на сервере, клиент только прячет кнопки. Таблица тестов одна и та же
для Go и Dart: одинаковые кейсы в `services/..._test.go` и `test/chats/`.

**Проверки при отправке:**
- роль `Чтение` не может писать;
- медленный режим (ключ в Redis с TTL = интервалу; админов не касается);
- «новичкам без ссылок и медиа» (по `joinedAt`);
- набор реакций группы;
- лимит частоты `send` (уже есть).

**Обобщить личное.** Пройти все места с `Peer()`: если чат — группа, использовать участника
или подписку на чат.
- `notifyMessage` — очередь (ниже);
- `canWrite` — для группы это роль и бан, а не приватность;
- `ReadHistory` — по схеме ✓✓ выше;
- `dialogToProto`;
- закрепы «для всех» — только с правом `pinMessages`;
- удаление чужих сообщений — с правом `deleteMessages`, «у всех»;
- TTL и no-forwards — не для групп в этом срезе (у Telegram они в группах есть, но это
  позже);
- typing — через subject чата, «печатают Ольга и ещё 2».

**Пуши в группе.**
1. Задача `notifyGroupMessage` попадает в существующую JetStream-очередь `push`.
2. Воркер идёт по `chatMembers` курсором пачками по 500 и пропускает отправителя, заглушённых
   (кроме упомянутых: упоминание пробивает mute) и онлайн-сессии (гейт по presence уже есть).
3. Scope — `NotifyScopeGroups`.
4. Бейдж считается на получателя, как сейчас. Для больших групп `badge` — это 100
   `CountUnread` на каждого. Заменить счётчиком, который кэшируется в Redis на пользователя и
   инвалидируется чтением.

**Закон Яровой и архив.**
- `MetaEvent` получает `ChatID` без пира. `logSend` / `logMedia` / `logMeta` записывают «чат,
  отправитель, число получателей» вместо `peerHex()`.
- `logFanoutLinks` — один раз на сообщение, а не на получателя.
- Сначала уточнить у юриста, достаточно ли сведений «отправитель + чат» без списка
  получателей. Список участников на момент события можно восстановить по `joinedAt` и
  событиям выхода.
- `archiveReadUpTo` пока пропускает группы: архив истории — следующий план после среза 3
  (раздел «Архив истории сообщений»).
- `purgeInvisible` / медиа-GC: в группе «удалено у меня» не делает файл невидимым. Файл
  освобождается только удалением «у всех».

**Приватность «Кто может добавлять меня в группы».**
- Поле `PrivacySettings.group_invites*`: аудитория EVERYBODY / CONTACTS + исключения, по
  образцу `CanCall`.
- Если добавить запрещено, `AddMembers` возвращает таких людей списком. Клиент предлагает
  «Отправить ссылку-приглашение» в личку, как в Telegram.
- Блокировка: заблокировавшего тебя добавить нельзя.

## Клиент

- **Миграция 35:**
  - `chatInfo` (`chatID` PK; поля `ChatInfo` + `myRole`, `myRights`, `pts` одним BLOB-протобуфом
    + открытые колонки для запросов);
  - `chatMembersCache` (известные участники: админы, я, недавно писавшие — то, что
    `members()` отдаёт сейчас);
  - `chatInviteLinks`;
  - `chatMentions`.

  Заявки не кэшируем: это список только для админа и только онлайн. Без сети показываем
  ошибку, а не пустой список.
- **`Message.fromUserID`.** Имя отправителя берётся по единому правилу имени (облачный
  контакт → книга → профиль → @username → номер). Аватар и цвет имени зависят от userID.
  Профили неизвестных отправителей подтягиваются через `_requestProfiles`.
- **`ChatsSync`:**
  - вторая очередь применения — журнал чата (`updates_plan.dart` с `chatID` в ключе; правила
    дубликата и дыры те же);
  - `GetChatsState` при подключении;
  - `GetChatDifference` при открытии чата;
  - подписки на subject'ы делает сервер, клиенту ничего не нужно.
- **`ChatsRemoteDataSource`.** Реализовать групповые методы вместо `_unsupported()`. Все
  серверные действия без сети бросают `ChatsOfflineException`, как сейчас. В `_loadChats`
  перестать отбрасывать группы.
- **`ChatsFeatures`** получает флаг `groups`. В remote-режиме «Новое» → «Группа» показывается,
  а «Канал» / «Сообщество» скрыты до срезов 4–5.
- **Пуши.** iOS NSE и Android-хендлер показывают `chatTitle` заголовком, а отправителя — в
  теле. Тап по пушу открывает `/chats/chat/<id>`.
- **Приватность.** Пункт «Группы» в «Конфиденциальности», обе платформы, с кэшем в
  `privacySettings`.

- [ ] **3.1 Журнал чата и базовая группа.**
