# Секретные чаты (E2EE, «как в Telegram») — исследование

Статус: исследование, 2026-10-18. Кода нет. Перед стартом — юридический вопрос (§6).

## 1. Что хотим

Отдельный тип чата 1-на-1, содержимое которого сервер прочитать не может
(сквозное шифрование), рядом с обычными облачными чатами — ровно модель Telegram:
облачные чаты остаются серверными (история на всех устройствах, поиск, пуши с
текстом), а «Секретный чат» — опциональный, привязан к устройству.

## 2. Как это устроено в Telegram (Secret Chats, MTProto 2.0 E2E)

- **Привязка к устройству.** Секретный чат существует между двумя конкретными
  устройствами (авторизациями). На других устройствах того же аккаунта его нет,
  истории на сервере нет; выход из аккаунта на устройстве — чат пропадает.
- **Рукопожатие — DH-2048 через сервер, без prekey.** A берёт у сервера параметры
  (`messages.getDhConfig`), шлёт `g_a` (`requestEncryption`). Запрос получают все
  устройства B; первое, что ответило `g_b` (`acceptEncryption`), «забирает» чат,
  остальным приходит `encryptedChatDiscarded`. Пока B не в сети — «Ожидание, пока
  X появится в сети». Ключ — 256 байт `g_ab`, `key_fingerprint` — 64 бита SHA1.
- **Шифрование сообщений.** AES-256-IGE, `msg_key` = средние 128 бит
  SHA256(часть ключа ‖ plaintext ‖ padding 12–1024 байт), ключ/IV выводятся из
  `msg_key` и общего ключа. Сервер хранит только непрозрачные блобы до доставки
  (очередь с `qts`).
- **Forward secrecy — перевыпуск ключа.** Клиенты делают новый DH (`requestKey` /
  `acceptKey` / `commitKey` внутри самого секретного чата) каждые 100 сообщений
  или раз в неделю; старые ключи стираются.
- **Порядок и пропуски.** В каждом сообщении `in_seq_no`/`out_seq_no`: дубль —
  выбросить, дыра — запросить повтор (`decryptedMessageActionResend`), иначе
  чат рвётся.
- **Проверка ключа.** «Визуализация ключа»: картинка + эмодзи из хешей ключа —
  сверить вживую/по другому каналу (защита от MITM сервера).
- **Медиа.** Файл шифруется на клиенте случайным ключом+IV, они уходят *внутри*
  зашифрованного сообщения; сервер хранит только шифротекст.
- **UX.** Таймер самоуничтожения (стартует, когда получатель открыл), удаление
  всегда у обоих, нельзя пересылать, уведомление о скриншоте, превью ссылок —
  опционально через сервер (предупреждение), пуш без текста.
- **Ограничения.** Только 1-на-1, нет синхронизации, нет облачного бэкапа,
  нет групп. Криптографию MTProto долго критиковали (самодельная, IGE, SHA1) —
  это лучше не копировать.

## 3. Чем это лучше/хуже Signal-подхода

| | Telegram secret | Signal (PQXDH + Double Ratchet) |
|---|---|---|
| Старт чата | нужен онлайн B (accept) | асинхронно через prekey-бандлы на сервере |
| Forward secrecy | ступенчато (100 сообщ./неделя) | на каждое сообщение |
| Post-compromise security | при следующем rekey | на каждом обороте DH-храповика |
| Постквантовость | нет | PQXDH (ML-KEM) на старте; SPQR («тройной храповик») с 2025 |
| Мультидевайс | нет (это фича) | есть, сложно (Sesame) |
| Сложность сервера | маленькая (очередь блобов) | prekey-сервер, подписанные ключи, пополнение OTPK |

**Вывод:** UX и серверную модель берём у Telegram (чат = пара устройств, accept,
очередь блобов, без мультидевайса), а криптографию — уровня Signal (гибридное
X25519 + ML-KEM рукопожатие + Double Ratchet). Всё нужное уже в зависимостях:
`package:cryptography` (X25519, AES-GCM, HKDF, HMAC, Ed25519) и `pqcrypto`
(ML-KEM) — уже используются в `lib/crypto/` (`syncer.dart`, `call_keys.dart`,
`file_encryptor.dart`). Готовых Dart-реализаций libsignal нет (официальный
libsignal — Rust + Java/Swift/TS; `libsignal_protocol_dart` — community-порт без
PQXDH), FFI к Rust ради 1-на-1 не окупается — пишем свою реализацию строго по
спецификациям Signal (Double Ratchet, PQXDH) с тестами.

## 4. Предлагаемая схема для Iperon

### 4.1 Модель
- Секретный чат = (userA, sessionA) ↔ (userB, sessionB). `sessionID` уже есть на
  сервере, адресная доставка на устройство — `ServicePublisher.PublishToSession`
  (`internal/services/publisher.go`).
- В списке чатов — отдельная строка с замком и зелёным именем (как в TG). Можно
  иметь несколько секретных чатов с одним человеком (с разных устройств).
- Отзыв сессии / логаут / удаление БД → чат закрывается (сервер шлёт `discarded`
  второй стороне).

### 4.2 Рукопожатие (3 сообщения, с коммитментом)
Коммитмент (как в ZRTP) нужен, чтобы короткий SAS из эмодзи был стойким: сервер-MITM
не может «подобрать» ключи под совпадающие эмодзи, потому что A зафиксировал свой
ключ раньше, чем увидел ключ B.

1. **A → сервер → все устройства B:** `Request{ secretChatID, commit = SHA256(epkA_x25519 ‖ nonceA) }`.
2. **Первое устройство B:** `Accept{ epkB_x25519, kemPkB (ML-KEM-768) }`; сервер
   закрепляет чат за sessionB, остальным устройствам B — `Discarded`.
3. **A:** `Commit{ epkA_x25519, nonceA, kemCt = Encaps(kemPkB) }`.
   B проверяет коммитмент.
4. Обе стороны: `SK = HKDF(X25519(a,B) ‖ ML-KEM-ss, salt = secretChatID, info = transcript_hash)`
   → корневой ключ Double Ratchet. Эфемерные приватные ключи — стереть.

Проверка: из `SK` → SAS 5–6 эмодзи (переиспользовать алфавит `CallKeys._sasAlphabet`,
`lib/crypto/call_keys.dart`, с отдельной меткой домена) + QR/длинный отпечаток на
экране «Ключ шифрования». После каждого ML-KEM-rekey отпечаток не меняется (он про
исходное рукопожатие), как у Telegram.

### 4.3 Сообщения — Double Ratchet
- DH-храповик X25519 + симметричные цепочки HMAC-SHA256, AEAD = AES-256-GCM
  (аппаратное ускорение через `cryptography_flutter`), заголовок (DH pub, PN, N)
  — в AAD (или header encryption позже, чтобы сервер не видел счётчики).
- Пропущенные ключи — до 1000 на цепочку, с TTL (неделя), в БД.
- **PQ-подмешивание:** раз в 100 сообщений / неделю (ровно как rekey в Telegram)
  — служебное `Rekey{kemPk}` / `RekeyAck{kemCt}`, секрет ML-KEM подмешивается в
  корневой ключ. Проще SPQR и даёт PQ-PCS ступенчато.
- Plaintext — новый proto `SecretPayload` (не `MessageContent`: там серверные
  поля): текст + entities, медиа-ключи, reply по `randomID`, TTL, служебные
  действия (`ttlChanged`, `screenshot`, `readUpTo`, `delete`, `resend`, `rekey`,
  `typing` можно отдельным открытым сигналом — содержимого не несёт).
- Паддинг до бакетов (256/1K/4K/…) — скрываем длину.
- Порядок: сервер отдаёт очередь строго по `qts`, клиент ack'ает; дубли/повторы
  ловит храповик (номер в цепочке) + `randomID`.

### 4.4 Медиа
`FileEncryptor` уже шифрует файл случайным `fileKey` по чанкам — но сейчас
`fileKey`/`hkdfSalt` уходят серверу в `UploadConfirm.Request.encryptionKey`, сервер
его заворачивает и отдаёт скачивающему (`internal/services/upload.go: Confirm` →
`RepositoryCDN.UploadEncrypted`). Для секретных чатов нужен режим **opaque upload**:
confirm без ключа, сервер хранит только шифротекст, а `fileKey`/`hkdfSalt`/размер/
превью-thumbnail (маленький, inline) едут внутри `SecretPayload`. Загрузчик/докачка/
GC остаются прежними. Удаление файла — по удалению сообщения у обоих / TTL.

### 4.5 Пуши
Сервер текста не знает. Вариант A (рекомендую, как TG): пуш «Новое сообщение» от
отправителя без текста (`PushPayload.Kind` → новый `SECRET_MESSAGE`). Вариант B —
расшифровка в NSE/`MessagePushHandler` — требует, чтобы расширение двигало храповик
параллельно с приложением: гонки за состояние, рассинхрон, потеря сообщений. Не делаем.
Скрытые профили / код-пароль — как сейчас (без имени).

### 4.6 Локально
- Новые таблицы (миграция N+1): `secretChats` (состояние, отпечаток, TTL, роль),
  `secretMessages`, `secretRatchet` (состояние, BLOB), `secretSkippedKeys`.
  В release БД уже под SQLCipher; ключ БД — Keychain `first_unlock_this_device`
  (`lib/repositories/repositories.dart`), Application Support исключён из бэкапа
  (`AppDelegate.excludeAppDataFromBackup`), на Android `allowBackup=false` — т.е.
  состояние храповика не утечёт в бэкап и не «воскреснет» на другом устройстве. ✔
- Состояние храповика пишется **в одной транзакции** с сохранением расшифрованного
  сообщения (иначе краш между ними = вечный рассинхрон).
- `ChatsDataSource` — отдельный `SecretChatsDataSource`/модуль `lib/chats/secret/`,
  не смешивать с `ChatsSync` (там pts/история/GET_DIFFERENCE — у секретных их нет).
- Переиспользуем: `screen_protector` + запрет копирования/пересылки (коммиты
  ac40193, 3e2c8d5), автоудаление (`chats_ttl` — но семантика «таймер с момента
  прочтения» и удаление делает клиент), SAS-экран звонков, звонки (уже E2EE).
- Скриншоты: iOS — `userDidTakeScreenshotNotification` → служебное «сделал
  скриншот»; Android — `FLAG_SECURE` просто запрещает.

### 4.7 Сервер (`~/GolandProjects/iperon`)
- Новый `MessageType SECRET_CHATS` с `oneof`: `Request/Accept/Commit/Discard/Send/Ack`
  + push-апдейт по стриму (`PublishToSession`).
- Mongo: `secret_chats` (id, adminUser/Session, participantUser/Session, state,
  createdAt) и `secret_queue` (recipientSession, qts, blob, randomID, date) —
  удаляется по ack, недоставленное — по TTL (например 30 дней) → `Discarded`.
- Гейты как у обычных: «кто может писать», блок, скрытые профили, лимит частоты
  (`rate_limit.go`), размер блоба.
- Ничего не расшифровываем и не храним дольше доставки (кроме того, что требует закон, §6).

### 4.8 Включение: флаг Remote Config, позже — только Premium
Фича выкатывается выключенной и включается удалённо; со временем создание
секретных чатов станет привилегией Premium.

**Клиент — флаги в `Settings`** (`lib/settings.dart`, по образцу
`phoneNumberModerationApplicationStoreEnable`: в debug перекрывает `.env.development`,
в release — Remote Config; дефолты — в `remoteConfig.setDefaults`):

| Ключ | Дефолт | Смысл |
|---|---|---|
| `SECRET_CHATS_ENABLED` | `false` | показывать точки входа «Начать секретный чат» |
| `SECRET_CHATS_PREMIUM_ONLY` | `false` | создавать могут только Premium (включим, когда появятся подписки) |

Геттеры `secretChatsEnabled` / `secretChatsPremiumOnly`. Условия Remote Config
(версия приложения, платформа, процент пользователей) дают поэтапную раскатку:
сначала тестеры → % → все.

**Remote Config — только UI, не защита.** Его значение подменяемо на клиенте,
поэтому то же правило дублирует сервер (`settings` сервера:
`secretChats.enabled`, `secretChats.premiumOnly`). `Request` при выключенной фиче
или без Premium → отказ с явным кодом (`failedPrecondition`, i18n-ключи
`secretChat.disabled` / `secretChat.premiumRequired`; не `unauthenticated` /
`unavailable` — их `API.call` превращает в логаут / «нет связи»).

**Что именно гейтим — только создание:**
- Premium нужен **инициатору**. Принять запрос и переписываться может любой —
  иначе Premium-пользователю почти не с кем говорить (так же устроены
  Premium-фичи в Telegram).
- Принимающая часть (приём запроса, экран чата, расшифровка) работает **всегда**,
  независимо от флага: иначе при раскатке на часть аудитории запрос к
  пользователю с выключенным флагом молча пропадёт. Флаг скрывает только кнопки
  создания (профиль собеседника, меню «Новый чат»).
- Выключение флага / истечение Premium **не ломает существующие чаты**: переписка
  продолжается, нельзя только создать новый. Удалять чужую E2EE-переписку из-за
  тарифа нельзя.
- Аварийный выключатель (баг в крипте, требование регулятора): серверный
  `secretChats.enabled=false` запрещает новые; отдельный `secretChats.frozen` —
  запрет `Send` в существующих (с понятной ошибкой в чате), без удаления истории.

**Совместимость версий.** Старые сборки не умеют секретные чаты. Сервер при
`Request` проверяет, что у собеседника есть хотя бы одна сессия с поддержкой
(версия приложения из device sessions или флаг возможностей в `Subscribe`),
иначе отказ `secretChat.peerUnsupported` («Собеседнику нужно обновить
приложение»). Запрос шлётся только поддерживающим сессиям.

**Признак Premium на клиенте.** Сейчас `IsPremium` есть только на сервере
(`internal/models/users.go`, ставится вручную в БД; уже используется в
`CanSeeLastSeen`), клиенту не передаётся. Добавить `isPremium` в ответ
`MY_PROFILE` (`protos/myprofile_v1.proto`, копия в серверный репо) и кешировать в
`myProfile` (миграция) — чтобы offline UI показывал правильное состояние.
Изменение тарифа долетает живьём через уже существующий `publishMyProfile`.

**UI при `PREMIUM_ONLY=true` и не-Premium:** пока системы подписок нет —
пункт скрыт (некуда вести). Когда появится покупка — пункт виден со значком
Premium и ведёт на экран оформления.

## 5. Модель угроз (что получаем)
- Сервер/взлом сервера/S3: видят метаданные (кто, кому, когда, размер-бакет), не
  видят содержимое и медиа. ✔
- Активный MITM сервера при создании: ловится сверкой эмодзи (коммитмент делает
  короткий SAS стойким); без сверки — защиты нет (как в TG).
- Компрометация устройства: прошлое защищено (FS), будущее восстанавливается после
  следующего DH-оборота (PCS).
- «Сохранить сейчас — расшифровать потом» (квантовый): закрыто ML-KEM на старте и
  в rekey.
- Не закрываем: метаданные, скриншоты камерой, вредонос на устройстве.

## 6. ⚠️ Юридическое — закон Яровой (решить ДО разработки)
149-ФЗ ст. 10.1 ч. 4.1 обязывает ОРИ, применяющего дополнительное кодирование,
передавать ФСБ информацию, необходимую для декодирования. Ровно за это (невыдача
ключей секретных чатов) в 2018 блокировали Telegram. Текущее решение по retention
(2026-10-15, юрист): «ключи ФСБ не передаём — выдаём расшифрованное» — для E2EE это
**технически невозможно**: у сервера нет ни ключей, ни открытого текста. Для
секретных чатов сервер сможет выдать только метаданные + шифротекст (и
6-месячное хранение файлов будет хранением шифротекста).
Нужно отдельное заключение юриста: допустимо ли до/после включения в реестр ОРИ;
это же касается уже сделанного E2EE звонков (голос звонков сейчас не пишем).
Также — App Store Export Compliance: проверить декларацию шифрования.

## 7. Этапы
0. Юрист (§6) — стоп-фактор.
1. Крипто-ядро на чистом Dart в `lib/crypto/secret/`: рукопожатие, Double Ratchet,
   rekey, паддинг; юнит-тесты + тест-векторы Signal для Double Ratchet, fuzz на
   перестановки/потери/дубли, тест «краш между сообщением и состоянием».
2. Proto `secret_chats_v1.proto` (копия в серверный репо) + сервер: чаты, очередь,
   ack, discard по отзыву сессии, гейты, тесты. Серверные флаги
   `secretChats.enabled/premiumOnly/frozen`, проверка поддержки у собеседника,
   `isPremium` в `MY_PROFILE` (§4.8).
3. Клиент: таблицы, модуль `lib/chats/secret/`, экраны (создание из профиля
   «Начать секретный чат», ожидание, список, чат, «Ключ шифрования») в Cupertino +
   Material, i18n. Флаги `SECRET_CHATS_ENABLED` / `SECRET_CHATS_PREMIUM_ONLY` в
   `Settings` + Remote Config (дефолт — выключено); приём запросов — без флага.
4. Медиа: opaque upload (сервер + клиент), превью inline.
5. Таймер самоуничтожения, скриншоты, пуши `SECRET_MESSAGE`.
6. Внешний аудит крипты перед продом (собственная реализация протокола — без
   аудита в прод не стоит).
7. Раскатка через Remote Config: тестеры → % → все. Позже, с системой подписок —
   `SECRET_CHATS_PREMIUM_ONLY=true` + `secretChats.premiumOnly=true` на сервере и
   экран оформления Premium.

Оценка: ядро + сервер + текстовый чат — крупная фича (≈ как «личные чаты» срез 1);
медиа и полировка — ещё столько же.

## 8. Открытые вопросы
- Асинхронный старт (prekey-бандлы, как Signal) нужен или достаточно accept, как в TG?
  Рекомендация: accept, prekey — позже, если будет жалоба на «ожидание».
- Секретные группы — нет (Telegram их тоже не делает; это MLS — отдельный проект).
- Превью ссылок — только клиентское или выключено (сервер не должен видеть URL).
- Premium нужен только инициатору (рекомендация) или обоим?
- Что делают пользователи, создавшие чаты до включения `PREMIUM_ONLY`: старые
  чаты остаются (§4.8), новые — только с Premium. Нужен ли «грейс» для ранних?
- Показывать ли на других устройствах пользователя «есть секретный чат на iPhone»
  (TG — не показывает).
