# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Flutter messenger app (Android + iOS, Firebase project `iperon`, product name "Iperon"). The UI ships **two parallel native-look variants** — Cupertino (iOS) and Material (Android) — picked at startup by `Platform.isIOS` (see the **UI** section below); every screen exists as both a `*_cupertino.dart` and a `*_material.dart`. Beyond the app scaffolding (logging, DI, Firebase, cubit/bloc state) it already wires up a gRPC/protobuf backend client, an encrypted SQLite store, a hybrid classical + post-quantum key exchange, phone-number auth, and slang-based i18n. The backend host defaults to `staging.iperon.net:443`.

## Commands

- `flutter pub get` — install dependencies.
- `flutter run` — run the app on a connected device/emulator. Debug builds load `.env.development` (see Settings below); an unencrypted DB is used in debug, an encrypted one in release.
- `flutter analyze` — static analysis (uses `analysis_options.yaml`, based on `flutter_lints`).
- `flutter test` — run tests (`test/`, chat logic mostly under `test/chats/`).
- `flutter test test/chats/updates_plan_test.dart` — run a single test file; add `--name '<substring>'` for one test. Tests needing slang translations must `await AppLocale.ru.build()` in `setUpAll` (`buildSync` fails: locales are deferred).
- `dart run build_runner build --delete-conflicting-outputs` — regenerate `dart_mappable` code (`*.mapper.dart` files under `lib/models/` and `lib/cubit/`). Run this after changing any `@MappableClass()` model. `dart_mappable_builder` runs under this builder. Runtime config comes from `Settings`/dotenv/Remote Config (see the Settings section).
- `dart run slang` — regenerate i18n code (`lib/i18n/translations*.g.dart`) from the `lib/i18n/*.i18n.yaml` sources (config in `slang.yaml`). Run after editing translations.
- Protobuf: the `*.pb*.dart` under `lib/protobuf/` are generated from `protos/*.proto`. Do not hand-edit them. The `.proto` files are **shared with the server repo** (`~/GolandProjects/iperon/protos/`, Go code generated there with `task gen` → `internal/api/v1`) — edit here and copy the changed files over (or vice versa); `myprofile_v1.proto` currently differs between the two. Regenerate only the protos you touched, then format: `protoc --dart_out=grpc:lib/protobuf protos/chats_v1.proto && dart format lib/protobuf`. For `v1.proto` drop the `grpc:` option (`--dart_out=lib/protobuf`) and leave `v1.pbgrpc.dart` alone — the checked-in `v1.pb.dart`/`v1.pbjson.dart` were generated that way, and the `grpc:` variant rewrites them wholesale. Check `git diff --stat lib/protobuf` stays proportional to the change.
- `taskfile.yml` (go-task) wraps the same commands: `task lang` (slang), `task watch` (build_runner watch), `task gen` (protoc for **all** protos + build_runner + format — see the caveat above), `task fmt`, `task analyze`, `task apk` (release APK installed to a specific device serial).

## Architecture

- **Dependency injection**: `lib/di.dart` uses `get_it` as a service locator (`getIt`). Singletons are registered async via `registerCommonDependencies()`, called once at app startup in `main.dart` before `runApp` (which then `await getIt.allReady()`). Graph: `Logger` → `Settings` → `Repositories`; `Utils` (no deps); `API` (Settings); `Auth` (Repositories, API) → `Routers`; `Crypto` (Settings, Utils); `CDNManager` (API, Crypto, Auth, Repositories — encrypted media upload/download); `Calls` (Settings, API, Auth); `PushManager` (API, Auth, Repositories) → `CallPush`. Chat singletons (`ChatsSync`, `ChatsPresence`, `ChatsTyping`, data sources) are **not** in `get_it` — they are `X.instance` statics under `lib/chats/`. Add new app-wide services here following the existing `Logger` pattern (`registerSingletonAsync` + guarded by `isRegistered`), and mirror them in `unregisterCommonDependencies()`.
- **Utils**: `lib/utils.dart` holds `Utils` (registered in `get_it`). It centralizes phone-number normalization via `dlibphonenumber` (`phoneNormalization` — RU-centric: rewrites a leading `8` to `7` and treats bare 10-digit `9XXXXXXXXX` as a Russian mobile, returning a `PhoneNumberModel` with `international`/`national`/`e164`/`rfc3966`; invalid input yields an all-empty model, never throws), `bytesToHex`/`hexToBytes`, and async `packageInfo()`/`deviceInfo()` (via `package_info_plus`/`device_info_plus`/`device_marketing_names`).
- **Logging**: `lib/logger.dart` wraps `package:talker` in a `Logger` class exposing `debug/info/warning/error/critical/handle`. Always fetch it via `getIt.get<Logger>()` rather than constructing a new `Talker` directly. `handle()` is the intended entry point for reporting caught exceptions (mirrors Talker's `handle`).
- **Crash reporting**: `main.dart` wires both `FlutterError.onError` and `PlatformDispatcher.instance.onError` to `FirebaseCrashlytics.instance` so both framework and platform-level errors are reported.
- **State management**: uses `flutter_bloc`/`bloc` cubits. Convention: one cubit class + one immutable state class per feature, under `lib/cubit/<feature>/` (see `lib/cubit/common_cubit.dart` + `lib/cubit/common_state.dart` as the template). State classes use `dart_mappable` (`@MappableClass()` + `with <State>Mappable` + `part '<file>.mapper.dart'`) for `copyWith`/equality codegen — remember to run `build_runner` after editing them. Cubits are plain classes (not registered in `get_it`); state carries a `Status` enum (`initialization`, `loading`, `success`, from `lib/constants.dart`) to track async lifecycle.
- **Barrel exports**: `lib/cubit.dart` re-exports `lib/cubit/cubit.dart`, which re-exports individual cubit files — import cubits via `package:messenger/cubit.dart` and add new cubits to `lib/cubit/cubit.dart`'s export list.
- **Auth / routing guard**: `lib/auth.dart` holds `Auth`, the single source of truth for "is the user logged in". It is registered in `get_it` (`dependsOn: [Repositories, API]`) and loads the active session from SQLite **once** at startup via `repositories.sessions.getActive()`; `isAuthorized` is then read from memory. `lib/routers.dart` wires it into both `GoRouter`s through `redirect` (sends anonymous users to `/auth`, keeps logged-in users out of `/auth`) plus `refreshListenable`. `redirect` *can* be async in go_router, but it runs on every navigation — hence the in-memory cache instead of hitting the DB per transition. After writing a session to the DB, call `getIt.get<Auth>().refresh()` so the router re-evaluates the route (see `lib/cubit/auth/auth_moderation_application_store_cubit.dart`). `Routers` builds **two** `GoRouter`s that share `_redirect`/`refreshListenable=auth`: `cupertino(key)` (routes `_common` + `_cupertino`) and `material(key)` (routes `_commonMaterial`) — `main.dart` selects one by platform. `_common`/`_commonMaterial` each use a `StatefulShellRoute.indexedStack` for the bottom tab bar (`/contacts`, `/calls`, `/chats`, `/settings`) rendered by `HomeCupertino`/`HomeMaterial`; sub-screens like `/settings/language` and `/settings/appearance` are declared as nested `routes:` but pin `parentNavigatorKey: rootNavigatorKey` so they push full-screen over the tab bar. Navigate with `context.go(...)`. When adding a screen, add it to **both** branches.
  - **Push routes MUST use `pageBuilder:` with the decoupled-package `Page`, not `builder:`.** Each app is wrapped in `CupertinoApp`/`MaterialApp` from `package:cupertino_ui`/`package:material_ui` (the decoupled UI packages), *not* Flutter's built-in `package:flutter/cupertino.dart` / `material.dart`. For a `builder:`-only route, go_router auto-picks the `Page` type by `findAncestorWidgetOfExactType` against Flutter's built-in `CupertinoApp`/`MaterialApp` — which never matches the decoupled ones, so it silently falls back to `NoTransitionPage` (no platform transition, **no iOS swipe-back gesture**). Use the `_page(state, child)` / `_pageMaterial(state, child)` helpers in `lib/routers.dart` (returning a `cupertino_ui` `CupertinoPage` / `material_ui` `MaterialPage`) for any full-screen push. The tab-root routes stay on `builder:` since they're never pushed.
- **Yandex ID sign-in**: an alternative to the call-password login, mainly for non-RU numbers (calling a foreign number is expensive). Yandex is used **only to confirm the phone number** — no Yandex identifiers are stored anywhere; the user is still looked up/created by phone. Flow: `AuthCubit.yandexSignIn()` (`lib/cubit/auth/auth_cubit.dart`) → `hasNetwork()` guard → `YandexLoginSdk.signIn(clientId: settings.yandexOauthClientID)` → `access_token` → pre-auth unary `AUTH_YANDEX` (`protos/yandex_v1.proto`) → `confirmationSession` + `hasTwoStepVerification` → `/auth/cloud_password` or `AuthLoginCompleter`, exactly like `passkeySignIn()` (it returns the same `({error, redirectURI})` record; cancel/in-progress = empty record, nothing shown). The server verifies the token itself via `login.yandex.ru/info` (incl. the token's `client_id`), takes `default_phone`, allows **any region** (call-password is RU-mobile only), and marks new users `phoneVerificationSource = 3`. Error i18n keys live under `yandex.*`; the server deliberately avoids `unauthenticated`/`unavailable` codes because `API.call` turns those into a logout / generic "no connection". Native setup is already in place: client ID in `Settings` (`YANDEX_OAUTH_CLIENT_ID`), `manifestPlaceholders["YANDEX_CLIENT_ID"]` in `android/app/build.gradle.kts` (requires `MainActivity : FlutterFragmentActivity`), and on iOS the `yx<clientId>` URL scheme + `LSApplicationQueriesSchemes` in `Info.plist` plus URL forwarding in `SceneDelegate.swift`. **The OAuth app on oauth.yandex.ru must grant `login:default_phone`** — scopes can't be requested through the SDK, and without it every Yandex login fails with `yandex.phoneMissing`. On the auth screen the Yandex button (`assets/images/yandex_id.svg`) sits left of the passkey one; both share one `signInBusy` (`_SignInProvider`) state so only one sign-in runs at a time.
- **Firebase**: configured via FlutterFire (`lib/firebase_options.dart`, generated — do not hand-edit; regenerate with `flutterfire configure` if project settings change). Crashlytics wiring lives in `main.dart`; Remote Config is initialized in `lib/settings.dart` (see below).
- **Settings / config**: `lib/settings.dart` holds `Settings`, registered in `get_it` (`dependsOn: [Logger]`). It is the single accessor for runtime config and layers two sources: `flutter_dotenv` (`.env`, plus `.env.development` in debug) takes precedence, falling back to Firebase Remote Config (1-hour min fetch interval; defaults live in the `remoteConfig.setDefaults({...})` map here — add new remote-config keys there). Read config through `Settings` getters (`apiHost`, `apiPort`, `databaseName`, etc.); don't touch `dotenv`/`remoteConfig` directly elsewhere. **Behaviour flags come from the server first** (stage 5b of `docs/plans/admin-panel.md`): `ClientConfig` (`protos/client_config_v1.proto` — secret chats, group calls, call timings, animated-emoji URL, Yandex client_id, minimal version), set in the admin panel; chain `.env` (debug) → `Settings.serverConfig` → Remote Config (transition) → `_defaults`. `ClientConfigSync` (`lib/client_config.dart`) fills it: cache from `device.db` (`clientConfig`, per server, migration 7) before the first screen, pre-auth unary `CLIENT_CONFIG` in `startAccountServices`, then the `SUBSCRIBE` response and `CLIENT_CONFIG` stream pushes (`API._handleMessage`). `Settings` is a `ChangeNotifier` — wrap UI that must react live in a `ListenableBuilder` (the group-call button on the Calls tab). `minimalVersion` → `AppUpdateGate` (`lib/components/app_update/`, a layer in the app `builder`): «Обновите приложение» with a store / Sparkle button. Test numbers need no list in the app any more: `AUTH_CALL_PASSWORD` answers `fixedCode` + `fixedCodeSession` and `AuthCubit` goes to `/auth/moderation_application_store`.
- **gRPC / API**: `lib/api.dart` holds `API`, registered in `get_it` (`dependsOn: [Settings]`). It builds a single `IperonClient` (from `lib/protobuf/protos/v1.pbgrpc.dart`) over one long-lived `ClientChannel` with keep-alive + jittered exponential backoff, and logs traffic via `TalkerGrpcLogger`. Two usage patterns:
  - **Unary RPCs**: `API.call(() => client.someRpc(...))` wraps the call, maps `GrpcError` codes to an `APICallStatus` (`APIStatus.success|error` + `statusCode` + a message/i18n-key `error`), and never throws for gRPC errors.
  - **Long-lived bidirectional stream**: `API` also owns the app's persistent `client.stream(...)` (the `rpc Stream` in `v1.proto`). It is opened/closed by `_reconcile()`, gated on two flags — set `setAuthorized(bool)` and `setForeground(bool)` (driven from `AppLifecycleState` in `main.dart`); the stream only stays open while both are true. On open it sends a `Subscribe` message (`_subscribe()`). Connection state is surfaced as `ApiConnectionStatus` (`connecting|updating|connected`) via `connectionStatus` + `connectionStatusStream`. Consume inbound traffic by message type through `api.on(MessageType)` (a filtered broadcast `Stream<Uint8List>`) rather than touching the raw stream.
  - The commented-out block at the bottom is a reference for the intended TLS/metadata/`callOptions` setup — the current channel uses `ChannelCredentials.insecure()`.
- **Persistence (encrypted SQLite)**: `lib/repositories/` holds `Repositories`, registered in `get_it` (`dependsOn: [Settings]`). It opens the account's `sqlite_async` `SqliteDatabase` (in the account folder, see below) and exposes typed repository objects, each a `part` file of `repositories.dart` in `lib/repositories/` (settings, sessions, profiles, contacts, uploads/downloads, call logs, privacy/notify settings, `hiddenProfiles`, and `chats` — the chat cache: dialogs, messages, outbox, pinned, etc.). Widgets/data sources react to table changes via `repositories.db.onChange([...tables])`. Note the two distinct "session" concepts: `sessions` is the **local** auth session (drives `Auth`), while `deviceSessions` mirrors the user's **remote** active devices fetched over gRPC (`device_sessions_v1.proto`) for the settings screen. `myProfile` is the local cache of the user's own editable profile (name/birthDate/aboutMe), kept in sync with the `MY_PROFILE` stream message (see `SettingsMyProfileCubit`); `profiles` caches other users' profiles, and `contacts` stores the address book (including cloud-synced entries — `isCloud`/`oprf` columns). In release builds the DB is encrypted (SQLCipher `PRAGMA key`) with a random password persisted in `flutter_secure_storage`; in debug it's unencrypted. `foreign_keys = ON` is set per connection. **Schema changes go through `migrations.add(SqliteMigration(n, ...))` in `_initialization()`** (currently up to migration 52) — never edit an existing migration; add the next number. Device-wide data lives in a second DB, `device.db` (same password; `lib/repositories/device.dart`): `settingsDevice` and the `accounts` index (multi-account stage 2) — its first migration copies `settingsDevice` (schema + row) and the active account from the account DB, later `settingsDevice` columns go to `DeviceDatabase.migrations`, **not** the account DB. `sessions`/`users` stay in the account DB (FKs and owner subqueries point at them); `Sessions.deleteAndCreate`/`deleteActive` keep `accounts` in sync. Per-account files live in the account folder (`lib/repositories/account_files.dart`): `<support>/accounts/<accountID>/` holds `iperon.db` (password `databasePassword:<accountID>`), `chat_outbox/`, `secret_media/`; `<cache>/accounts/<accountID>/media/` is the download cache — reach them via `AccountScope.current.dataSubdir/cacheSubdir`, never `getApplicationSupportDirectory()` directly. `accounts` rows are slots: logout clears `userID` but keeps the slot and folder. Old shared paths are moved once at startup (`AccountFilesMigration`, guarded by the `accounts/.migrating` lock). `Settings.isDeleteDatabase` (env `IS_DELETE_DATABASE`) wipes the DB + stored password on launch.
- **Models vs. state**: `lib/models/` holds `@MappableClass()` data models (`Session`, `User`, `SettingsDeviceModel`, enums like `ColorThemeModel`/`DarkModeModel`, …) with generated `*.mapper.dart` — these are what repositories read/write. `lib/models/mapper.dart` registers custom `dart_mappable` mappers (`Uint8ListMapper`, `BoolMapper`, `EpochDateTimeMapper`) that bridge SQLite BLOB↔`Uint8List`, int↔`bool`, and epoch-millis-int↔`DateTime`; new models storing those types rely on these. **Gotcha:** repositories persist dates via `.millisecondsSinceEpoch` (an int), but dart_mappable's default `DateTimeMapper` decodes only ISO strings and throws `FormatException` on the int — so any model that reads a `DateTime`/`DateTime?` column back must opt into `EpochDateTimeMapper` via `@MappableClass(includeCustomMappers: [EpochDateTimeMapper()])` (see `MyProfile`). Sessions dodged this only because `Sessions.getActive()` doesn't SELECT its `createAt` column. Cubit *state* classes (`lib/cubit/**/*_state.dart`) are separate — see the state-management convention above.
- **Crypto**: `lib/crypto/` holds `Crypto`, registered in `get_it` (`dependsOn: [Settings, Utils]`), exposing `keyExchange` (`lib/crypto/syncer.dart`, a `part` of `crypto.dart`). It combines classical (`package:cryptography`) with post-quantum ML-KEM (`package:pqcrypto`) for a hybrid key exchange — session `sharedKey`/`salt` end up in the `sessions` table.
- **Background tasks & push (not yet wired)**: `native_workmanager` and `firebase_messaging` are declared in `pubspec.yaml`, but the actual wiring is currently commented out — the `@pragma('vm:entry-point')` background worker and `NativeWorkManager.initialize/registerDartWorker/enqueue` calls in `main.dart`, and there is no `FirebaseMessaging` handler yet. Don't look for an existing integration; a background worker must re-run `registerCommonDependencies()` since it starts in a fresh isolate (see the commented `helloWorldWorker` reference in `main.dart`).
- **i18n (slang)**: translations are authored in `lib/i18n/en.i18n.yaml` / `ru.i18n.yaml` and compiled to `lib/i18n/translations*.g.dart` (run `dart run slang`). `main.dart` wraps the app in `TranslationProvider`; the active locale is persisted in `settingsDevice.locale` and applied via `LocaleSettings`. English is the base/fallback locale.
- **Cloud password (two-step verification) = OPAQUE-3DH (RFC 9807)**: neither the password nor anything equivalent reaches the server. Client side: `lib/crypto/opaque.dart` (`OpaqueClient`, ristretto255-SHA512, HKDF/HMAC/SHA-512; the group operations — here and in contacts `Oprf` — are libsodium via `Ristretto255` in `lib/crypto/ristretto.dart`: `package:sodium` builds libsodium from source in its build hook, so iOS/macOS/Android builds need the native toolchain; the pure-Dart `ristretto255` package it replaced took ~140 ms per point multiplication and ~3 s for its base-point table on the UI isolate) + `lib/crypto/cloud_password.dart` (`cloudPasswordClient()`: context `iperon-cloud-password-v1`, KSF Argon2id 32 MiB / t=2 / p=4) — **context and KSF parameters must never change** (every stored password depends on them; the server is `internal/crypto/opaque.go` in iperon). A wrong password is detected locally at KE2 (`OpaqueError.wrongPassword`, KE3 is not sent); the server counts an attempt at the start of each exchange and reports `attemptsLeft`. Login (`AuthCloudPasswordCubit`): `AUTH_CLOUD_PASSWORD_START/FINISH`; recovery = email code (`RECOVERY_CONFIRM`) → `AUTH_CLOUD_PASSWORD_REGISTER_START/FINISH`. Settings and group ownership transfer go through `CloudPassword` (`lib/cloud_password.dart`): `unlock` (`CLOUD_PASSWORD_AUTH_*`) yields a 10-minute server token used by `register` / `DISABLE` / `EMAIL_SET` / `TransferOwnership`; `cloudPassword.unlockRequired` = token expired → back to unlock; registering a new password drops the token, so `SettingsCloudPasswordCubit` re-unlocks with the new one. Tests: RFC 9807 vectors in `test/crypto/opaque_test.dart`; interop with the real server code in `test/crypto/opaque_interop_test.dart` (needs `OPAQUE_INTEROP_SERVER` = a build of iperon's `cmd/opaque-interop`).
- **App passcode & biometric lock**: an optional local app-lock, separate from server auth. The PIN is hashed with **Argon2id** (`package:cryptography`) and only the hash is persisted in `settingsDevice`; the create flow (`SettingsPasscodeCreateCubit`) and the verify flow (`SettingsPasscodeCubit`) **must use identical Argon2id parameters** (`parallelism/memory/iterations/hashLength`) or entered PINs will never match. The lock UI uses `flutter_screen_lock`; biometric unlock uses `local_auth` (`LocalAuthentication`) and is triggered from `main.dart`'s `didChangeAppLifecycleState` (lock on `paused`/`hidden`, prompt on `resumed`) — the app root is a `WidgetsBindingObserver`.
- **Connection status UI**: `ConnectionCubit` (`lib/cubit/connection_cubit.dart`) merges two independent signals into one status for the UI — device network reachability (`connectivity_plus`) and the gRPC stream state (`API.connectionStatusStream`). Like other cubits it is not in `get_it`; a single instance is provided high in the shell so all tabs share the same status (rendered by `lib/components/connection_title.dart`).
- **Offline handling (always design for it)**: any screen or cubit that reads or writes server state over gRPC **must** account for the device being offline — do not assume the happy path. `API.call`/`unaryEncoded*` never throw for network errors; offline they return `APIStatus.error` (`statusCode` = `unavailable`/`deadlineExceeded`, i18n key `grpcError.errorConnectingServer`/`unableConnectServer`). Rules of thumb: (1) **Never silently show a default as if it were the real value** — if a load failed, track that in state (a `loadError`/`Status.error` flag) and render a "couldn't load / retry" affordance instead of a fabricated value. (2) **Don't do optimistic-then-rollback on a write when there's no network** — the value visibly flips back with no explanation; check `getIt.get<Utils>().hasNetwork()` (or gate on `ConnectionCubit`) first and give explicit feedback (Cupertino `showCupertinoDialog`, Material `SnackBar`), mirroring the no-network guard in `lib/calls.dart` (`startCall`). (3) For values that must stay visible offline, cache the last-known one locally in SQLite (as `myProfile` does) and refresh on reconnect. Server-authoritative settings generally can't be *edited* offline — block the edit with feedback rather than pretending it succeeded.
- **UI (dual Cupertino + Material)**: `main.dart` picks the app root by platform — `IperonMessengerCupertino` (`lib/app_cupertino.dart`, a `cupertino_ui` `CupertinoApp.router`) on iOS, `IperonMessengerMaterial` (`lib/app_material.dart`, a `material_ui` `MaterialApp.router`) on Android. Screens live under `lib/screens/**` as **both** `*_cupertino.dart` and `*_material.dart` (kept in sync; logic shared by both lives in `*_common.dart`, e.g. `lib/screens/chats/chat_common.dart`). On iOS, choices go in menus (`CupertinoContextMenu` / `CupertinoMenuAnchor` pull-downs), not `CupertinoActionSheet` — e.g. «delete for both / only for me» for chats and messages (`deleteScopeMenuCupertino` in `chat_actions_cupertino.dart`); Android keeps alerts/bottom sheets. Navbar and sheet-header actions are **icons, not text**: on iOS use `NavBarButtonCupertino(NavBarAction.done|next|cancel|close|edit|clear|more, label:, loading:, onPressed:)` (`lib/components/nav_bar_button_cupertino.dart` — plain icons pinned to the bar edge like the old text: cancel/close to the start, the rest to the end, override with `alignment:` when e.g. «Отмена» sits in `trailing`; `label` goes to VoiceOver only), on Android an `IconButton(tooltip:, icon: Icon(Icons.check))`. Cupertino widgets come from `package:cupertino_ui`, Material from `package:material_ui` (both decoupled packages — see the routing `Page` gotcha above; `lib/themes/material.dart` also imports a few `ButtonStyle`/`BorderSide` types from `package:flutter/material.dart` under an `fm` prefix because `flutter_screen_lock` demands the built-in ones). Theming: `lib/themes/cupertino.dart` (`ThemesCupertino`, sets `primaryColor`) and `lib/themes/material.dart` (`ThemesMaterial`, builds a `ThemeData` from `ColorScheme.fromSeed` with the surface tones overridden to match the Cupertino palette so both platforms read as one app); both are driven by `settingsDevice.colorTheme` + `darkMode` from `CommonCubit` state, and force blue on `/auth`. **Cupertino accent in dark mode** comes from Material's dark seed scheme (`ThemesCupertino.accent`: light = the iOS colour as before, dark = `ColorScheme.fromSeed(...dark).primary`, a light pastel tone), so anything *filled* with the accent must draw its content with `ThemesCupertino.onAccent(context)` (= theme `primaryContrastingColor`: white in light, dark `onPrimary` in dark) — never hardcode white on an accent fill. Actions (navbar buttons, action rows, body text buttons) stay **white** in dark via `navActionColor`/`actionColor`; outgoing bubbles use `chatOutgoing`/`chatOnOutgoing` (`primaryContainer` in dark, like Android). When a widget needs a platform-specific presentation, add a `*_cupertino.dart` + `*_material.dart` pair and branch on `Platform.isIOS` in the shared entry point (see `lib/components/toolbar_attachments/` — `showToolbarAttachments()` opens `showCupertinoModalPopup`+`ToolbarAttachmentsCupertino` on iOS, `showModalBottomSheet`+`ToolbarAttachmentsMaterial` on Android).
- **Media picking (`image_picker`)**: photo/video selection uses `package:image_picker` (native pickers — `PHPickerViewController` on iOS, the system photo picker on Android), chosen over `wechat_assets_picker` because the native pickers avoid the Flutter-drawn gallery's iCloud thumbnail crashes (`CloudPhotoLibraryErrorDomain 1006` / `PHPhotosErrorDomain 3169`) and need no photo-library permission on iOS 14+. The avatar flow in `settings_my_profile_cupertino.dart` shows a `CupertinoActionSheet` (Camera / Gallery) then calls `ImagePicker().pickImage(source:, imageQuality:, maxWidth:)`; camera returns one shot (`preferredCameraDevice` only applies to `ImageSource.camera`). For multi-select use `pickMultiImage` (photos) or `pickMultipleMedia` (mixed photo+video) — both gallery-only, no camera. iOS permission strings (`NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`) live **localized** in `ios/Runner/{en,ru}.lproj/InfoPlist.strings` (with the English default also in `Info.plist`) — add both when introducing a new usage key. Native plugin changes need a full `flutter run` (+ `pod install`), not hot restart.
- **Chats (`lib/chats/`)**: Telegram-style model, plan in `docs/plans/chats-groups-channels.md`. ## Form fields — gotchas

- **Cupertino: black flash on a disabled field.** `CupertinoTextFormFieldRow` builds a `CupertinoTextField.borderless` with no `decoration`, and when `enabled: false` `CupertinoTextField` fills a decoration-less field with `_kDisabledBackground` — near-black `0xFF050505` in dark mode (`0xFFFAFAFA` in light, so it goes unnoticed). If a field is disabled during a request (`enabled: !loading`), pass `decoration: const BoxDecoration()` (transparent, so the card fill shows through). See `_row` in `lib/screens/auth/auth_cloud_password_cupertino.dart`.
- **Material: label position.** Borderless form fields (inside a `Card`, with `labelText`) use `floatingLabelBehavior: FloatingLabelBehavior.always` — otherwise an empty field centers its label while a filled one floats it, so forms look inconsistent (the profile is usually prefilled, the cloud-password form is empty). Already applied in `auth_cloud_password_material.dart`, `settings_cloud_password_material.dart`, `settings_my_profile_edit_material.dart`, `settings_my_profile_username_material.dart`, `contacts_add_material.dart`, `profile_hide_material.dart`, and the outlined phone field in `auth_material.dart`.
- **Android: autofill popup closes the keyboard.** A Flutter `TextField` defaults to `autofillHints: const []` — an *empty* list still opts the field into Android autofill, so the system guesses a name field and opens its suggestion window over the app; that window takes window focus (`inactive` → `resumed`) and the keyboard is hidden after the first letter (`HIDE_SAME_WINDOW_FOCUSED_WITHOUT_EDITOR`). Only `autofillHints: null` disables it — used for the name fields in `contacts_add_material.dart` and `settings_my_profile_edit_material.dart`, and for every cloud-password field (`auth_cloud_password_material.dart`, `settings_cloud_password_material.dart`, the ownership-transfer dialog in `chat_admins_material.dart`) — `AutofillHints.newPassword` / `.email` / `.oneTimeCode` trigger Google's popup the same way. Relatedly, never swap the app root's widget structure on `inactive` (the blur-on-inactive is an overlay layer `BlurLayer`, not a wrapper around `child`), or every screen is rebuilt and loses focus.
- **Multi-step forms: key the fields.** When one screen swaps steps (e.g. cloud password → recovery email → code + new password) and the new field lands at the same tree position with the same widget type, Flutter reuses the old field's `State` and its open keyboard connection — the new `keyboardType` (email layout), `autofillHints` and `autofocus` are not applied. Give each field a key tied to its controller (`key: ObjectKey(controller)`) so it is recreated per step. See `_row` in `auth_cloud_password_{cupertino,material}.dart`.

## CI/CD

GitHub Actions live in `.github/workflows/`. `lib/firebase_options.dart` and the `.env` files are gitignored, so CI reconstructs them from secrets before building (restore the base64 secret → **`dart format` the restored `firebase_options.dart`** so it doesn't fail the format check → `touch .env .env.development`) — mirror that in every job that builds/analyzes if you add a workflow. Two **reusable** workflows hold the actual work and are invoked via `uses:` (referenced by full `iperon-net/messenger/...@main` path, so they only resolve on the GitHub remote, not for `act`/local runs):
- **`_linter.yaml`** (reusable, `workflow_call`): two parallel jobs — **Format** (`dart format --output=none --set-exit-if-changed lib`; formatting is enforced — run `dart format lib` before pushing) and **Analyze** (`flutter analyze`).
- **`_deploy_testflight.yaml`** (reusable, `workflow_call`): builds a release IPA and uploads to TestFlight via fastlane (`bundle exec fastlane beta` in `ios/`). `BUILD_NAME` comes from the tag (`v0.0.1` → `0.0.1`); `BUILD_NUMBER` is a UTC `date -u +%y%m%d%H%M` timestamp so it stays unique and monotonically increasing, independent of the tag. It also: regenerates `dart_mappable`/`slang` code, forces **manual** code-signing via appended `ios/Flutter/Release.xcconfig` keys + a generated `ExportOptions.plist` (leaving `pbxproj` untouched) — with a **second** profile for the Notification Service Extension (secret `IOS_NSE_PROVISIONING_PROFILE_BASE64`, keys appended to `ios/NotificationService/Release.xcconfig`, the extension's own base config), builds a Conventional-Commits changelog for the TestFlight "What to Test" field (range = previous `v*` tag..current tag — i.e. what landed in this release vs. the last one; grouped feat/fix/other, truncated to Apple's 4000-char limit), and uploads dSYMs to Crashlytics as the **last** step (best-effort — `uploadDebugSymbols` in `firebase.json` is left `false` and symbols are shipped directly with the `upload-symbols` binary, since the Xcode build-phase path is unreliable on CI).

Callers:
- **`testing.yaml`** (on PRs + pushes to `main`): calls `_linter.yaml` only.
- **`warm_cache.yaml`** (pushes to `main` touching deps/workflows + schedule): pre-warms the Flutter/pub/fastlane/SwiftPM caches on `main`, because caches saved by a `v*` tag build aren't visible to the next tag. Its keys and Flutter version must match `_deploy_testflight.yaml` / `build_and_deploy.yaml`.
- **`build_and_deploy.yaml`** (on `v*` tags): calls `_linter.yaml`, then `_deploy_testflight.yaml` (`needs: Linter`).
- **`dependabot.yaml`**: fetches Dependabot PR metadata (auto-approve scaffolding).

Qodana (`qodana.yaml`, JVM-community linter, `qodana.starter` profile) is configured but not wired into a workflow that runs it here.

### Local pre-commit hook

The repo ships a `.githooks/pre-commit` hook that runs `dart run dart_pre_commit` (format + `analyze` with `error-level: info`, mirroring CI) against staged files. Git does not clone `core.hooksPath`, so after cloning enable it once: `git config core.hooksPath .githooks`. Config is under the `dart_pre_commit:` key in `pubspec.yaml` (`outdated`/`pull-up-dependencies` deliberately off as too noisy). Run manually with `dart run dart_pre_commit`.

- **Force-logout on server-side session revocation is now wired** (previously a TODO). `API.call` (`lib/api.dart`) detects the auth-error response and calls `getIt.get<Auth>().logout()`, whose `notifyListeners()` makes go_router re-run `redirect` and kick the user to `/auth` with no `BuildContext`. This is why `Auth` extends `ChangeNotifier` and the routers pass it as `refreshListenable` — **do not drop the `ChangeNotifier` base as "unused"**: the in-app login/logout paths navigate explicitly and would work without it, but this background scenario cannot.
- **Login completion**: every login path (call password, passkey, Yandex, cloud password) finishes through `AuthLoginCompleter` (`lib/cubit/auth/auth_login_completer.dart`), which writes the session and calls `Auth.refresh()`; the store-moderation flow does the same itself. New login methods should reuse it. An account blocked by moderation (admin panel) is refused by the server's single gate in `AUTH_CONFIRMATION` with `PermissionDenied` `auth.accountBlocked` and details in the gRPC trailer (`iperon-block-reason` / `-until` / `iperon-support`, kept in `APICallStatus.trailers`); the completer turns it into a redirect to `/auth/blocked` (`AuthBlocked{Cupertino,Material}`, `accountBlockedURI`). Other users see such a person with `Profile.accountBlocked` («Аккаунт заблокирован» instead of presence, `Chat.canPost` false). Reports to moderation: «Пожаловаться» (profile, chat info «Ещё», incoming message menu) → `lib/chats/reports.dart` `sendReport` (`REPORT`, `protos/reports_v1.proto`), UI in `lib/screens/report/` (`ReportTarget.fromChat`: secret chat → peer without content). Moderation flags of groups/channels arrive in `ChatInfo` (`moderationBlocked` → `Chat.moderationBlocked`: `ChatModerationBlockedView` instead of the feed, `canPost` false; `verified` → `VerifiedBadge` next to the title).
